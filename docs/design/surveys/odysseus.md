## What it is

A self-hosted, single-process "AI workspace for one household": chat + agent mode, deep research, document editor, IMAP/SMTP email with triage, notes/todos/calendar (CalDAV), scheduled agent tasks, a "Cookbook" that recommends and serves local models based on detected hardware, and a "Crew" of user-defined personas including a singleton "personal assistant" with timed check-ins (CONFIRMED, `README.md` Features, `core/database.py:CrewMember`, `src/task_scheduler.py:_execute_checkin`). Its own threat model says "treat it like an admin console" for trusted users on a private network; an admin session can run shell, read/write files, send mail, and serve models with no sandbox (CONFIRMED, `THREAT_MODEL.md` Trust Boundary and Known Gaps 1).

Relevance to us: it is the closest thing in the reference set to an **executive-assistant / ops surface** (email, calendar, notes, reminders, proactive check-ins) and to **local-model operations** (hardware-fit, serve profiles, context budgets, fallback chains, student/teacher escalation). It is not an orchestration kernel and its security posture is the opposite of ours.

## Orchestration model

- Single agent loop, `src/agent_loop.py:stream_agent_loop` (3,515 lines). The model emits fenced code blocks tagged with a tool name (or native function calls); the loop executes them, appends results, and repeats up to `MAX_AGENT_ROUNDS = 50` (CONFIRMED, `src/agent_tools/__init__.py:67`, `src/agent_loop.py` header docstring).
- No CEO / worker hierarchy. "Delegation" is ad-hoc: the agent may call `create_session`, `send_to_session`, `chat_with_model`, `pipeline` to spin up other chat sessions or call other models directly (CONFIRMED, `src/agent_tools/session_tools.py`, `src/agent_tools/model_interaction_tools.py`, `src/agent_loop.py:283,476-478`). These are nested LLM calls made from inside a tool, bypassing the outer loop's budget, verifier and tool policy (INFERRED from `chat_with_model` calling `llm_call_async` directly).
- Plan mode: a turn can be forced into "propose a checklist, mutate nothing" with an allowlist of read-only tools; an approved plan is pinned into the system prompt every turn and the agent ticks items via `update_plan` (CONFIRMED, `src/tool_security.py:PLAN_MODE_READONLY_TOOLS`, `src/agent_loop.py:PLAN_MODE_DIRECTIVE`, `build_active_plan_note`).
- Completion verifier: a fresh-context second model call reads the request plus an actions snapshot and returns `VERIFICATION: SUCCESS|FAIL: reasons` (CONFIRMED, `src/agent_loop.py:_run_verifier_subagent`, `_build_actions_snapshot`). Failures are advisory: on any error the verifier returns `[]` "so it can't block a valid completion".
- Runaway guard: identical `(tool, args[:120])` repeated >= 15 times aborts (CONFIRMED, `src/agent_loop.py:_detect_runaway_call`).
- Detached runs: an agent stream keeps running server-side after the SSE client disconnects, with a replay buffer and 180 s eviction grace; in-memory only, not restart-safe (CONFIRMED, `src/agent_runs.py` header).
- Background shell jobs are restart-safe via on-disk exit-code files and an "auto-continue" monitor that re-invokes the agent when a job finishes (CONFIRMED, `src/bg_jobs.py` header, `src/bg_monitor.py` exists).
- Scheduler: `ScheduledTask` rows with `once/daily/weekly/monthly/cron`, event triggers (`session_created`, `message_sent` every N events), `then_task_id` chaining, per-task `max_steps`, `webhook_token`, and a `TaskRun` table with `steps` JSON, `tokens_used`, and the resolved `model` (CONFIRMED, `core/database.py:ScheduledTask`, `TaskRun`). A shared TTL singleflight cache dedupes external fetches across tasks firing in the same minute (CONFIRMED, `src/task_scheduler.py:_cached`).
- Chat-to-agent promotion: deterministic regexes classify a plain chat message as needing tools (calendar/email/notes/shell/research) so the cheap chat path is used by default (CONFIRMED, `src/action_intents.py:classify_tool_intent`).
- Deep research: IterResearch-style Think -> Search -> Extract -> Synthesize loop with plan, per-round query generation, evolving report, bounded rounds/time/URLs, low-quality-source filter, and untrusted wrapping of fetched pages (CONFIRMED, `src/deep_research.py:DeepResearcher`, `src/research_utils.py:is_low_quality`).

## Agent roster / roles found (with paths)

There is no fixed roster; roles are data the user creates.

- `CrewMember` (`core/database.py:546`): `name`, `avatar`, `user_name`, `personality` (system prompt), `model`, `endpoint_url`, `greeting`, `enabled_tools` (JSON allowlist or `"all"`), `session_id`, `is_default_assistant` (singleton per owner), `timezone`. CONFIRMED.
- Personal assistant check-in (`src/task_scheduler.py:_execute_checkin`): gathers calendar windows grouped by importance (`critical/high/normal/low`), notes/todos, and enabled integrations (Miniflux etc.), then hands the raw bundle to the LLM to write a digest. CONFIRMED.
- `ASSISTANT_ALWAYS_AVAILABLE` (`src/tool_index.py`): the assistant's baseline tool set for scheduled/proactive runs: email read/send/archive, calendar, notes, tasks, memory, web_search, read_file, documents, contacts, `api_call`, `ui_control`. CONFIRMED.
- Reminder personas (`src/reminder_personas.py`): five voices used only to phrase one-line reminders. CONFIRMED. Cosmetic.
- Teacher role (`src/teacher_escalation.py`): a SOTA "teacher" endpoint invoked when a self-hosted "student" fails a turn; writes a SKILL.md so the student can do it next time. CONFIRMED.
- Verifier role (`src/agent_loop.py:_run_verifier_subagent`): fresh-context completion judge. CONFIRMED.
- Utility role (`src/endpoint_resolver.py:resolve_endpoint("utility", ...)`): a cheap model resolved by role for evals/summaries, with fallback to the default then the student endpoint. CONFIRMED (call site in `teacher_escalation.py:evaluate_turn_llm`).
- External coding agents: Claude Code / Codex integrations get a scope-gated bearer token and a skill bundle; every endpoint is checked server-side against per-integration toggles, 403 otherwise (CONFIRMED, `integrations/claude/README.md`, `routes/codex_routes.py` exists).

## Memory model

- Native memory: `data/memory.json` plus a vector index (FAISS historically, ChromaDB now) with owner scoping (CONFIRMED, `src/memory.py:MemoryManager`, `src/memory_vector.py`, `scripts/migrate_faiss_to_chroma.py`).
- Provider abstraction: `MemoryProvider` ABC with `remember/recall/list_memories` and `MemoryRecord{id,text,timestamp,category,source,owner,session_id,metadata}`; native provider always present, external providers additive (CONFIRMED, `src/memory_provider.py`).
- Background extraction: after each response the last N messages go to the LLM to extract "memorable facts"; a periodic LLM "tidy" audit consolidates duplicates, keyed by a content fingerprint so it short-circuits when unchanged (CONFIRMED, `services/memory/memory_extractor.py` header, `_fingerprint_entries`).
- Inline command: `remember: X` / `note: X` bypasses the LLM (CONFIRMED, `src/memory.py:process_inline_memory_command`).
- Skills as memory: `data/skills/<category>/<name>/SKILL.md` with YAML frontmatter and When-to-Use / Procedure / Pitfalls / Verification sections; usage counters in a sidecar; `status: draft` and `confidence` fields; auto-extracted from runs with >= 2 rounds or >= 2 tool calls at `MIN_CONFIDENCE = 0.6` (CONFIRMED, `services/memory/skills.py`, `services/memory/skill_extractor.py`).
- Saved memories and skill text are declared untrusted and wrapped when re-injected (CONFIRMED, `THREAT_MODEL.md` Prompt-Injection Hardening; `tests/test_skill_index_prompt_injection.py` exists).
- Context handling: adaptive input budget scaled to the discovered context window at 0.85 headroom, capped at 200k, conservative 6k when the window is unknown; Cursor-style structured self-summarization at 85% of the window with aggressive trimming for <= 8k models (CONFIRMED, `src/context_budget.py`, `src/context_compactor.py`).

## Tool / plugin / MCP model

- Built-in tools are Python functions registered in `TOOL_HANDLERS`; schemas in `src/tool_schemas.py`; a ~70-name catalog in `src/tool_policy.py:_COMMON_TOOL_NAMES` (CONFIRMED).
- RAG tool selection: tool descriptions are embedded in a ChromaDB collection and only top-K relevant tools are injected per message, plus a tiny `ALWAYS_AVAILABLE` set (`manage_memory`, `ask_user`, `update_plan`) (CONFIRMED, `src/tool_index.py`). Motivation stated in `ROADMAP.md`: "Agent prompt/context bloat ... too heavy for smaller local models".
- Per-turn `ToolPolicy` dataclass: `disabled_tools`, `hidden_tools`, `reasons`, `mode`, `block_all_tool_calls`, `disable_mcp`; "guide-only" mode is detected from the user text by regex (CONFIRMED, `src/tool_policy.py`).
- MCP: `McpManager` connects stdio and Streamable HTTP servers; per-server `disabled_tools` in the DB; MCP tool names carry an `mcp__` prefix; third-party schemas are sanitized and length-capped before being rendered into the prompt; read-only classification uses `readOnlyHint`/`destructiveHint` annotations first, then a verb-prefix heuristic, failing closed for plan mode (CONFIRMED, `src/mcp_manager.py:_format_mcp_params`, `mcp_tool_is_readonly`, `src/agent_loop.py:_load_mcp_disabled_map`).
- MCP OAuth: RFC 9728 discovery + DCR + PKCE, tokens persisted encrypted per server (CONFIRMED, `src/mcp_oauth.py` header).
- The app also ships its own MCP servers for email, image gen, memory, RAG (CONFIRMED, `mcp_servers/`).
- `ask_user`: a multiple-choice question tool that ends the turn and returns the user's click as the next message (CONFIRMED, `src/agent_loop.py:480`, `_awaiting_user`).
- Model fallback: `stream_llm_with_fallback` tries an ordered candidate list, only switching on pre-content failure, and emits a visible `{"type":"fallback","selected_model","answered_by","reason"}` event so a silent substitution is impossible (CONFIRMED, `src/llm_core.py:2435-2495`).

## Sandbox & security posture (isolation, credential handling, gates)

- Isolation: none. `bash`/`python` run as the app user via `create_subprocess_shell` with a 1 h timeout and streamed progress; file tools are confined to a workspace but "the shell starts there but is not sandboxed" (CONFIRMED, `src/agent_tools/subprocess_tools.py:BashTool`, `src/tool_index.py` `get_workspace` description, `THREAT_MODEL.md` Known Gap 1).
- Authorization is role-based (admin vs non-admin), not per-tool-risk: `NON_ADMIN_BLOCKED_TOOLS` plus anything `mcp__*`; admins get everything (CONFIRMED, `src/tool_security.py`, `THREAT_MODEL.md` Roles table).
- Internal loopback: a per-process random `INTERNAL_TOOL_TOKEN` and a reserved `internal-tool` username grant admin unconditionally in `require_admin` (CONFIRMED, `THREAT_MODEL.md` Internal Tool Loopback). A single reserved-username check is the whole boundary.
- Credentials: provider keys and IMAP/SMTP passwords Fernet-encrypted at rest with a 0600 key in `data/`; explicitly "does not protect against a process compromise" (CONFIRMED, `src/secret_storage.py`, `src/api_key_manager.py`). The agent can call `vault_search`/`vault_get` (Bitwarden CLI) and receives the **plaintext password in the tool result**; `vault_get` requires a `reason` string and logs the access (CONFIRMED, `src/tools/vault.py:do_vault_get`). Provider headers are stored on the session object and passed through tool functions (CONFIRMED, `src/agent_tools/session_tools.py:create_session`).
- Human gates: exactly one real one. With `agent_email_confirm` on (default), `send_email` stages the mail as `status='agent_draft'` in `scheduled_emails` and the UI has list/approve/cancel endpoints (CONFIRMED, `routes/email_routes.py:2351-2400`). Plan mode is a second, coarser gate (nothing mutates until the human approves the checklist). Everything else (file writes, shell, calendar, settings, model serving) executes immediately.
- Prompt-injection: `untrusted_context_message` wraps external content in a `user`-role block with escaped guard markers; policy preamble in every system prompt; the teacher's trace is wrapped again so a poisoned trace cannot become a persisted skill (CONFIRMED, `src/prompt_security.py`, `src/teacher_escalation.py:_UNTRUSTED_TRACE_GUARD`).
- SSRF: outbound URL checks reject non-HTTP schemes and link-local/metadata ranges; private ranges allowed by default because local model servers are the primary use case (CONFIRMED, `src/url_safety.py`).
- Audit: `TaskRun.steps` stores a JSON log of tool calls per scheduled run; chat sessions store messages; there is no append-only or hash-chained log and no per-LLM-call cost record (CONFIRMED for what exists; absence INFERRED from `core/database.py` model list and grep for "chain"/"cost" finding none).

## BEST PARTS

1. **Fresh-context completion verifier with an actions snapshot** — Evidence: `src/agent_loop.py:_run_verifier_subagent`, `_build_actions_snapshot`. Sector: engineering (coder fleet), executive (CEO summaries). Why: a second model with no shared history judges "did the work actually happen" from the request plus the tool record, with a strict four-item checklist. This is exactly the shape our `auditor`/`checker` should take, and the snapshot format (tool, command, exit code, output head) maps directly onto our event log, so the verifier can be fed from `tool.executed` events rather than from the worker's own claims.

2. **Plan mode as a fail-closed read-only allowlist plus a pinned approved plan** — Evidence: `src/tool_security.py:PLAN_MODE_READONLY_TOOLS`, `_PLAN_MODE_KNOWN_MUTATORS`, `src/agent_loop.py:PLAN_MODE_DIRECTIVE`, `build_active_plan_note`; MCP side `src/mcp_manager.py:mcp_tool_is_readonly`. Sector: executive, engineering, trading. Why: the allowlist is computed so that any newly added tool defaults to blocked, shell is excluded outright because it "can't be constrained to read-only at the tool layer", and MCP tools without `readOnlyHint` fail closed. The approved plan is re-injected every turn so weak local models cannot lose it. For us: a `plan` phase for CEO objectives and for any trading strategy change, enforced by the policy gate (not the prompt), with the approved checklist recorded as an event and the CEO's `update_plan` writes landing as `goal` updates in pmmcp.

3. **Student/teacher escalation that writes portable SKILL.md procedures, with the trace treated as untrusted** — Evidence: `src/teacher_escalation.py` (trigger conditions, `_SOTA_HOSTS`, `_UNTRUSTED_TRACE_GUARD`, portability rules, `evaluate_turn_regex` applied to the teacher's own reply, `source: teacher-escalation` tag), `services/memory/skills.py` (SKILL.md format with When-to-Use/Procedure/Pitfalls/Verification, `status: draft`, `confidence`). Sector: kernel (model router), engineering. Why: it is a concrete recipe for making cheap local models (Bonsai, Ollama) useful in a fleet: run the student, detect failure cheaply, escalate to a frontier model once, persist a procedure so the next run stays local. Their portability rules ("no hostnames, no absolute paths, use the wrapped tool not raw ssh/tmux") are the right constraints for skills that get shared across agents. For us the teacher call is just another routed `llm.request`/`llm.response` pair and the skill lands in pmmcp `aos/shared` as a draft that a human promotes.

4. **Model fallback chain that cannot be silent** — Evidence: `src/llm_core.py:stream_llm_with_fallback` (switch only on pre-content failure; emit `{"type":"fallback","selected_model","answered_by","reason"}` on first output from a non-primary). Sector: kernel (router). Why: Hermes-style per-task priority chains are only safe if the substitution is visible and only happens before any tokens were streamed. Our router should record `model.fallback` as an event with the same three fields and never re-issue a request after partial output.

5. **Hardware-fit model recommendation and deterministic serve profiles** — Evidence: `services/hwfit/fit.py` (bandwidth tables incl. Apple M-series by GPU core count, use-case weights, speed/context targets), `services/hwfit/profiles.py` (Quality/Balanced/Speed llama.cpp profiles from VRAM math: `n_gpu_layers`, `n_cpu_moe`, KV cache type, context), `src/cookbook_serve_lifecycle.py` (scheduler-owned serves with `_scheduledStopAtMs` that auto-stop and unregister the endpoint). Sector: kernel (models), ops. Why: this is the missing piece between `providers.yaml` placeholders and a real local fleet on an M1 Max with a ~40 GB weight+KV budget: pick quant and context per agent tier from a formula, not by hand, and time-box local serves so the memory budget is respected across agents. The "serve for a window then stop and delete the endpoint" pattern is what a T0 ops agent should be able to request and a human approve.

6. **Executive-assistant check-in bundle** — Evidence: `src/task_scheduler.py:_execute_checkin` (calendar windows grouped by importance tiers with `[!!]/[!]` markers, notes/todos, enabled integrations via a 3-minute singleflight cache), `ASSISTANT_ALWAYS_AVAILABLE` in `src/tool_index.py`, `CrewMember.timezone`, `ScheduledTask.then_task_id`, `TaskRun.steps/tokens_used/model`. Sector: executive (chief-of-staff / ops agent). Why: the shape is right for our `ops` or `chief-of-staff` standard agent: gather deterministic data first (code, not model), then let the model write the digest; run on a cron in the operator's timezone; chain a follow-up task; record steps and tokens per run. The singleflight cache is a useful kernel helper when several scheduled agents hit the same MCP server in the same minute.

7. **RAG-selected tool sets plus a per-turn ToolPolicy object** — Evidence: `src/tool_index.py` (`ALWAYS_AVAILABLE` kept "deliberately tiny", embedded tool descriptions), `src/tool_policy.py:ToolPolicy` (disabled, hidden, reasons, mode, disable_mcp), `ROADMAP.md` "Agent prompt/context bloat". Sector: kernel (hub / tool-view policy), engineering. Why: with 49 pmmcp tools plus GitHub/Vercel/Supabase packs, a T1 local model will drown. Our hub already has tool-views; adding per-run top-K retrieval over the *allowed* view, with the gate still enforcing the full policy on execution, keeps small models usable without widening access. The `reasons` map is a good pattern for the Run Inspector: every hidden tool has a human-readable reason.

8. **Untrusted-context wrapper with guard-marker escaping and second-order protection** — Evidence: `src/prompt_security.py` (`_escape_guard_markers`, label inside the guarded block, `metadata.trusted=False`), `src/mcp_manager.py:_sanitize_schema_token` (cap MCP schema tokens), `tests/test_tool_output_prompt_injection.py`, `tests/test_skill_index_prompt_injection.py`. Sector: ops-security (comms/tainted ingress), growth (scrapers). Why: our taint model decides *what a run may do*; this decides *how tainted text is presented* so the model is less likely to act on it. Both are needed. The escaping of the delimiter literals and the sanitizing of third-party MCP schemas before they hit the prompt are cheap, testable additions to the hub.

## BAD PARTS / anti-patterns

1. **Admin-or-nothing authorization; the model's reachable surface is the whole machine** — Evidence: `THREAT_MODEL.md` ("A logged-in admin can execute shell commands, read and write files, send email"; Known Gap 1 "No shell/filesystem sandbox"), `src/tool_security.py:NON_ADMIN_BLOCKED_TOOLS`, `src/agent_tools/subprocess_tools.py:BashTool` (`create_subprocess_shell`, 1 h timeout, no cgroup/network limits). Why left out: our invariant 3 and 9 require a per-call policy gate with risk classes and containerized workers. A binary admin flag is the OpenClaw-style posture we already named the anti-pattern.

2. **Secrets flow through the model** — Evidence: `src/tools/vault.py:do_vault_get` returns the password in the tool result ("Retrieve a full vault entry (including password)"), `src/secret_storage.py` docstring ("Does not protect against a process compromise"), session headers stored on the session object and handed to tool functions (`src/agent_tools/session_tools.py`). Why left out: invariant 2. A `reason` string and an audit line do not change the fact that the plaintext is in the context window and therefore in the log, the compaction summary, and any exfil path. Our broker injects at the egress proxy edge; agents never see a value.

3. **Nested LLM calls from inside tools bypass the loop's accounting** — Evidence: `src/agent_tools/model_interaction_tools.py:chat_with_model` and `ask_teacher` call `llm_call_async` directly; `send_to_session`, `pipeline`, `create_session` (`src/agent_tools/session_tools.py`) spawn other sessions from within a tool. Why left out: invariant 4 and 7 (`coding_agent`/`session_insight_agent` disabled for the same reason). Delegation in our fleet is a kernel operation (`delegate_task` creating a child run with its own budget, taint, model binding and events), never a tool that calls a provider.

4. **Gates are prompt-side or opt-in, not structural; "bias toward action" rules** — Evidence: `src/agent_loop.py:_AGENT_RULES` ("BIAS TOWARD ACTION ... JUST DO IT ... The user can undo"; "AFTER A TOOL SUCCEEDS, do not second-guess ... no validation theater"), guide-only mode detected by regex on the user's message (`src/tool_policy.py:_GUIDE_ONLY_PATTERNS`), the email confirm being a single setting `agent_email_confirm`. Why left out: invariant 3 (default deny, `irreversible` always human). Undo does not exist for a sent email, a merged PR, or a placed order. The regex-detected "no tools" mode is the model-adjacent text making an access decision by proxy.

5. **Auto-extracted memories and skills written back without a human in the loop** — Evidence: `services/memory/memory_extractor.py` ("After each LLM response ... extract memorable facts, then stores them"), `services/memory/skill_extractor.py` (auto-save at `confidence >= 0.6`), `src/teacher_escalation.py:_maybe_write_skill` calling `do_manage_skills(add)` directly. Why left out: invariant 8 spirit and the taint model. A skill is executable guidance; auto-persisting it from a run that may have read attacker-controlled content is a second-order injection channel even with their trace guard. In our fleet extracted skills and facts land as `draft` in pmmcp and a human (or a kernel-only reviewer with no write to `souls/`) promotes them.

6. **No durable, tamper-evident audit** — Evidence: `src/agent_runs.py` ("in-memory ... does NOT survive a server restart"), `TaskRun.steps` as free-form JSON in `core/database.py:650`, no cost per LLM call anywhere in the models, `mcp_servers/` and `routes/` each keeping their own state. Why left out: invariant 5. Nothing to take here; noted so nobody proposes "store steps JSON on the run row" as sufficient.

## Conflicts with CLAUDE.md invariants

1. Invariant 1 (loopback + bearer): Odysseus binds `0.0.0.0:7000` for LAN use, uses cookies plus optional `LOCALHOST_BYPASS`, and a reserved-username loopback (`THREAT_MODEL.md`, `SECURITY.md`). Their integrations use bearer tokens over the LAN. Not applicable to our control plane.
2. Invariant 2 (agents never hold credentials): violated by `vault_get`, by session-held provider headers, and by `api_call`/`app_api` tools that carry integration keys (`src/task_scheduler.py:_execute_checkin` builds auth headers from `load_integrations()` inside task code).
3. Invariant 3 (gate on every call, default deny, irreversible => human): tools execute on the model's say-so; only email send has an approval path; non-admin blocking is a denylist, admins are unrestricted.
4. Invariant 4 (two events per LLM call with cost): no cost accounting; nested calls in `chat_with_model`/`ask_teacher`/`pipeline`/verifier/teacher/memory-extractor are not individually recorded.
5. Invariant 5 (hash-chained immutable log): absent.
6. Invariant 6 (ephemeral bounded by template): `create_session` lets the agent pick any model/endpoint for a new session (`src/agent_tools/session_tools.py:create_session`), i.e. a child can be more capable than the parent.
7. Invariant 7 (unknown MCP tools kernel-only): unknown MCP tools are exposed to admins by default; only plan mode treats unclassified tools as writes.
8. Invariant 8 (souls read-only): personas (`CrewMember.personality`) and skills are model-editable via `manage_skills`, `manage_settings`, and the teacher loop.
9. Invariant 9 (container hardening): no containers; shell is the host.
10. Invariant 10 (`__` naming): compatible; Odysseus also uses an `mcp__` prefix (`src/tool_security.py:is_public_blocked_tool`).

## Verdict

Take the verification and escalation machinery as design patterns for our kernel: the fresh-context verifier fed from the event log, plan mode as a fail-closed read-only allowlist with the approved plan pinned and recorded, the student/teacher loop producing draft SKILL.md files for cheap local models, the visible-only model fallback rule, the hardware-fit serve profiles and time-boxed local serves for the M1 Max budget, and the check-in bundle shape for an executive-assistant/ops agent. Leave the entire authorization and credential model (admin-or-nothing, host shell, plaintext vault results, nested provider calls from tools, auto-persisted memories and skills, prompt-side "bias toward action"). Because it is AGPL we reimplement ideas, never copy code, and every borrowed pattern must be re-expressed as a kernel-side gate or event rather than a prompt rule.
