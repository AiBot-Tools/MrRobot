# Trading sector: crypto and stocks — aos-kernel fleet design

Sector: **trading**. Scope: market/news/on-chain research (tainted ingress), quant/strategy analysis and backtesting, a kernel-enforced risk officer (not an LLM), execution, portfolio ledger and reconciliation, journal and post-mortem, paper trading by default, live orders as `irreversible`, exchange/broker keys that are trade-only and never inside an agent.

Inputs: `CLAUDE.md` (the contract), `docs/plan/phase-0-bootstrap.md` (Phase 0 shapes for `agent.yaml`, `tool-views.yaml`, `kernel.yaml`, protocol v1, event catalog; cited as `plan §3.4/§3.6/§3.7` and decisions `D15`–`D30`), the sibling sector designs (`fleet/executive.md`, cited as `exec §N` and `exec Q/K`; `fleet/engineering.md`, cited as `eng §N` and `eng O/K`; `fleet/growth.md`, cited as `growth §N` and `growth O/G`), and the 23 survey reports under `scratchpad/survey/`.

**Evidence legend.** `CONFIRMED` = I opened the cited file in the reference clone during this task and read the cited lines (paths relative to `scratchpad/refs/`). `CONFIRMED (survey)` = the cited survey under `scratchpad/survey/<name>.md` states it read the file or fetched the URL; I read the survey. `INFERRED (snippet)` = a web fact the landscape survey could only reach through a search snippet (primary page egress-blocked); numbers are "as reported" and must be re-read from the primary source before they become config. `INFERRED` = my derivation. `DESIGN` = a choice in this document. No feature is attributed to a project without one of the first three tags.

Frontier design rules applied: no role-play theater (an agent exists only for a distinct tool surface, isolation or taint need, model binding, context boundary or gate posture; otherwise it is a template, a soul, a kernel job or a tool view); few persistent agents plus ephemeral templates; planner/executor split; verifier in a fresh context; parallel isolated workers; isolated-context delegation; memory tiers; per-task model chains; budgets; per-agent evals; every irreversible action named and human-gated; everything inside the CLAUDE.md invariants and the phase order (Phase 2 sandboxes + egress proxy before any venue key exists).

## 1. Mission

Turn the operator's capital into a supervised research-and-execution loop in which language models do the two things the evidence says they are good at — synthesising cited research and monitoring/narrating — and deterministic kernel code does everything the evidence says they are bad at: sizing, bracketing, exits, order placement, risk limits and reconciliation. Paper trading is the default and the only unattended mode. Every live order is an `irreversible` tool call decided by the operator on a card that shows the kernel-computed size, the venue, the client order id and whether the order sits inside a human-signed mandate. Exchange and broker keys are trade-only with withdrawals disabled, live only in the pmmcp vault, and are attached at the egress proxy edge for one exact hostname; no container, no agent and no event ever holds one.

Three measurable commitments:

1. **Zero model-decided money.** No manifest in this sector exposes a tool that accepts a quantity, a leverage, a stop or a recipient from the model; the `Signal` and `OrderPlan` schemas are `.strict()` and have no such fields (§3.5). The kernel's `risk` module computes size and bracket from a human-approved strategy card and the live mandate. This is invariant 3 ("the model never makes an access-control decision") extended, per agency-os's server-side invoice math, to "the model never computes money" (`agency-os/.directus/run-scripts/calculate-invoice.ts` — CONFIRMED (survey)).
2. **Every order is replayable from the log.** `order.prepared` mints the client order id before any approval card is shown; `order.submitted/acked/filled/cancelled/rejected` are chained events; the ledger, the tax lots and the halted flag are projections rebuilt from the log at boot (Phase 1 restart-safe projections). A kernel restart mid-order leaves nothing unknown: the reconcile job queries the venue by client id before anything is resent.
3. **The kill switch is kernel state, not a prompt.** `trading.halted` is a persisted event that denies every submit tool (paper and live), cancels open non-protective orders, and never flattens; flatten is a separate human decision. Breakers (daily loss, drawdown, consecutive stops, cooldown, per-symbol lockout, order count, trading window, stale data, fee erosion, naked position, reconcile drift) live in `config/trading.yaml` and no agent has a tool that can read-modify them.
4. **No decision executes stale.** An approval binds `argsHash`, but the ticket is redeemed only if the halt flag, the mandate, the signal lease, the breaker state, the ledger and a fresh quote are re-checked at **execution** time and still agree with the card, and only inside the card's TTL (default 120 s for a live submit). Anything else voids the ticket with a typed reason and mints a fresh card; nothing is ever auto-resubmitted (§3.3b). This is the executive's execution-time re-evaluation rule (`exec §7.2.5`, `growth G4`) applied to money, and it is the difference between "the operator approved these bytes" and "the operator approved this trade".

### 1.1 What the evidence says LLM agents are and are not good at in trading

Stated plainly, because the roster follows from it.

**Not good at (out of sample, with money):**

* **Generating alpha.** FINSABER (20 years, 100+ symbols, survivorship/look-ahead/data-snooping mitigated): "previously reported LLM advantages deteriorate significantly"; LLM strategies "overly conservative in bull markets ... overly aggressive in bear markets" — INFERRED (snippet) https://arxiv.org/abs/2505.07078. Backtrader-Bench: half the models at "roughly random-chance level (25%)" without tools — INFERRED (snippet) https://arxiv.org/html/2608.11232.
* **Sizing and exits.** DXRG's production record (231,638 turns, 14,596 fills, two fleets on Hyperliquid perps): "Median leverage is 5.0x in every volatility sextile across a 5.7x volatility spread" (sizing is volatility-blind); "43.2% of positions touched +300 bps of open profit within 24h; 49.3% of those still closed negative"; "a fixed 2%/4% bracket beat every discretionary exit we measured, +39.0 bps per position"; the fleet "trails a matched Hyperliquid retail benchmark (41% vs. 50% roundtrip win rate)" — CONFIRMED (survey) https://github.com/ProjectDXAI/continuous-record-llm-trading-agents and INFERRED (snippet) https://arxiv.org/abs/2609.05663.
* **Not overtrading.** Alpha Arena Season 1 (n=6, 17 days, one venue): "Qwen executed an excessive 1,418 trades"; "PnL ... was dominated by trading costs in early runs as agents over-traded and took quick, tiny gains that fees erased" — INFERRED (snippet), landscape-trading-growth A9. Only the behavioural findings (overtrading, fee erosion, wide dispersion) are robust; model rankings from that contest are noise.
* **Being consistent.** Three frontier models "tied on decision quality" but "choice consistency differed sharply (35% vs 90%+ flip rate)" — CONFIRMED (survey) DXRG. Agent Market Arena: "agent frameworks display markedly distinct behavioral patterns ... whereas model backbones contribute less" — INFERRED (snippet) https://arxiv.org/abs/2510.11695. Translation: the operating layer (what is rendered, what is enforced) decides outcomes more than the model or the prompt.
* **Not leaking the future.** Any backtest overlapping the model's training window "inherits an additional bias that lives inside the model's weights and is invisible to data-pipeline audits" — INFERRED (snippet) landscape A10; TradingAgents itself shipped "look-ahead / point-in-time fixes" in v0.3.1/v0.4.0 — CONFIRMED (survey) README changelog. Bias survey: "no single bias is discussed in more than 28 percent of studies" — INFERRED (snippet) https://arxiv.org/html/2602.14233v1.

**Good at (supported):**

* **Research synthesis with citations**: filings, news, macro turned into a structured, sourced brief (TradingAgents analyst layer; ai-hedge-fund "Language models form _views_ and _narrate_ decisions" — CONFIRMED (survey) https://github.com/virattt/ai-hedge-fund/blob/main/VISION.md). The best persona text in the surveyed set is a research discipline, not a trader: "Always present both sides", "Cite primary sources. SEC filings, earnings transcripts", "Quantify the downside", "thesis breakers", "Disclose your confidence level" (`agency-agents/finance/finance-investment-researcher.md` rules 1–8 — CONFIRMED).
* **Event monitoring and classification**: TradingAgents' News Analyst "monitors global news and macroeconomic indicators, interpreting the impact of events" — CONFIRMED (survey); classification is what the cheap lanes do reliably.
* **Strategy-development assistance through a tool surface**: Jesse's "local Model Context Protocol (MCP) server" for strategy development and backtesting, with live trading a separately installed plugin — CONFIRMED (survey) https://github.com/jesse-ai/jesse.
* **Narration and post-mortems**: the "Back Office" ledger of "positions, P&L, and every decision" (ai-hedge-fund VISION.md — CONFIRMED (survey)) is a job for the event log plus a narrator.

**Design conclusion.** The LLM roles are `market-scout` (research, tainted), `quant` (strategy design and signal proposals, with backtests as a sandboxed tool), `executor` (bounded order planning and monitoring, default mode deterministic), `bookkeeper` (journal and post-mortem over the ledger) and two critic souls on the fleet `judge` template. The risk officer, the ledger, reconciliation, sizing, bracketing, order idempotency and the kill switch are kernel code. Anything that "trades" discretionary size and exits is refused (§8).

## 2. Org topology

```
operator (control plane, HumanActor)     approvals, mandates, halt/resume/flatten, strategy-card sign-off, key attestation
   |
 ceo (orchestrator, exec §2.1)           delegates ONE trading objective per run; depth 1; sees terminal events only
   |
   |-- quant (persistent, sector lead per exec §8.6: plans, no spawn)   T1 kernel-hosted + hostile sandbox for `bt.run`
   |-- executor (persistent, clean-only)                                 T0/T1 kernel-hosted, riskCeiling irreversible
   |-- bookkeeper (persistent, scheduled)                                T1 kernel-hosted, local-first models
   |
   `-- ephemeral leaves (spawned by the CEO from templates; cannot spawn):
         market-scout (profile of the fleet `scout` template; souls news/filings/onchain/sentiment; always tainted)
         critic       (the executive `judge` template; souls bear, compliance-reviewer; fresh context, read-only)

 kernel components owned by this sector (no LLM, no manifest):
   risk officer  src/trading/risk.ts + config/trading.yaml   (limits, breakers, kill switch, mandate checker, sizing)
   ledger        src/trading/ledger.ts                        (positions, lots, P&L, wash-sale flags; projection from events)
   reconcile     src/trading/reconcile.ts (Phase 1 cron)      (venue state vs ledger; drift trips the halt)
   order planner src/trading/order-planner.ts                 (deterministic OrderPlan when the executor LLM is off)
   bt            kernel-hosted tool over the hostile sandbox  (point-in-time backtests; typed backtest.result)
   venue packs   MCP adapters in a T2 container, keyless      (alpaca / coinbase / hyperliquid / ibkr; keys injected by the proxy)
```

* **Depth is 1.** The CEO is the only delegator (`exec §2.1`, `KERNEL_MAX_DEPTH = 1`). The sector lead `quant` is a non-delegating planner-worker: it returns a `ProposedPlan` (which scouts to run, which backtests, which signals to stage) and the CEO fans out (`exec §2.2`, `exec §8.6`). This keeps the relayed-approval surface closed and matches the evidenced shape (one orchestrator, isolated workers — `landscape-coding-fleets.md` anti-pattern 3, CONFIRMED (survey)). Revisit only under `exec Q1` after the Phase 1 harness.
* **Iteration loops stay inside one run.** The quant's evaluator-optimizer loop (hypothesis → `bt.run` → read metrics → revise) does not need delegation because the backtest is a *tool* the kernel executes in the hostile sandbox and returns as a typed event, not an agent (frontier rule 1: a backtest has no persona, no context of its own and no gate posture beyond `write-sandbox`). Same for `sim.run` (§3.8).
* **The taint boundary is a human approval, not a schema.** Scouts read the web and are tainted; the quant consuming their results is tainted (`exec §3.1` taint rule: `child.taint = max(parent.taint, taint of every inputRef)`); therefore the quant's `signal.propose` write parks for a human (invariant 3). The human's approval of a batch of signals is the one place untrusted research becomes an input the clean `executor` may read. This is the operator decision the brief asked to flag (Q1): the alternative, letting a numeric-only schema launder taint, is specified but not the default.
* **Execution is clean by construction.** The registry refuses `run.start { agentId: 'executor', taint: 'tainted' }` and refuses a `delegate` whose `inputRefs` carry taint (`spawn.rejected { reason: 'taint' }`, K3); the executor's only signal source is the kernel-native `signals.read` tool with the precondition `approvedBy != null`. It never sees a memo, a headline or a tweet.

### 2.1 Tiers: isolation, capability, risk ceiling

Phase 0's `tier: 0..3` is a capability ladder (`plan §3.4` D15: 0 no tools, 1 read-only MCP, 2 write tools + sandbox exec in `trusted`, 3 may request `irreversible`). The starter roster's T0–T3 is an isolation ladder. `exec Q7` proposes keeping D15 as `tier` and recording isolation as `sandbox.domain`; `eng O1`/`K1` proposes a separate `riskCeiling: read | write | irreversible`. This sector needs all three axes: the quant is capability-2 (writes signals) with isolation `hostile` for `bt.run` (it executes strategy code) and ceiling `write`; the executor is capability-3 (requests live submits) with no sandbox at all and ceiling `irreversible`; the bookkeeper is capability-2 (journal writes) with no sandbox and ceiling `write`. Manifests below state `tier (D15) / sandbox.domain / riskCeiling` and this document adopts `eng K1` (open decision Q8 here).

### 2.3 The sector's approval budget (how many decisions a day this actually asks for)

`exec §7.5` sets a fleet-wide `approvals.dailyBudget` (default 20) and names trading "the dominant term ... the reason option B keeps being asked for". A sector that never counts its own asks is why that term is dominant, so the count is a design constraint here, not an outcome:

| mode | cards/day reaching the operator | what holds it down |
|---|---|---|
| Phase 1 (research only) | ~0.3 | memos are read-only; promoting one to `aos/shared` is the curator's card, not this sector's |
| Phase 2 paper | **≤ 2** | one deferred `tainted-write` batch card per day carrying the whole signal batch (per-signal ticks inside one card), plus a `strategy` card only when one is proposed or expires (~1/week) |
| Phase 2-late / 3 live per-order | **≤ 5** | `limits.maxOrdersPerDay` for any `live` venue defaults to **3**, and the executor is scheduled on **two fixed approval windows** so the operator is interrupted twice rather than ten times; plus at most one halt/resume and one escalation |

Three rules make those numbers kernel facts rather than hopes:

1. **The lever is fewer orders, not fewer approvals.** Nothing here batches, defers or trust-rules an `irreversible` submit (`exec §7.2`, and `exec §7.2.5` restricts trust rules to `write`-from-a-clean-run, which excludes every card in this sector). When the count is too high the operator lowers `maxOrdersPerDay`, narrows the mandate or slows the strategy — all data edits, none of them gate edits.
2. **Trading takes the fleet's back-pressure.** When the unresolved deferred queue exceeds `approvals.dailyBudget`, the scheduler refuses to start new unattended `schedule:` runs of `executor` and `quant` and logs `schedule.skipped { reason: 'approvalBacklog' }` (`exec §7.5`). Nothing auto-approves, nothing expires early, in-flight runs are untouched, and an operator-started run is never blocked.
3. **Safety cards are exempt from the budget and from back-pressure.** Halt notifications, `trading.flatten` cards, protective-leg escalations (§3.3.1) and `trading.drift` escalations are never counted against the budget and never suppressed by it. Back-pressure that delays a stop is a risk control that increases risk.

If the measured count exceeds these numbers for five consecutive days, the sector is misdesigned; the response is a narrower mandate or a slower strategy, recorded as an operator decision, never a widened gate.

## 3. Kernel components of the sector (defined first because every manifest references them)

### 3.1 The risk officer: `src/trading/risk.ts` over `config/trading.yaml`

Deterministic, no model call, evaluated by the gate as **preconditions** on every venue write tool (`eng K2` `preconditions`, `exec K5` argument preconditions) and by the scheduler as **breakers**. Config is data the agent cannot reach: `config/` is a protected root (`plan` T16 `PROTECTED_ROOTS = ['souls','agents','config']`), so any tool argument resolving under it is denied `protected-path` before execution (`plan` T13). The shape (zod `.strict()`, every number positive, no field admits "unlimited"):

```
trading:
  version: 1
  mode: paper                      # paper | live-per-order | live-mandate ; only the control plane changes it (K7)
  moneyUnit: microUsd              # integer everywhere (D4); crypto notional converted at the quote used for the order
  limits:                          # hard ceilings; a mandate may only be narrower
    maxNotionalPerOrderMicroUsd, maxOpenNotionalMicroUsd, maxPositionsOpen, maxLeverage (1 = none),
    maxOrdersPerDay, maxOrdersPerSymbolPerDay, riskFractionPerTradeBps (e.g. 50 = 0.5 % of equity),
    maxDailyLossMicroUsd, maxDrawdownBps (peak-to-trough), tradingWindows: [{ venue, days, startLocal, endLocal }],
    shortSelling: { equities: false, cryptoPerps: true }    # an equities short needs a locate and can be recalled; default off (Q15)
    maxPriceDeviationBps: 50         # plan price vs the quote taken at prepare; re-checked at execution (§3.3b)
    maxSlippageBps: 30               # a "market" order is submitted as a marketable limit at quote +/- this, where the venue allows
    maxSpreadBps: 60                 # deny when the book is wider than this (the overnight crypto wick)
    # IBKR's precautionary settings (order size, total value, "% from market price") are the evidenced analogue of these
    # three, and §8 refuses "Bypass Order Precautions for API Orders" -- so the kernel must own the same checks itself
    # (INFERRED (snippet) landscape A11/A12)
  bracket:                         # DXRG: a fixed bracket beat every discretionary exit (CONFIRMED (survey))
    stopLossBps: 200, takeProfitBps: 400, trailing: false      # defaults; per-strategy override only via a human-approved strategy card
  breakers:                        # freqtrade protections vocabulary (CONFIRMED (survey) docs/includes/protections.md)
    stoplossGuard: { lookbackMinutes, tradeLimit, stopMinutes }          # StoplossGuard
    maxDrawdown:   { lookbackDays, maxDrawdownBps, stopMinutes }         # MaxDrawdown
    cooldown:      { afterExitMinutes }                                  # CooldownPeriod
    lowProfitPairs:{ lookbackDays, minProfitBps, lockMinutes }           # LowProfitPairs → per-symbol lockout
    dailyLoss:     { maxDailyLossMicroUsd }                              # FIA daily-loss rule (INFERRED (snippet))
    markToMarket:  { killSwitchRateBps }                                 # Hummingbot kill_switch_rate fires "even without new trades" (CONFIRMED (survey))
    staleData:     { maxQuoteAgeMs }                                     # no fresh quote → deny new orders
    reconcile:     { everyMinutes, driftNotionalMicroUsd, driftPositions: 0 }   # any unknown position = drift
    feeErosion:    { lookbackDays, maxFeeToGrossPnlBps, lockMinutes }    # Alpha Arena's measured failure was fees, not direction
    overtrading:   { maxOrdersPerStrategyPerDay, lockMinutes }           # per-strategy, narrower than the global order cap
    nakedPosition: { onDetect: 'halt' }                                  # an open position with no resting protective leg (§3.3.1)
  venues:                          # allowlist; a venue absent here does not exist to the gate
    # every venue declares how it brackets, what happens if a protective leg fails, and how it encodes a client order id
    - id: fake-venue,   hostname: -, assetClass: both, mode: paper, bracketSupport: native, clientIdFormat: raw   # Phase 2a, in-process
    - id: alpaca-paper, hostname: paper-api.alpaca.markets, assetClass: equities, mode: paper, keyVaultId: alpaca-paper,
      bracketSupport: native, onProtectiveFailure: escalate, clientIdFormat: { kind: string, maxLen: 48 }
    - id: alpaca-live,  hostname: api.alpaca.markets,       assetClass: equities, mode: live,  keyVaultId: alpaca-live,  keyScopes: [trade], withdrawals: disabled, ipAllowlisted: true,
      bracketSupport: native, onProtectiveFailure: escalate, clientIdFormat: { kind: string, maxLen: 48 }
    - id: hyperliquid-testnet, hostname: api.hyperliquid-testnet.xyz, assetClass: crypto-perps, mode: paper, ...,
      bracketSupport: attached, onProtectiveFailure: reduce-only-close, clientIdFormat: { kind: hex, bytes: 16 }   # required: maxLeverage > 1
  instruments:                     # allowlisted symbols per venue; wildcard refused
  marks:                           # the feed the breakers need (§3.2a); without it markToMarket is prose
    everyMs: 15000                 # only while a position is open
    logEveryMs: 60000              # sampling into the chained log, plus every mark that trips or clears a breaker
  keys:
    rotationDays: 90               # raises trading.key.stale
    maxAgeDays: 180                # past this the gate refuses live mode for that venue; paper keeps working
  promotion:                       # kernel preconditions on trading.mode.set live-* (§3.1 check, T-K19)
    minPaperDays: 60, minPaperOrders: 100, maxDriftEventsInWindow: 0, maxNakedPositionEvents: 0
    requirePaperBeatsBenchmarkNetOfFees: true
    drillMaxAgeDays: 45            # halt drill and restart/reconcile drill must both be fresher than this
    requireKeyProbePass: true
  compliance:
    washSaleTracking: { equities: true, crypto: false }    # flag per asset class (INFERRED (snippet), re-verify; §10 Q12)
    dayTradeCounting: true                                 # PDT status INFERRED (snippet); re-read FINRA 26-10 before relying on it
    settlement: { equities: 'T+1' }                        # a cash account cannot re-use unsettled proceeds; INFERRED (snippet), Q12
```

Functions (pure, unit-tested, fed by projections, never by model text):

* `size(signal, strategyCard, mandate, ledger, quote) → { qty, notionalMicroUsd, stopPrice, takeProfitPrice, reason }` — `riskPerTrade = equity × riskFractionPerTradeBps`; `qty = min(riskPerTrade / stopDistance, maxNotionalPerOrder / price, remainingOpenNotional / price, mandate caps)`; stop distance from the strategy card's bracket or an ATR-scaled stop (volatility-aware by construction, the DXRG failure inverted — CONFIRMED (survey)). Returns `qty: 0` with a reason when any cap is binding, and the gate turns that into `deny` with the same reason.
* `check(order, mandate, ledger, clock) → ok | { deny: reason }` — venue and instrument allowlisted; inside trading window; not halted; not locked out; order count and notional caps; no leverage above cap; live only when `mode` and mandate agree; duplicate `clientOrderId` refused; a `side: 'short'` on an equities instrument is refused unless `limits.shortSelling.equities` is true **and** the venue pack's `venue.instrument.get` reports the symbol easy-to-borrow (no locate ⇒ `deny: no-locate`, and a short-sale-restricted symbol forces limit-only at or above the national best bid ⇒ `deny: ssr-market-order`); a buy whose cash comes from unsettled proceeds in a cash account is refused (`deny: unsettled-funds`); the plan's effective price is within `limits.maxPriceDeviationBps` of `quoteAtPrepare` (`deny: price-deviation`), the book is no wider than `limits.maxSpreadBps` (`deny: spread`), and a `market` order is rewritten by the kernel into a marketable limit at quote ± `limits.maxSlippageBps` on any venue that supports one (`deny: no-slippage-cap` where it does not); an open or filled order already referencing the same `(signalId, venue, instrument)` is refused (`deny: duplicate-intent`, §3.3a). Reason codes are a frozen literal list, logged on `tool.gate`. **`check` is called twice for every order: once at `venue.prepare` and again at ticket redemption against the state of the world at that moment** (§3.3b).
* `breakers.evaluate(ledger, marks, now) → [{ breaker, tripped, until }]` — run on every fill event, on every mark update (mark-to-market, not only on fills), and on the scheduler tick; a trip appends `trading.breaker.tripped` and then `trading.halted { by: 'breaker', breaker }` (§3.4).
* `mandate.covers(order, mandate) → boolean` — used to label the approval card `withinMandate` and, only if the operator chooses Q2 option B, to satisfy the human-decision requirement for a bounded class of live submits.
* `promotion.eligible(venue, ledger, drills, keyProbe, now) → ok | { refuse: reason }` — the precondition on `trading.mode.set live-*`. Going live was a human intention in v1 and nothing checked it; now the paper record (days, orders, zero drift, zero naked positions, net-of-fees vs the benchmark), the freshness of the halt and restart drills, and the key probe are all kernel facts. A human may still override, but only through `trading.mode.force` — its own `irreversible` control-plane command with a typed reason, logged as `trading.mode.forced`★ — so "we went live without evidence" is a row in the chain rather than a memory.

Its own eval: property tests over the projections (a random walk of fills never crosses a cap; a halt never re-opens without a `trading.resumed` event; sizing is monotone in volatility). It never reads model output.

### 3.2 Ledger and reconciliation: `src/trading/ledger.ts`, `src/trading/reconcile.ts`

* **Ledger** is a projection over `order.*` and `fill.*` events (§3.10): positions by venue/instrument, average cost, tax lots (FIFO by default, lot ids), realised/unrealised P&L in integer micro-USD, open orders, daily order counts, equity curve, peak (for drawdown). Rebuilt from the log at boot (Phase 1 restart-safe projections, `exec K9`). Nothing is a mutable row.
* **Reconcile** is a Phase 1 cron job (`schedule:` on a kernel job, not on an agent): every `breakers.reconcile.everyMinutes` it calls the venue pack's read tools kernel-only (`hub.callKernelOnly`) — positions, balances, open orders, fills since the last cursor — and diffs against the ledger. Emits `trading.reconciled { venue, deltas }` or `trading.drift { venue, kind: unknown-position | qty-mismatch | orphan-order | balance-mismatch, evidence }`; drift above threshold trips the halt (§3.4). It also resolves ambiguous submits: any `order.submitted` without an `order.acked`/`order.rejected` within `ackTimeoutMs` is looked up by `clientOrderId` before the kernel considers a resend ("query ... by `client_order_id` to confirm the order's absence before sending again" — INFERRED (snippet) landscape A12). Missed ticks are claimed-before-dispatch and coalesced, never replayed twice (prime-agent `claimDueInState` — CONFIRMED (survey)); three consecutive failures auto-disable the schedule with a machine-readable reason and trip the halt (OpenHands automation health rules — CONFIRMED (survey) `OpenHands/src/types/automation.ts`), because a trading loop with no reconciliation is a loop with no floor.
* **Wash-sale flag**: for equities, a sell at a loss followed by a buy of the same symbol within 30 days before/after (the 61-day window, IRC §1091 — INFERRED (snippet)) emits `trading.wash_sale_risk` and the card for the offending order carries it; the kernel does not block (tax treatment is the operator's call), it warns.

### 3.2a Marks: the feed the breakers actually need

`breakers.markToMarket` and `maxDrawdownBps` are worthless if nothing produces marks, and v1 named no producer: the only clock in the sector was the five-minute reconcile, which on a leveraged perp is a five-minute hole. Hummingbot's kill switch is explicitly the kind that must fire "even without new trades occurring" (CONFIRMED (survey) kill-switch.mdx), so marks are a named kernel job, not an assumption:

* `src/trading/marks.ts` polls `venue.quote` (or subscribes where the pack offers a stream) every `marks.everyMs` (default 15 000) **while any position is open**, and not at all when the book is flat, so the cost is proportional to exposure rather than to uptime.
* Every poll updates the mark table and calls `breakers.evaluate(ledger, marks, now)`. Marks are **sampled** into the log (`market.mark`★ at `marks.logEveryMs`, plus every mark that trips or clears a breaker), because a 15-second tick written into a hash-chained log is 5 760 events a day for nothing.
* A mark older than `staleData.maxQuoteAgeMs` denies new orders **and**, if a position is open, trips `staleData` into a halt: not knowing the mark on an open leveraged position is itself the emergency, not merely a reason to stop adding to it. `market.data.stale` carries the last good mark and its age.
* The job is the same claim-before-dispatch scheduled job as reconcile (prime-agent `claimDueInState` — CONFIRMED (survey)) and auto-disables into a halt after three consecutive failures (OpenHands automation health — CONFIRMED (survey) `src/types/automation.ts`).

### 3.3 Order idempotency and the venue write ladder

Every venue pack exposes the same three-mode ladder, defined once in `tool-views.yaml` (eliza's `simulate` needs "only the wallet's public key, never a private key ... it cannot authorize or lead to a live submission and it skips the confirmation gate entirely"; `prepare` "stages the transaction but does not sign or send" — CONFIRMED `eliza/plugins/plugin-wallet/README.md` line 19):

| verb | risk | who | what |
|---|---|---|---|
| `venue.quote`, `venue.book`, `venue.candles`, `venue.positions`, `venue.balances`, `venue.orders.list`, `venue.order.get`, `venue.fills` | `read` | executor, bookkeeper (typed wrappers), reconcile (kernel) | keyless where the venue allows (public data), key-scoped `view` otherwise |
| `venue.simulate` | `read` | executor, quant | kernel-side fill estimate from the current book/quote plus fee schedule; no venue call, no key |
| `venue.prepare` | `write` | executor | mints the canonical `orderKey` in the **kernel**, encodes it per venue into `venueClientId`, computes size **and the protective legs** via `risk.size`, appends `order.prepared { orderKey, venueClientId, legs, argsHash, sizeReason, quoteAtPrepare }`; nothing leaves the machine |
| `venue.paper.submit` | `write` | executor (clean run) | paper endpoint or testnet; carries the prepared `clientOrderId`; allowed unattended for a clean run within mandate/limits |
| `venue.cancel` | `write`, precondition `orderRole != 'protective' → needs-human` | executor, halt routine | cancelling a stop/take-profit leg widens risk, so it needs a human even on paper |
| `venue.live.submit`, `venue.live.replace` | `irreversible`, `approval: always` | executor | the card shows the prepared preview's hash, kernel size, venue, instrument, `clientOrderId`, `withinMandate`; a retried submit reuses the id |
| `venue.close_position` (flatten) | `irreversible` | control plane only (`trading.flatten`) | never automatic |
| `venue.transfer`, `venue.withdraw`, `venue.keys.*`, `venue.account.settings`, any `*margin*` toggle | `kernel-only` (and the key must lack the scope anyway) | nobody | invariant 7; the operator attests at key registration that withdrawals are disabled and the IP allowlist is the proxy's egress IP |

**Order identity: one canonical key, a per-venue encoding.** v1 minted `aos-<runId8>-<seq>` and sent that string to every venue. Two problems, both evidenced. (a) A truncated run id with no time component is exactly the collision the survey cites from the wild — "give `client_order_id` a per-run time component to stop same-day collisions" (CONFIRMED (title) https://github.com/AustinWinstanley/trading-bot/pull/39, via landscape A12). (b) It is not portable: Alpaca accepts an arbitrary string ≤ 48 chars (CONFIRMED (survey) alpaca-docs orders.md) while Hyperliquid uses a `cloid`, a fixed-width client order id (CONFIRMED (survey) that `cloid` is the mechanism and that cancel-by-`--cloid` exists; its exact encoding is INFERRED and must be read from the SDK before that pack ships). So the kernel mints one canonical `orderKey` (UUIDv7 — time-ordered, 128 bits, no truncation) and every venue pack declares a `clientIdFormat` with a deterministic **injective** encoding into `venueClientId` (`aos-<base32(orderKey)>` for a string venue, the raw 16 bytes as hex for a `cloid`-style venue). `order.prepared` records both; internal dedupe, leases and reconcile key on `orderKey`, the wire carries `venueClientId`, and a pack whose encoding is not injective fails its own pack test. `clientOrderId` elsewhere in this document means `venueClientId`.

The idempotency key is minted **before** the operator sees the first card and bound to the logical order for the card's lifetime (eliza `trade-confirmation.ts` lines 1–5: "binds one idempotency key to a logical order before the user sees the first confirmation prompt"; TTL 5 min at line 17; key = `randomUUID()` in `steward-trading-service.ts:473`; venue-neutral `SubmitOrderRequest` per venue with `idempotencyKey?` in `types/trade.ts:80-107` — all CONFIRMED). Coinbase returns the existing order on a duplicate `client_order_id` and its SDK warns that an empty id "will remove the intended safeguard of accidentally placing duplicate orders" (CONFIRMED (survey) coinbase-advanced-py README); Alpaca 422s on a duplicate active id and should be treated as a dedupe key, not an idempotent create (INFERRED (snippet)). The kernel therefore never trusts the venue's dedupe alone: `submitWithRecovery` looks the id up on any ambiguous response before a resend (§3.2).

#### 3.3.1 Brackets are atomic, or the trade does not happen

v1 required §3.4 to refuse a cancel that would strip a "resting protective stop" without ever saying who put one there. An entry submitted now and a stop submitted in the next call is a window in which a crash, a leg rejection, a rate limit or a halt leaves a naked position — and on a leveraged perp that is the one failure in this sector that can exceed the whole account. The protective legs are therefore part of the order, not a follow-up:

* Every venue declares `bracketSupport: native | attached | none`. `native` = entry, stop and take-profit go as one payload (an Alpaca-style bracket order class, or a venue-native OCO / TP-SL group); `attached` = the legs are separate calls but reduce-only resting orders exist; `none` = neither.
* On `native` the submit is one call, a partial fill keeps the group, and there is no window at all. This is the only configuration allowed for a new venue by default.
* On `attached` the kernel submits the entry, attaches the legs, and if every leg is not confirmed resting within `protectiveAttachTimeoutMs` (default 5 000) it executes the venue's `onProtectiveFailure`. `order.legs.attached`★ / `order.legs.failed`★ make the window visible in the log.
* `onProtectiveFailure` is **per-venue human-set config**: `escalate` (default) halts the sector, notifies immediately (never deferred) and leaves the position for the operator; `reduce-only-close` additionally submits a reduce-only market close under a `KernelActor` ticket (§3.4). Unwinding a position is a money decision, so `reduce-only-close` is a **pre-authorisation the operator writes into `trading.yaml`** — never a runtime choice, never a model's, and never inferred from the situation. It is also *required*: an instrument whose venue is `bracketSupport: attached | none`, or whose `maxLeverage > 1`, cannot be enabled at all unless its venue sets `onProtectiveFailure: reduce-only-close`. Leverage is permitted only where the kernel was pre-authorised in writing to unwind.
* `naked-position` is a first-class `trading.drift` kind and a breaker: reconcile raises it for any open position with no resting protective order, whatever the cause, and `breakers.nakedPosition` halts on detection. This closes the loop with §3.4, which may now assume that "the protective leg" is a thing that exists.

### 3.3a Single-writer rule (the hole idempotency alone does not close)

`orderKey` is minted per prepared order, so two *concurrent* executor runs reading the same approved signal would mint two different keys and the venue would honour both orders. Idempotency protects against a retried submit, not against a duplicated intent. Three kernel rules close it, all deterministic:

1. **One executor run per venue at a time.** The executor's lane has `concurrency: 1` per `venue` and the run holds the lease key `trading.venue:<venueId>`; a second `run.start` for a busy venue is queued, never parallelised. A scheduled tick that arrives while the previous tick is still running is coalesced, not stacked (prime-agent `claimDueInState` claim-before-dispatch — CONFIRMED (survey)).
2. **A signal is claimed, not merely read.** `signals.read` takes a lease: the kernel appends `signal.claimed { signalId, runId, leaseUntil }` and `signals.read` in any other run skips a signal with a live lease. The lease expires (default 10 min) and expiry is a logged release, never a silent one (`landscape-agent-os` anti-pattern 10: every wait needs an expiry — CONFIRMED (survey)). A signal already carrying an `order.prepared` is never re-served. **The mechanism is not new kernel machinery**: this is `growth G11`'s lease table (compare-and-set acquisition at admission, typed refusal for the loser, release on `run.finished`, expiry on orphan, `lease.held` evaluated as a precondition at execution time) with the lease keys `trading.signal:<signalId>` and `trading.venue:<venueId>`. Trading contributes the key naming and the `duplicate-intent` reason code and nothing else; a second lease implementation for this sector would be the sector's own worst bug.
3. **One live order per `(signalId, venue, instrument)` unless the human says otherwise.** `risk.check` denies `duplicate-intent` when an open or filled order already references the signal, even under a different `clientOrderId`. This is the kernel-side analogue of FIA's "duplicate checks" (INFERRED (snippet) landscape A12) applied at the *intent* layer rather than the wire layer, because the wire layer cannot see two ids for one decision.

Restart interacts with all three: leases are a projection rebuilt from the log, and the post-boot reconcile (§3.2) runs before any executor run is admitted, so a lease held by a run that died is released only after the venue has been queried by `clientOrderId`.

### 3.3b Execution-time re-evaluation, ticket TTL, exactly-once

An approval is a decision about a *state of the world*; v1 bound only the bytes (`argsHash`). An operator who approves a live submit at 10:00 and taps it at 10:20 could execute into a halted kernel, a breaker tripped since, an expired or revoked mandate, an expired signal, a lease taken by another run, or a market 3 % away. So every trading ticket is re-evaluated at **redemption**, not at request time — the executive's rule for continuations and trust rules (`exec §7.2.5`: the taint check happens at execution time, not at rule-creation time) and growth's gate rule for taint, lease and provenance (`growth G4`), applied here to the whole risk state:

`halted == false` · mandate live, unexpired, unrevoked and still covering the order · signal lease still held by this run and `validUntil > now` · no breaker tripped since the card was filed · `risk.check` re-run against the **current** ledger and clock · a fresh `venue.quote` inside `staleData.maxQuoteAgeMs` whose price is within `limits.maxPriceDeviationBps` of `quoteAtPrepare` and whose spread is inside `limits.maxSpreadBps` · the `StrategyCard` still approved and unexpired.

Any failure **voids the ticket** with a typed reason (`stale-decision:<check>`), emits `approval.voided`★, and the run must prepare again and file a fresh card. A void is never an execution, and nothing is auto-resubmitted. Two supporting rules:

* **Ticket TTL.** A live-submit card expires after `approvals.trading.ttlMs` (default 120 000; eliza's five-minute confirmation TTL is the ceiling — `trade-confirmation.ts:17` CONFIRMED). Expiry is a logged deny the operator can see, not a silent gap.
* **Exactly-once, and never re-armed.** The submit executes under the executive's `approvalId`-keyed receipt (`exec §7.2.7`, from orca's `mutation_receipts` — CONFIRMED (survey)), so a crash between approval and result cannot double-send. On boot, a receipt still `pending` whose order cannot be found at the venue by `venueClientId` is **not** retried; it is surfaced as an escalation. Mastra's rule is the right asymmetry — "a stuck running run is strictly safer than silently re-arming a suspension" (`packages/core/src/workflows/workflow.ts:4490-4560` — CONFIRMED (survey)) — and with money the asymmetry is larger still.

### 3.4 Kill switch, breakers, ESTOP

* `trading.halt { reason }` is a **human** control-plane command (K7) and also the automatic consequence of a tripped breaker or a reconcile drift. Effect, in order, all kernel-side: append `trading.halted { by: human | breaker | drift | estop, reason }`; the gate denies every `venue.*submit*`, `venue.live.replace` and `venue.paper.submit` with reason `halted`; the kernel cancels open **non-protective** orders through `venue.cancel` under a kernel ticket and logs each; protective legs stay; **no flatten**. One ordering rule matters more than it looks: a cancel is evaluated against the position it would expose. If cancelling an order would leave an open position with no resting protective stop — the common case where entry and bracket are one OCO group, or where a partial fill has already occurred — the kernel **refuses that cancel**, keeps the protective leg alive, and files an `escalation` notification naming the position. A halt that strips a position's stop is a halt that increases risk, which is the opposite of the intent; the halt still blocks every new submit while the operator decides. "Kill switches block all new order placement ... persist across restarts, though they are not an automatic flattening action" — INFERRED (snippet) landscape A12; Hummingbot's kill switch "stops the bot" on a mark-to-market threshold "even without new trades occurring" — CONFIRMED (survey) hummingbot-docs kill-switch.mdx.
* `trading.flatten { venue?, instrument? }` is a separate human command producing `irreversible` `venue.close_position` calls, each its own approval card (batching is a view; irreversible items are listed individually — `exec §7.2`).
* `trading.resume` is human-only; the projection refuses to resume while a breaker's `until` is in the future or a drift is unresolved.
* The fleet-wide ESTOP (Hermes `agent/estop.py` header: a sentinel file, "cron scheduler, kanban dispatcher and new gateway turns skip work; in-flight work is never killed ... a corrupt/empty file still counts as engaged" — CONFIRMED; `eng §2` `eng.pause`) also halts trading: the halt projection reads the ESTOP sentinel, and a corrupt sentinel counts as engaged.
* **Kernel-initiated venue writes are a named, enumerated actor, not an exception.** The halt routine's cancels and the protective-failure close (§3.3.1) run as `KernelActor` tickets: emitted only by routines on a code-level allowlist (`halt.cancel`, `protective.recover`, `reconcile.read`), gated and logged exactly like an agent's call (`tool.gate { actor: 'kernel', routine }`), never requestable by any agent, manifest, tool argument or config flag, and enumerable in the Ops Deck. "The kernel did it" has to be as auditable as "the executor did it", or `KernelActor` quietly becomes the sector's bypass — which is the Hermes floors-first lesson applied to ourselves (`tools/approval_floors.py` — CONFIRMED).
* **Drills are scheduled, not remembered.** A monthly **halt drill** and a quarterly **restart/reconcile drill** run against the fake venue pack (§11 Phase 2a) as ordinary scheduled kernel jobs, each emitting `trading.drill.result`★ with pass/fail and evidence refs. A drill older than `promotion.drillMaxAgeDays` blocks `live` mode (§3.1 `promotion.eligible`). A safety mechanism nobody has fired since the exit test is a claim, not a control.
* Restart-safe: `halted` is rebuilt from the log; the reconcile job runs first after boot and before any executor run is admitted (`exec §3.3` boot reconciliation extended with a sector precondition, K3).

### 3.5 The two schemas that make "the model never computes money" structural

```
StrategyCard = {                      // human-approved config; the quant proposes, the operator signs
  strategyId, version, title, universe: [{ venue, instrument }], horizon, assetClass,
  entryRules: string, exitRules: string,          // prose for the human; not executable
  bracket?: { stopLossBps, takeProfitBps, trailing },   // override of trading.yaml bracket, still bounded by limits
  riskFractionPerTradeBps?: int ≤ trading.limits.riskFractionPerTradeBps,
  maxOpenPositions?: int, cooldownMinutes?: int,
  backtestEvidence: [{ backtestId, resultHash, window: { start, end }, postCutoff: boolean, guardsEnabled: true }],
  paperEvidence?: [{ from, to, tradesN, pnlMicroUsd, benchmarkMicroUsd }],
  approvedBy: approvalId, expiresAt
}

Signal = {                            // what the quant may write (tainted-write ⇒ human), what the executor may read
  signalId, strategyId, instrument: { venue, symbol, assetClass },
  side: 'long' | 'short' | 'flat', conviction: number ∈ [0,1], horizon: 'minutes' | 'hours' | 'days',
  thesis: string ≤ 500, thesisBreakers: string[] ≤ 5,
  evidenceRefs: [{ ref, sha256, origin: 'operator' | 'agent' | 'untrusted' | 'system' }],
  validUntil, proposedBy: { runId, agentId }, taint,
  approvedBy?: approvalId            // set by the kernel from approval.resolved; the executor's read precondition
}                                     // .strict(): no qty, no price, no leverage, no stop, no recipient, no venue key — refused at parse

OrderPlan = {                         // the executor's only write; validated against the mandate before venue.prepare
  signalId, clientOrderId,             // clientOrderId is the one the kernel minted in the brief; a different value is refused
  orderType: 'limit' | 'market', limitOffsetBps?: int within mandate.limitBandBps,
  timeInForce: 'day' | 'ioc' | 'gtc' (⊆ mandate.timeInForce), slices: int ≤ mandate.maxSlices,
  reason: string ≤ 300
}                                     // .strict(): qty, bracket, venue, symbol, mode come from Signal + risk.size + mandate; a plan naming them is refused

SignalExecView = {                    // the ONLY shape `signals.read` returns to the executor
  signalId, strategyId, venue, symbol, assetClass,
  side: 'long' | 'short' | 'flat', conviction, horizon, validUntil, approvedBy, leaseUntil
}                                     // no thesis, no thesisBreakers, no evidenceRefs, no venue free text: numbers, enums and ids only
```

**Why the executor never sees the prose.** v1 said the executor "never sees a memo, a headline or a tweet" while handing it a `Signal` carrying `thesis` and `thesisBreakers` — strings an LLM wrote *inside a tainted run* out of scraped pages. A human approval stamps `approvedBy`; it does not launder bytes. That put attacker-influenced text into the context of the one agent in the fleet with an `irreversible` risk ceiling, which is the ForcedLeak shape (INFERRED (snippet) landscape B9) and exactly what growth's provenance rule refuses for `publish.*` (`growth G4`: a write whose content descends from an untrusted artifact is denied unless the bytes were declassified). So `signals.read` serves the executor a `SignalExecView` — numbers, enums and ids, with `symbol` matched against the instrument allowlist. The thesis is rendered on the operator's card as quoted, flagged, untrusted-derived text in a block visually separate from the kernel-computed fields, and is readable by the bookkeeper for post-mortems. **The human's approval declassifies the decision, not the prose.**

"Model-supplied confirmation flags are never authoritative": `llmConfirmedFlagIsAuthoritative(_value) { return false; }` (`eliza/packages/core/src/utils/confirmation.ts:212-215` — CONFIRMED), and the confirmation gate's pending key is "derived from the request params ... the LLM cannot bypass this gate by setting request params" (`wallet-financial-confirmation.ts` header lines 1–18 — CONFIRMED). Our equivalent is structural rather than a runtime check: the schemas have no field a model could set to mean "approved", "sized" or "live", and the approval binds `argsHash` of the canonical prepared order (`plan` T14a/T23: the hub refuses a ticket on `argsHash` mismatch).

### 3.6 Mandate: a human-signed, bounded, expiring authority object

```
Mandate = {
  mandateId, agentId: 'executor', mode: 'paper' | 'live',
  venues: venueId[], instruments: [{ venue, symbol }],
  maxNotionalPerOrderMicroUsd, maxOpenNotionalMicroUsd, maxOrdersPerDay, maxDailyLossMicroUsd,
  side: 'long-only' | 'both', maxLeverage, limitBandBps, maxSlices, timeInForce: ('day'|'ioc'|'gtc')[],
  maxPriceDeviationBps, maxSlippageBps,               // narrow-only against trading.yaml limits; re-checked at redemption (§3.3b)
  tradingWindows, perOrderApproval: boolean,          // false is only meaningful under Q2 option B
  issuedBy: { connectionId, kind: 'human' }, issuedAt, expiresAt (≤ 30 d), maxUses?: int, revokedAt?
}
```

Issued only by `trading.mandate.issue` on the loopback control plane by a `HumanActor` (`plan §3.7` brand check); recorded as `trading.mandate.issued { argsHash }`; every field must be ≤ the corresponding `trading.yaml` limit (narrow-only, the Managed Agents rule "a roster agent can narrow what a tool reaches but never widen it" — CONFIRMED (survey)); `maxUses`, `expiresAt` and revocation follow ruflo's `PolicyApproval` shape (CONFIRMED (survey) `ruflo/v3/@claude-flow/security/src/policy/types.ts`). No tool exposed to any agent can create, edit or extend a mandate; the executor's `signals.read` and `venue.*` preconditions consult it read-only. The model can never change the bounds because the bounds are not reachable from any tool it has.

What a mandate does under the default reading of invariant 3 (Q2 option A): it bounds what may be *prepared* (`risk.check` denies outside it), pre-authorises unattended **paper** submits for a clean executor run, and labels every live card `withinMandate: true|false` (`exec §4.3`: "A mandate does not pre-approve the irreversible calls — each still parks for a per-call human decision"). What it would do under option B: satisfy the human-decision requirement for live submits that are inside it, with `maxUses` and expiry, per-order cards still filed as **notifications**. Option B is an amendment to the CLAUDE.md reading of "irreversible always requires a human" and is therefore ask-before (Q2, K7).

### 3.7 Venue packs, keys, and the proxy

* Each venue is an MCP server (`ccxt`-style or the venue's own REST behind a thin adapter) running in a **T2 `trusted` container with no credentials**; the Phase 2 egress proxy injects the venue key for exactly that venue's hostname and nothing else (sentinel-in-env, exact-host binding, revocable per-process grant — openclaw egress proxy design, CONFIRMED (survey) `openclaw/src/secrets/egress-proxy/*`; iron-proxy "refuses to start if proxy enabled but not running/misconfigured" — CONFIRMED `hermes-agent/tools/environments/docker_egress.py` lines 26–56 `enforce_on_docker` raises on any half-configured state; Managed Agents "the opaque placeholder is substituted with the real secret at egress. The agent never sees the secret value" — CONFIRMED (survey)). A Host/SNI mismatch on a credentialed rule is **deny + taint the run**, not "forward without the secret" (CubeSandbox forwards on inject-gate failure; we invert it — CONFIRMED (survey) `CubeEgress/lua/access_phase.lua`).
* Key posture, attested by the operator at registration and probed where the venue exposes it: trade-only, withdrawals disabled, IP allowlist = the proxy's egress IP. Hyperliquid API wallets "can sign trading actions for the approving master account, but they cannot withdraw" — CONFIRMED (survey); Binance minimum = "Enable Reading" + "Enable Spot & Margin Trading" with an IP whitelist, `enableWithdrawals` must be false — INFERRED (snippet); Coinbase "never enable 'Transfer' or 'Withdraw' permissions for trading bots" — INFERRED (snippet); IBKR Read-Only API default on, Trusted IPs, and **never** "Bypass Order Precautions for API Orders" — INFERRED (snippet). Keys live only under `vaultId`s in the pmmcp vault; the broker registers their values with the `SecretMask` at boot so no event can ever contain one (`plan` T24).
* **Rotation and revocation are actions, not intentions.** A key registered once and never rotated is a key nobody can revoke in a hurry, and v1 had no path for "this venue container may be compromised". `trading.key.rotate` and `trading.key.revoke` are control-plane commands by a `HumanActor`: rotate binds a new `vaultId` to the same venue and hostname, drains in-flight submits, restarts the pack and logs `venue.key.rotated { vaultId, previousVaultId }`★ (ids, never values); revoke drops the proxy grant immediately — openclaw's grants are per-process and revocable (CONFIRMED (survey) `src/secrets/egress-proxy/*`) — halts that venue and logs `venue.key.revoked`★. `keys.rotationDays` (default 90) raises `trading.key.stale`★; past `keys.maxAgeDays` the gate refuses `live` mode for that venue while paper keeps working, so a stale key degrades the sector rather than breaking it.
* Unknown tools on every venue server default to `kernel-only` until classified (invariant 7); the pack ships with schema-hash pinning and drift alerts (Phase 2), so a venue that adds a `withdraw` tool overnight cannot reach an agent.
* Paper venues need keys too (Alpaca paper keys) — they go through the same path; freqtrade-style keyless dry-run is what `venue.simulate` provides (freqtrade `dry_run`: "only Read-Only operations ... on the exchange are performed" — CONFIRMED (survey)); Hummingbot paper mode "Exchange APIs are not required" — INFERRED (snippet).

### 3.8 `bt.run` and `sim.run`: tools, not agents

* `bt.run { strategyRef, window: { start, end }, universe, seed, guards: true }` (risk `write`, sandbox exec in the **hostile** domain: strategy code is model-written and executed, no egress, `--read-only`, caps per invariant 9). Point-in-time data is mounted read-only from the kernel's market-data store; the container cannot fetch. Output is a typed `backtest.result { backtestId, resultHash, metrics: { trades, pnlMicroUsd, maxDrawdownBps, sharpe, feesMicroUsd, benchmarkPnlMicroUsd }, guardsEnabled, postCutoff, window }` event; the full report is an artifact by hash (`MAX_LOGGED_OUTPUT`). ### 3.9 Market data: the point-in-time store (why `bt.run` can trust its inputs)

`bt.run`'s guarantees are only as good as the bars it reads, so the store is specified rather than assumed. `marketdata` is a kernel-side MCP server over a local append-only store (Parquet/SQLite under the kernel's data root, not the repo), fed by allowlisted providers through the proxy. Three properties, each a test:

* **As-of, not latest.** Every row carries `asOf` (the timestamp the value was *observable*) separate from the event time. A `bt.run` for window `[start, end]` is served only rows with `asOf <= bar.close`; a query that would return a later-observed row fails the job rather than silently leaking. This is the concrete form of the look-ahead patches TradingAgents had to ship (CONFIRMED (survey) README changelog) and of the bias survey's finding that look-ahead is discussed in a minority of studies (INFERRED (snippet) landscape A10).
* **Revisions are appended, never overwritten.** Fundamentals and macro series get restated; a restatement is a new row with a new `asOf`, and the old row stays. A backtest therefore reproduces what was knowable, not what is now known. The store is immutable in the same spirit as the event log (invariant 5), though it is bulk data and lives outside the chain — what enters the chain is the `datasetHash` a backtest pins.
* **Every backtest pins its data.** `backtest.result` carries `datasetHash` alongside `resultHash`; re-running a strategy against a different snapshot produces a different hash and the `StrategyCard`'s evidence no longer matches, which the card's approval precondition checks. Without this, "the backtest that justified this card" is unfalsifiable.

* **Numbers and prose are different servers.** v1 classified all of `marketdata.*` as `taints: false` (Q3) while the same server was expected to serve fundamentals and news — third-party free text, which is the growth sector's entire taint source. The server is split: `marketdata.series.*` returns numeric and enum fields only, zod `.strict()`, with symbol strings matched against the instrument allowlist regex, and is `taints: false`; `marketdata.text.*` (headlines, filing bodies, transcripts, any free-text field) is `taints: true, quarantine: true` and is exposed only to `market-scout`. The quant may hold the numeric half and stay clean; it becomes tainted by reading scout memos, which is the honest boundary and keeps Q3 from quietly laundering a news feed.

Live quotes are a separate path: `venue.quote` from the venue pack is the price the kernel sizes against (`staleData.maxQuoteAgeMs` denies on a stale one), never a third-party feed, so sizing and execution cannot disagree about the price. Market-data provider credentials, where a provider needs one, follow the venue-key path exactly (vault + proxy injection, Q14).

* **model priority chain** `judge` lane: `standard: [anthropic/<sonnet-class>]`, `deep: [anthropic/claude-opus-5]` when the batch contains a live-mode strategy; ideally a different model family than the quant (eng O8 reasoning: shared bias) once a second provider probes.
* **taint posture** Inherits from the evidence; no write tools, so it only changes the verdict label (`tainted-evidence`).
* **budget caps** `{ microUsd: 500 000, wallclockMs: 300 000, maxLlmCalls: 6, maxToolCalls: 40 }`; rounds capped by `budgets.maxJudgeRounds: 3`.
* **approval preconditions** none.
* **KPIs / evals** agreement with realised outcomes (did the bear's named breaker fire on losing signals?); false-pass and over-rejection on seeded sound/unsound cards (`exec §8.3` reviewer-bias check); compliance annotations match the kernel's deterministic flags exactly (structural).
* **soul summary** `bear`: a reviewer paid to be wrong loudly; if the bull case survives, it says so in one line. `compliance-reviewer`: a compliance officer who lists what the kernel checked, what it could not, and what the operator must read from the primary source.
* **phase introduced** 1 (reviewing research memos and draft strategy cards, which is where a bear case is cheapest and most useful), with the `compliance-reviewer` soul from 2 once the kernel has deterministic flags for it to annotate.

## 5. Workflows

Events named are from the Phase 0 catalog plus §3.10 (★ = new). Approval classes are `exec §7.1`'s plus `strategy` (K3).

### 5.1 Objective → research → strategy card → paper signals → paper orders (Phase 2; the sector's exit test)

1. Operator: `run.start { agentId: 'ceo', input: 'Paper-trade a 20/50-day momentum strategy on the S&P 100 for 30 days' }`. CEO delegates `quant` (`laneClass: 'deep'`) with a brief; `delegation.admitted`; CEO run ends (`exec §2.1`).
2. `quant` (clean: brief is operator text) recalls `aos/shared`, returns a `ProposedPlan`: 6 `market-scout` tasks (souls `filings` × 3 sectors, `news` × 2, `sentiment` × 1; hostname bundles named), then a `quant` task "design + backtest", then a `critic:bear` task, then a `strategy` approval. Inventory of irreversible actions: **empty** (paper only). Budget within envelope, no `hostile`-domain template in the plan (the `bt.run` tool runs in `hostile`, but that is a tool the quant already holds; Q10 asks whether that should count) ⇒ `plan.accepted { by: 'policy' }` (`exec §4.3`).
3. CEO fans out the scouts (`agent.spawned` × 6, each tainted at ingress; `tool.gate` → `tool.call web.fetch` → `quarantine.held` per page; memos as artifacts; `run.finished`). Results are `resultRef`s with `taint: tainted`.
4. CEO delegates `quant` with `inputRefs: [memos]` ⇒ the quant run is **tainted**. It calls `marketdata.candles` (read), writes strategy code into its workspace, calls `bt.run` × 5 (each `tool.gate` → sandbox job in `hostile`, `backtest.started`★/`backtest.result`★ with `guardsEnabled: true`, `postCutoff` computed from the bound card's `trainingCutoff`); one window overlaps the cutoff ⇒ `contaminated`, excluded. It calls `strategy.propose` ⇒ `approval.requested { class: 'strategy' }` (always human) and stages 12 `signals.propose` calls ⇒ each parks as `tainted-write` (deferred to the digest, 24 h). `run.finished { reason: 'parked' | 'suspended' }` per `exec Q3`.
5. CEO spawns `critic:bear` over the card and the memos (fresh context) ⇒ `GoalVerdict { score: 0.6, missing: ['no regime test for 2022'] }` attached to the strategy card.
6. Operator, on the morning digest: approves the `StrategyCard` (`approval.resolved`, `strategy.approved`★ with `expiresAt` 90 d) and ticks 9 of 12 signals (`approval.resolved` × 9 ⇒ `signal.approved`★ with `approvedBy`; 3 expire ⇒ `signal.expired`★, a logged deny). Operator issues a **paper mandate** via `trading.mandate.issue` (K7; on v1 filed as a synthetic-ref approval, Q7) ⇒ `trading.mandate.issued`★.
7. Scheduler fires `run.start { agentId: 'executor', taint: 'clean' }` at the venue's window open (`schedule:` on the executor with `mode: invoke`). `signals.read` (precondition `approvedBy != null`) ⇒ 9 signals, each leased to this run (`signal.claimed`★, 10 min; a second executor run for the same venue is queued behind the lane, §3.3a). For each: `venue.quote` (read) → `venue.simulate` (read) → `venue.prepare` (`tool.gate allow`: `risk.check` ok, `risk.size` ⇒ qty, stop 2 %, TP 4 %; `order.prepared`★ with `clientOrderId aos-…`) → `venue.paper.submit` (`write`, clean run within mandate ⇒ allow; `order.submitted`★) → venue ack via the pack ⇒ `order.acked`★ → fills ⇒ `order.filled`★ → ledger projection updates; breakers evaluate on every fill and mark. `run.finished { costMicroUsd }`.
8. Reconcile job (every 5 min) ⇒ `trading.reconciled`★; bookkeeper's daily run ⇒ journal in `aos/agent/bookkeeper`, post-mortems as positions close. `chain.verify` passes. Exit test for the sector: one objective → approved card → ≥ 5 paper orders with `order.prepared` ids → reconciled with zero drift → a journal whose every number matches the ledger, and a kernel restart mid-window that orphans nothing (reconcile-by-client-id after boot). Two adversarial drills are part of the same exit test: a **forced-concurrency drill** (two executor runs started against one approved signal must yield exactly one order) and a **halt-with-partial-fill drill** (a halt while a bracketed position is half filled must leave the protective stop resting and escalate rather than cancel it).

### 5.2 Paper → live: per-order approval (Phase 2-late/3) and the mandate question

1. Operator attests a live key in the vault (`alpaca-live`, trade-only, withdrawals disabled, IP allowlisted) and switches `trading.mode` to `live-per-order` via the control plane (K7) ⇒ `trading.mode.changed`★; the venue container is restarted with the proxy rule `paper-api.alpaca.markets → alpaca-paper`, `api.alpaca.markets → alpaca-live` (each key bound to exactly one hostname; `proxy.decision` per request).
2. Operator issues a **live mandate** (`mode: live`, `maxNotionalPerOrderMicroUsd: 500 000 000` ($500), `maxOrdersPerDay: 5`, `expiresAt: +14 d`, `perOrderApproval: true`).
3. Executor run (clean): `signals.read` → `venue.prepare` (kernel size; `order.prepared` with `clientOrderId`) → `venue.live.submit` ⇒ `tool.gate needs-human` ⇒ `approval.requested { class: 'irreversible', toolRef: venue.live.submit, argsHash, argsPreview: { venue, symbol, side, qty, notional, stop, takeProfit, clientOrderId, withinMandate: true, washSaleRisk: false, thesis } }` ⇒ `run.parked` (or suspended per `exec Q3`).
4. Operator approves on the card (control plane, `HumanActor`) ⇒ `approval.resolved { argsHash }` ⇒ the hub re-checks `argsHash` **and the gate re-runs the whole execution-time check set** (halt, mandate, lease, breakers, `risk.check`, fresh quote within `maxPriceDeviationBps`, card TTL — §3.3b; a failure emits `approval.voided`★ and no order is sent) ⇒ executes under the `approvalId` receipt with the same `venueClientId` ⇒ `order.submitted`★ → `order.acked`★. If the venue response is ambiguous (timeout), `submitWithRecovery` calls `venue.order.get(clientOrderId)` before any resend; a duplicate is impossible by construction (§3.3).
5. **Mandate variant (Q2 option B, only if the operator adopts it as a CLAUDE.md amendment):** step 3's card is filed as a *notification*, `mandate.covers` is true, `maxUses` decrements (`trading.mandate.used`★), the submit executes, and every card outside the mandate still parks. Under option A (default) nothing changes from step 3–4; the mandate only labels the card and bounds what can be prepared.

### 5.3 Breaker trip → halt → post-mortem → human resume/flatten

1. A mark update takes the day's realised + unrealised loss past `breakers.dailyLoss.maxDailyLossMicroUsd` ⇒ `trading.breaker.tripped { breaker: 'dailyLoss', until: nextSessionOpen }`★ ⇒ `trading.halted { by: 'breaker' }`★.
2. Kernel cancels open non-protective orders (`venue.cancel` under a kernel ticket ⇒ `order.cancelled`★ each); protective stops remain; no flatten. Every `venue.*submit*` now denies with reason `halted` (`tool.gate deny`); any executor run in flight gets typed tool errors and ends `run.finished { reason: 'halted' }`.
3. Scheduler fires `bookkeeper` on `trading.halted`: bundle = fills of the day, breaker state, open positions and their stops, signals that led here ⇒ a halt post-mortem with evidence refs and a proposal `strategy.retire?` or `param.review { riskFractionPerTradeBps }`; `request_human { class: 'escalation' }` ⇒ notification (not deferred).
4. Operator reads the post-mortem; chooses `trading.resume` (refused until `until` passes) or `trading.flatten { instrument }` ⇒ one `irreversible` card per position ⇒ `venue.close_position` ⇒ `trading.flattened`★. Nothing flattened automatically; nothing resumed automatically.

### 5.4 Reconcile drift → halt → human

1. Reconcile tick finds a position at the venue the ledger does not know (a fill whose ack was lost during a kernel restart, or an order placed outside the kernel) ⇒ `trading.drift { kind: 'unknown-position', evidence }`★ ⇒ `trading.halted { by: 'drift' }`★.
2. Reconcile resolves what it can by `clientOrderId`: a known prepared order with a venue fill becomes `order.filled { recoveredBy: 'reconcile' }`★ and the drift clears; an order with no kernel record stays a drift.
3. Bookkeeper narrates; operator decides `trading.resume` after adopting or flattening the foreign position. The rule: absence of a kernel record never authorises the kernel to invent one (orca "Absence never authorizes stop, abandon, retry, or release" — CONFIRMED (survey)); a foreign position is a human's to explain.

* **Phase 1** (first real loop): `market-scout` souls and bundles; `quant` in research-only mode (memos, `ProposedPlan`, no `bt.run`, no `signals.propose`); `critic:bear` live over memos and draft cards (it is cheapest and most useful exactly here); `trading.yaml` schema and `risk.ts` written and property-tested against fixtures (no venue). Nothing in this sector places an order, paper or live, and no venue key exists. The sector's Phase 1 deliverable is a cited research memo pipeline whose taint and quarantine behaviour the harness scores.
* **Phase 2a** (no venue, no key, no account — the sector's real start, and the half that can be built on the operator's laptop in an afternoon's worth of test runs): the **fake venue pack** (in-process MCP server with scripted acks, rejections, timeouts, ambiguous responses, partial fills and leg-attach failures), `risk.ts`, the ledger, the reconcile job, the marks job, the single-writer leases, the halt and its protective-leg rule, the `executor` in `deterministic` mode, the `bookkeeper`, `bt.run` in the hostile domain, `signals.propose`/`signals.read`, paper mandates. Kernel items T-K1–T-K6, T-K9, T-K10, T-K12, T-K13, T-K14, T-K15–T-K17, T-K19, T-K20. **Exit test: every drill passes against the fake venue** — forced concurrency yields one order, halt with a partial fill keeps the stop, a kill between `order.submitted` and `order.acked` recovers by `venueClientId` with nothing resent and zero drift, a leg-attach failure escalates (or unwinds where pre-authorised), and a ticket approved before a breaker trip is voided rather than executed. v1 put twelve kernel changes and a real broker account into one phase; splitting it means the machinery that protects money is proven before any money is reachable.
* **Phase 2b** (the wire; per the phase order "trading cannot precede the egress proxy and taint"): venue packs in keyless T2 containers behind the proxy, key attestation and probe, key lifecycle (T-K18), `marketdata` split (T-K2), real paper venue (Alpaca paper first), T-K8. Exit test: §5.1's last paragraph run against the real paper venue, with the Phase 2a drills re-run green against it.
* **Phase 2-late / 3**: live per-order approvals (Q2 A) on one attested live key with a small mandate; the Approvals view renders the trading card fields; T-K7 lands with the v2 bump.
* **Phase 3+**: `llm` executor mode only after the T-K10 comparison; Q2 option B only after T-K11 and the Phase 3 trust-rule machinery, if ever.
* **Phase 5**: `sim.run` (optional, Q11); per-agent eval suites gating every strategy-card and manifest change; signed skills repo receives the bookkeeper's post-mortem procedures as human-promoted drafts.

## 12. Review findings applied

An adversarial pass over v1 through three lenses — invariants and security, frontier-not-theater, feasibility for one operator on one machine. The roster did not change: `quant`, `executor`, `bookkeeper` persistent; `market-scout` and `critic` as ephemeral templates; everything else kernel code or a tool view. Four blockers and twelve major findings changed the design.

### Blockers

| # | finding | what changed |
|---|---|---|
| B1 | **Untrusted prose reached the one agent with an `irreversible` ceiling.** v1 claimed the executor "never sees a memo, a headline or a tweet" while handing it a `Signal` carrying `thesis` and `thesisBreakers` — strings an LLM wrote inside a *tainted* run out of scraped pages. A human approval stamps `approvedBy`; it does not launder bytes. This is the ForcedLeak shape (INFERRED (snippet) landscape B9) and is exactly what `growth G4` refuses for `publish.*`. | New `SignalExecView` in §3.5 — numbers, enums and ids only — as the only shape `signals.read` returns to the executor; the thesis is card-only (rendered as quoted, flagged, untrusted-derived text, visually separate from the kernel block) and bookkeeper-readable. §4.2 rewritten to say this is structural, not a promise. New gate: zero free-text fields in a `SignalExecView`. |
| B2 | **Approvals were never re-evaluated at execution time.** `argsHash` binds the bytes, not the world. A card approved at 10:00 and tapped at 10:20 could execute into a halted kernel, a tripped breaker, an expired mandate, a stolen lease or a market 3 % away. The executive (§7.2.5) and growth (G4) both already re-check at execution time; trading did not. | New **§3.3b**: halt, mandate, lease, breaker state, `risk.check`, `StrategyCard` validity and a fresh quote within `maxPriceDeviationBps` are re-run at ticket redemption; failure emits `approval.voided`★ and mints a fresh card, never an execution. Ticket TTL (`approvals.trading.ttlMs`, default 120 s, eliza's 5 min as the ceiling). Exactly-once via `exec §7.2.7` receipts, with mastra's "never re-arm a suspension" rule for a `pending` receipt at boot. Commitment 4 added to §1; workflow §5.2 step 4 rewritten; T-K16. |
| B3 | **The protective leg was assumed, never guaranteed.** §3.4 refused a cancel that would strip "the resting protective stop" while nothing in the write ladder said who placed one. Entry now, stop next call, is a window in which a crash, a leg rejection or a halt leaves a naked position — on a leveraged perp, the one failure that can exceed the account. | New **§3.3.1**: `bracketSupport: native | attached | none` and `onProtectiveFailure: escalate | reduce-only-close` per venue; `protectiveAttachTimeoutMs`; `order.legs.attached/failed`★; `naked-position` as a drift kind and a breaker. `reduce-only-close` is a human pre-authorisation in `trading.yaml` and is **required** before any instrument with `maxLeverage > 1` or any non-`native` venue may be enabled. T-K17, Q16. |
| B4 | **The mark-to-market breaker had no feed.** `breakers.markToMarket` and `maxDrawdownBps` were said to evaluate "on every mark update" while the only clock in the sector was the 5-minute reconcile. Hummingbot's kill switch is precisely the kind that must fire "even without new trades occurring" (CONFIRMED (survey)). | New **§3.2a** `src/trading/marks.ts`: 15 s polling while a position is open, `breakers.evaluate` on every poll, `market.mark`★ sampled into the log at 60 s plus every breaker transition, a stale mark with an open position trips a halt rather than only denying new orders, claim-before-dispatch and auto-disable-into-halt. `marks` block in `trading.yaml`; T-K15, Q17. |

### Minor findings and missed ideas folded in

* **Anchoring is not only the executor's problem.** DXRG's leaderboard result (CONFIRMED (survey)) now also forbids rendering a running P&L ranking of the quant's own strategies into its context; performance reaches it as the bookkeeper's typed proposals (§4.1).
* **Bounded retry-with-feedback on `bt.run`** (crewAI `guardrail_max_retries = 3`, CONFIRMED (survey)) so a broken strategy script burns three attempts, not the run budget (§4.1).
* **`critic:bear` moved to Phase 1**, where a bear case over research memos and draft cards is cheapest and most useful; the `compliance-reviewer` soul stays at Phase 2 because it annotates kernel flags that do not exist yet (§4.5, §11).
* **Mastra's atomic-resume asymmetry** ("a stuck running run is strictly safer than silently re-arming a suspension", CONFIRMED (survey)) now governs boot recovery of a `pending` submit receipt (§3.3b).
* Borrowed-from matrix gained eight rows (mastra CAS/resume, orca receipts via `exec §7.2.7`, growth G11 leases, exec/growth execution-time re-evaluation, mastra+G12 gates-vs-scorers, the client-order-id collision PR, IBKR price precautions, crewAI bounded retries); §8 gained five refusals.

## 13. Rejected review findings

| finding considered | why it was not applied |
|---|---|
| "Merge `bookkeeper` into the `critic` template — it is just another read-only narrator." | It fails none of rule 1's tests: a distinct scheduled cadence (daily plus event-driven), a write namespace of its own, a local-first model binding that keeps the daily journal near $0, a read surface (ledger + venue reads + all signals including unapproved) that no critic has, and a context boundary — the post-mortem is the sector's only feedback loop that is not an approval. A critic is a fresh-context adversary with no memory; a bookkeeper is the opposite by design. |
| "Add a `risk-analyst` or `portfolio-manager` agent so a model can reason about exposure." | Already refused in §8 and refused again: it is invariant 3's model-as-gate in a new hat. Exposure is `ledger` + `risk.ts`; if the operator wants it narrated, that is the bookkeeper. |
| "Make `executor` an ephemeral template spawned per signal batch." | It holds the venue lane lease, the mandate read and the only `irreversible` ceiling in the sector, and its `llm`-vs-`deterministic` comparison needs a stable eval history against one manifest. An ephemeral executor would also multiply the single-writer problem that §3.3a exists to close. |
| "Adopt Q2 option B (mandate-authorised live submits) to get the approval count down." | Approval fatigue is solved by producing fewer orders (§2.3), not by deleting the human decision. Option B is a CLAUDE.md amendment (T-K11) and `exec §7.2.5` already excludes `irreversible` from trust rules. It stays the operator's decision, defaulted off, and §2.3 shows the honest cost of option A. |
| "Let a `compliance-reviewer` critic pass or fail the batch so the operator only sees clean cards." | A model verdict as a filter on what reaches the human is a model making an access-control decision by omission. The critic annotates; the human sees everything. |
| "Drop `sim.run` entirely." | It is already Phase 5, optional, contingent on Q11, forbidden as a `Signal` input and metered through the router. Deleting the section would lose the reasoning about why the MiroFish epistemic claim is refused, which is the useful part. |
| "Auto-flatten on a tripped breaker so the operator is not woken." | Ambiguous kill semantics are the anti-pattern (INFERRED (snippet) landscape A12): a halt blocks new orders and keeps protective legs; flatten is a separate human decision. §3.3.1's `reduce-only-close` is narrower — it unwinds only a position the kernel *failed to protect*, and only where the operator pre-authorised it in config. |
| "Put the venue packs in the `hostile` domain since they talk to the internet." | They need exactly one egress hostname with a credential injected at the proxy; that is what `trusted` plus a per-venue allowlist is for. `hostile` (no egress) would make them useless, and widening `hostile` to have egress would damage every other sector that relies on it. |
| "Let the quant read the live ledger so it can adapt strategies to current exposure." | That re-creates the leaderboard anchoring DXRG measured, and it puts a tainted run one step from position data. The bookkeeper's typed proposals are the channel. |
| "Raise `maxOrdersPerDay` on live venues; three is uselessly small." | Three is the number that keeps live trading inside the fleet's approval budget under option A (§2.3). It is an operator edit, and raising it is honest as long as the operator raises the budget with it — which is exactly the trade-off §2.3 is there to make visible. |
