## What it is

A single long-lived **Gateway** daemon (default `127.0.0.1:18789`, WebSocket + HTTP) that owns every messaging surface (WhatsApp, Telegram, Slack, Discord, Signal, iMessage, Teams, 20+ more via channel plugins), runs one or more **agents** (each with its own workspace, `agentDir` SQLite session store, auth profiles), and exposes control-plane clients (CLI, TUI, Control UI, macOS/iOS/Android apps, "nodes" for device capabilities). It is a personal/team AI assistant framework with tools, skills (`SKILL.md`), plugins, MCP client+server, cron/automations, sub-agents, and pluggable memory. Its stated stance is "trusted gateway, untrusted execution, deterministic policy" and "one trust boundary per gateway" (`docs/gateway/security/trust-model.md`, CONFIRMED).

## Orchestration model

- **Agent loop** (`docs/concepts/agent-loop.md`, CONFIRMED): `agent` RPC returns `{runId}` immediately; `agentCommand` -> `runEmbeddedAgent` serializes via per-session + global queue lanes, resolves model + auth profile, builds system prompt (base + skills + bootstrap files), streams `assistant`/`tool`/`lifecycle` events; `agent.wait` blocks on lifecycle end. Transcript writes are fenced by a durable `activeWriterRunId` claim checked inside the SQLite commit transaction (superseded runs cannot commit).
- **Command queue / lanes** (`src/process/lanes.ts`, `src/process/command-queue.ts`, `src/gateway/server-lanes.ts`, `src/agents/lanes.ts`, `docs/concepts/queue.md`, CONFIRMED): closed enum of lanes `main`, `system-agent`, `system-agent-inference`, `cron`, `cron-nested`, `hook-dispatch`, `background`, `subagent`, `active-memory`, `nested`, plus dynamic `session:<key>` and `nested:<sessionKey>` lanes. Each run waits on its session lane, then a global lane capped by `agents.defaults.maxConcurrent`; `subagent` lane default 8; capacity **groups** bound `cron-nested`+`hook-dispatch` to one shared budget (comment cites a real additive-capacity bug, `openclaw#98813`). Lane tasks carry budgets, owner deadlines, progress-idle timeouts, abort grace (`CommandLaneTaskTimeoutError`). Inbound chat while a run is active uses queue modes `steer | followup | collect | interrupt` with debounce/cap/drop=summarize.
- **Sub-agents** (`docs/tools/subagents/*.md`, CONFIRMED): `sessions_spawn` creates `agent:<id>:subagent:<uuid>`; results flow up an **announce chain** one level at a time; `maxSpawnDepth` 1-5 (default 5), `maxChildrenPerAgent` default 5, `runTimeoutSeconds`, `sandbox: "require"` fails fast if child would be unsandboxed; cascade stop; `sessions_yield` handoff with a registry that owns completion across yields (`docs/concepts/subagent-yield-handoff.md`). **Swarm** (`docs/tools/swarm.md`) orchestrates from Code Mode scripts ("the program is the orchestration", no graph DSL) with `maxConcurrent 8`, `maxChildrenPerGroup 50`, `maxTotalPerGroup 200` runaway backstop, `outputSchema` structured results.
- **Team preset / roles** (`src/agents/agent-roles.ts`, `src/agents/agent-team.ts`, `docs/reference/templates/roles/`, CONFIRMED): four bundled roles `coordinator` ("Chief of Staff"), `researcher`, `writer`, `reviewer` as portable **Claw** packages (`CLAW.md` frontmatter + SOUL body + `workspace/AGENTS.md`). `agents team create` wires coordinator -> specialists; specialists return artifacts and do not delegate further. `docs/concepts/parallel-specialist-lanes.md` gives the "lane contract" template: Owns / Does not own / Chat budget / Handoff / Tool-risk rule, and says: do not start with a coordinator ("a coordinator without lane contracts just coordinates chaos").
- **Automations/cron** (`docs/automation/cron-jobs/how-it-works.md`, CONFIRMED): scheduler runs inside Gateway, persisted in SQLite, every run is a background task record; isolated runs have their own lifetime, 60-min watchdog, recognize structured execution-denial metadata so a blocked command is not reported green, auto-disable after repeated errors, re-prompt once on stale "on it" acknowledgements. **Standing orders** (`docs/automation/standing-orders.md`) = programs in `AGENTS.md` with Scope/Triggers/Approval gates/Escalation. **Standing intents** (`docs/concepts/standing-intents.md`) = event-conditioned prospective memory in SQLite (cooldown 24h, max 3 fires, 90-day expiry, owner-only creation). **Goal** (`docs/tools/goal.md`) = one durable per-session objective with `get_goal/create_goal/update_goal`.
- **Model routing/failover** (`docs/concepts/model-failover.md`, CONFIRMED): auth-profile rotation within provider, then `agents.defaults.model.fallbacks` chain; fallback is turn-local (does not repin session); explicit user selections are strict; terminal stops (`agent_run_terminal_timeout`, `idle_timeout_circuit_breaker`) are logged as `model_fallback_chain_stopped`.
- **Delegate architecture** (`docs/concepts/delegate-architecture.md`, CONFIRMED): capability tiers for an org-facing agent: Tier 1 read-only + draft, Tier 2 send-on-behalf under its own identity, Tier 3 proactive on schedule; "hard blocks" defined before granting any credential.

## Memory model

(`docs/concepts/memory-architecture.md`, `docs/concepts/dreaming.md`, `docs/concepts/memory-provenance.md`, `docs/concepts/agent-workspace.md`; implementation in `extensions/memory-core`, alternatives `memory-lancedb`, `memory-wiki`, `memory-honcho`; CONFIRMED)

- Plain files in the agent workspace + one SQLite index. Tiers: Instructions (`AGENTS.md`, human-only), Curated core (`MEMORY.md`, `USER.md`; written only by dreaming consolidation or direct user request), Episodic (`memory/YYYY-MM-DD.md`, transcripts; never injected, search-only), Prospective (standing intents, cron), Review (`DREAMS.md`).
- **Provenance columns the model cannot write through prose**: origin class `owner | agent | untrusted | system`; session kind (interactive/cron/heartbeat/subagent); observed timestamp + supersession key. Conservative classification: unknown -> `untrusted` or `system`, never `owner`.
- **Session-kind gating**: cron, heartbeat, and sub-agent sessions never produce durable memory candidates. **Recall-loop prevention**: injected memory is marked and never re-extracted. **Turn taint**: a tool result declared network-sourced taints the rest of the turn; memory classification treats it as `untrusted` even in an owner turn; clears on next user message.
- Single primary writer: "dreaming" pass (light -> REM -> deep) with deterministic gates around bounded model consolidation; preimages stored before any `MEMORY.md` rewrite; `openclaw memory forget --session` deletes by lineage.
- Design principles stated verbatim: no hidden state; writing is the hard part; the write path is the security boundary; deterministic gates, model judgment inside them; failures never block replies.

## Tool / plugin / MCP model

- **Tool policy layers** (`docs/gateway/sandbox-vs-tool-policy-vs-elevated.md`, CONFIRMED): profile -> provider profile -> global/per-agent allow/deny -> provider allow/deny -> sandbox allow/deny; `deny` always wins; `group:*` shorthands (`group:runtime`, `group:fs`, `group:sessions`, `group:web`, `group:plugins`, ...). Policy filters by *name* only: "If `exec` is allowed, denying `write` does not make shell commands read-only."
- **Sandbox tool policy defaults** (`src/agents/sandbox/constants.ts`, `src/agents/sandbox/tool-policy.ts`, CONFIRMED): `DEFAULT_TOOL_ALLOW` includes `exec, process, read, ls, write, edit, apply_patch, sessions_*`; `DEFAULT_TOOL_DENY` = `browser, canvas, computer, mobile_ui, nodes, automations, gateway, <channel ids>`; comment: "`allow: []` => allow all".
- **Sub-agent hard-deny** (`docs/tools/subagents/tool-policy.md`): sub-agents always lose `gateway, agents_list, session_status, progress_card, cron, message, sessions_send, conversations_*`; leaf depth also loses `subagents, sessions_list, sessions_history, sessions_spawn`; derived from the persisted session envelope every turn; `allow` cannot add it back.
- **Plugins** (`docs/plugins/architecture.md`, `docs/gateway/security/tool-permissions.md#plugins`): capability registration (`registerProvider`, `registerChannel`, `registerWebFetchProvider`, ...) plus typed hooks (`before_tool_call` with terminal `{block:true}`, `before_prompt_build` can narrow `toolsAllow`, `tool_result_persist`, `message_sending` cancel). Plugins **run in-process with the Gateway** and are "trusted code"; install executes code; `security.installPolicy` is an operator-supplied allow/warn/block command; no built-in dangerous-code blocking.
- **Skills** (`docs/tools/skills.md`): `SKILL.md` markdown with 7-level precedence (workspace > project > personal > managed > workshop > bundled > extra); **Skill Workshop** (`docs/tools/skill-workshop.md`) is a governed proposal -> review -> apply path with hashes and rollback metadata, but "automatic background learning" edits the workshop dir with normal file tools without proposals.
- **MCP** (`docs/tools/mcp.md`, `src/agents/agent-bundle-mcp-*.ts`): `mcp.servers` (stdio/SSE/streamable-http), `toolFilter.include/exclude`, `openclaw mcp doctor --probe`; MCP tools pass through the same profile/policy; server-prefixed names use `__` (`outlook__send_mail`) which matches our invariant 10 convention. "Allow Always" saves durable per-agent grants. Reverse direction `openclaw mcp serve` exposes conversations as an MCP server.
- **Exec approvals** (`docs/tools/exec-approvals.md`, `docs/tools/exec.md`, `src/infra/exec-approvals-core.ts`): modes `deny | allowlist | ask | auto | full`; approvals stored in SQLite; approved commands bind resolved real-path executable identity (+ content hash for writable) and one file operand, and are denied on drift; heredocs always need approval in allowlist mode; `strictInlineEval` for `python -c`-style forms; `safeBins` stdin-only profiles (`jq` explicitly denied as safe bin).

## Sandbox & security posture

**Isolation** (`src/agents/sandbox/docker.ts` ~L340-420, `src/agents/sandbox/config.ts` L110-117, `docs/gateway/sandboxing*.md`, CONFIRMED):
- Sandboxing is **off by default**; `mode: off | non-main | all`; `scope: session | agent | shared`; `workspaceAccess: none | ro | rw`. Backends: Docker, Podman, SSH, OpenShell, Crabbox (cloud lease).
- When on, Docker create args include `--init`, `--read-only` (default `readOnlyRoot: true`), `--network` default `"none"`, `--cap-drop ALL` (default), `--security-opt no-new-privileges` (always), optional seccomp/apparmor, `--pids-limit`/`--memory`/`--cpus` only if configured, `--user` only if configured (INFERRED: default is the image user). `network: "host"` blocked; `container:<id>` blocked unless `dangerouslyAllowContainerNamespaceJoin`. Bind sources validated twice (normalized + after resolving through deepest existing ancestor); denylist covers `/etc, /proc, /sys, /dev, /root, /boot, /run, /var/run, docker.sock` and HOME credential dirs; `dangerouslyAllowExternalBindSources` override exists.
- The Gateway process itself always stays on the host; only tool execution moves into the sandbox. Elevated mode (`/elevated on|full`) lets a chat sender on `tools.elevated.allowFrom` run exec **outside** the sandbox; `/elevated full` skips approvals when policy is already `full/off`.
- **Default exec policy is host execution with `security="full"`, `ask="off"`** ("Trusted single-operator default ... That is intentional UX, not a vulnerability by itself", `docs/gateway/security/trust-model.md`; code default `src/infra/exec-approvals-core.ts:131`). Fail-closed fallback exists (`createFailClosedExecApprovalsFallback` -> `security: "deny"`) but only when the approvals document is invalid.

**Credential handling** (`docs/gateway/secrets.md`, `docs/gateway/secrets/runtime-model.md`, `docs/gateway/secrets/secret-store-and-egress.md`, `src/secrets/egress-proxy/*`, CONFIRMED):
- Plaintext credentials in `openclaw.json`, `.env`, auth-profile SQLite, generated `models.json` are the norm; SecretRefs (`env | file | exec | store`) are opt-in per credential. Docs: "Plaintext credentials remain agent-readable when they sit in files the agent can inspect."
- Shared secret store: `kind: "secret"` is write-only via API but **unencrypted at rest** in `state/openclaw.sqlite` (0600); `kind: "env"` is injected as plaintext into Gateway-hosted exec.
- Sentinels `oc-sent-v2.<ciphertext>.end` replace provider keys through the model-call chain and are swapped at the guarded fetch; "not process isolation" — plaintext is in Gateway memory.
- **Secret egress proxy** (default-off): loopback HTTPS proxy with per-Gateway-start CA; each secret bound to exact hostnames (`--allow-host api.openai.com`); per-process Basic-auth grant revoked on exit/cancel/timeout; `allowedHosts` traffic allowlist (empty array = lockdown), `bypassHosts` for pinned clients (blind CONNECT); streaming body substitution with bounded carry window; every refusal names the fix command. Docs list limits: hostname-based not IP-pinned, bound host can reflect the credential, non-HTTPS refused.

**Gates / human-in-the-loop**:
- Session **permission modes** `read-only | guarded | workspace | full` (`docs/gateway/permission-modes.md`): `guarded` = human after allowlist fast path; `workspace` = **LLM reviewer** decides allow/deny/ask (three consecutive denials escalate to human); `full` = no reviewer, requires `operator.admin`. Default without config or sandbox is **full access**.
- Operator scopes (`operator.read/write/admin/pairing/approvals/questions/talk`) and named roles with `sandbox: "required"` and per-role agent allowlists (`docs/gateway/operator-scopes.md`).
- DM `dmPolicy: pairing` default (codes expire 1h, 3 pending per channel); group allowlists + mention gating; `session.dmScope` isolation; `contextVisibility`; `commands.ownerAllowFrom` bootstrapped on first pairing approval.
- Agent-requested agent creation, plugin installs, config writes go through the system agent's typed operations and operator approval; "conversational claims of approval never authorize the change" for restricted runs; but **Full Access runs auto-apply without a prompt** (`docs/cli/openclaw.md` L117-136).
- Audit: bounded metadata-only ledger + optional execution-identity envelopes (`executionId`/`contextId`, HMAC-pseudonymized, 30-day expiry); "audit records are not authorization evidence"; persistence best-effort, can lose evidence under saturation (`docs/gateway/audit.md`).

**Cross-agent reach defaults** (`docs/gateway/security/trust-model.md`, CONFIRMED): `tools.sessions.visibility` defaults to `all`; `tools.agentToAgent.enabled` defaults `true` with empty allow = every pair; `tools.message.crossContext.allowAcrossProviders` defaults `true`. Any unsandboxed tool-enabled agent can list/read/search/message every other agent's sessions. SECURITY.md: "Session ownership, visibility, and presence are usability features, not security boundaries."

**Evals/QA**: `qa/scenarios/*.yaml` + `taxonomy.yaml` + private `qa` CLI with `mock-openai` provider lane (`docs/concepts/personal-agent-benchmark-pack.md`, `qa/README.md`, CONFIRMED). Scenarios include `personal-redaction-no-secret-leak`, `personal-approval-denial-stop`, `personal-no-fake-progress`, `personal-failure-recovery`. `qa/frontier-harness-plan.md` and `qa/maturity-scores.yaml` exist (not read).

## BEST PARTS

1. **Named lanes + capacity groups + session/global double queue.** Evidence: `src/process/lanes.ts`, `src/process/command-queue.ts`, `src/gateway/server-lanes.ts` (cron/hook shared budget, comment on additive-capacity bug), `docs/concepts/queue.md`, `docs/concepts/parallel-specialist-lanes.md`. Sector: kernel (every sector's throughput). Why: it is the exact shape CLAUDE.md names as reference; the closed lane enum, per-lane concurrency published as one transaction, task budget/idle/abort-grace timeouts, and the "steer/followup/collect/interrupt" ingress modes are ready to map onto `src/runtime` lanes for a coding fleet (`subagent` lane) vs. CEO (`main`) vs. schedule (`cron`, `cron-nested`) without starving control-plane requests.
2. **Secret egress proxy: sentinel-in-env, exact-host binding, per-process revocable grant, traffic allowlist.** Evidence: `src/secrets/egress-proxy/{proxy-server,registry,stream-substitution,certificates}.ts`, `docs/gateway/secrets/secret-store-and-egress.md`. Sector: ops-security, engineering (T2 coder), trading (exchange keys). Why: this is a working reference for our Phase 2 sidecar: workers see only `oc-sent-v2...` sentinels, the proxy substitutes only for `api.openai.com`-style bound hosts, refuses unbound hosts with an actionable message, revokes on process exit, and can run in lockdown (`allowedHosts: []`). Take the design; put it in a sidecar, not in the gateway process, and log every decision to the chain (they only audit forwards).
3. **Memory provenance + session-kind gating + turn taint + single gated writer.** Evidence: `docs/concepts/memory-architecture.md` (tier table, provenance section, "Trust boundaries and limits", write-path diagram), `docs/concepts/dreaming.md` (preimages, deep-phase-only promotion), `extensions/memory-core`. Sector: kernel (pmmcp write policy), growth/comms (untrusted inbound), trading (never let scraped content become "facts"). Why: it turns our taint flag into a memory rule: cron/heartbeat/subagent/tainted runs may write task artifacts but never promotion candidates; recalled content is never re-extracted; curated memory has exactly one writer. Map directly onto pmmcp namespaces (`aos/shared` promoted only by a kernel-owned consolidation job with preimages logged).
4. **Role Claws with written lane contracts and non-delegating specialists.** Evidence: `docs/reference/templates/roles/*/CLAW.md` + `workspace/AGENTS.md`, `docs/reference/templates/roles/presets/team.json`, `src/agents/agent-roles.ts` (zod-validated `AGENT_ROLES`), `docs/concepts/parallel-specialist-lanes.md` ("Minimal lane contract template"). Sector: executive (CEO), engineering, growth. Why: a portable manifest format (identity + SOUL body + declared workspace files + skills/MCP/cron) that a human approves before the agent exists is what `agents/<id>/agent.yaml` + `souls/*.md` should look like; the Owns / Does-not-own / Chat-budget / Handoff / Tool-risk contract is the right template for every roster entry, and "specialists return artifacts, never delegate" keeps depth small.
5. **Depth-typed sub-agent hard-deny, fan-out backstops, announce chain, cascade stop, yield handoff.** Evidence: `docs/tools/subagents/nesting.md` (depth table, `maxSpawnDepth`, `maxChildrenPerAgent`), `docs/tools/subagents/tool-policy.md` (always-lost tools, envelope-derived every turn), `docs/tools/swarm.md` (`maxTotalPerGroup 200`, `outputSchema`, `collect: true` children), `docs/concepts/subagent-yield-handoff.md` (invariants: one completion owner, no revived authority). Sector: engineering (coding fleet), kernel. Why: ephemeral `scout/checker/worker` templates need exactly this: orchestrators below the cap get spawn tools, leaves do not, children never get `message`/`cron`/`gateway`, results move one level at a time, and a runaway-spawn ceiling exists per group. The "structured result via `outputSchema` + `Promise.all` in a script" pattern is a good CEO planning primitive with no graph DSL.
6. **Agent-requested creation and config changes are typed operations approved by the operator, with provenance.** Evidence: `docs/concepts/multi-agent.md` "Agent provenance" (`operator | agent | claw`, `agents list --tree`), `docs/cli/openclaw.md` "Operations and approval" (approval names requesting agent; late approval cannot revive a closed run; exact `config set` on sensitive paths never reaches a model), `src/system-agent/{operation-types,operator-approval,operations-execute}.ts`. Sector: executive, ops-security. Why: matches invariant 6 exactly (CEO files a request, human promotes) and adds two details worth copying: bind the approval to the requesting run so stopping the run cancels it, and record who asked for the agent in the registry.
7. **Exec approval binding: executable identity + operand binding, deny on drift, heredoc/inline-eval rules, "stricter-of" merge.** Evidence: `docs/tools/exec-approvals.md` "Trust model", `docs/tools/exec.md` L139-168 (`strictInlineEval`, dispatch-chain binding, POSIX login shells never auto-reviewed), `docs/gateway/security/prompt-injection.md` (heredoc always needs approval in allowlist mode). Sector: engineering (T2 coder), ops-security. Why: our gate classifies tools, but a T2 coder's `exec` is one tool with infinite semantics; OpenClaw's answer (approve a resolved real path + content hash + one file operand, re-check at spawn, refuse to approve what cannot be bound) is the right shape for the kernel's `exec` policy in the Docker driver and for a human approval card that stays valid only for the bytes that were approved.
8. **Isolated-run hardening + delegate capability tiers + skill proposals.** Evidence: `docs/automation/cron-jobs/how-it-works.md` (denial metadata never reported green; auto-disable after repeated errors; jobs created enabled because "nothing supervises a disabled job"), `docs/concepts/delegate-architecture.md` (Tier 1 read+draft -> Tier 2 send-on-behalf -> Tier 3 proactive, hard blocks first), `docs/tools/skill-workshop.md` (proposal with hashes and rollback -> human apply). Sector: growth (marketing/sales/social), ops-security, kernel (scheduler). Why: the delegate tiers are the promotion ladder for `publisher`/`comms`/`sales` agents (start read+draft, human approves the tier change); the cron rules prevent silent failures in scheduled posting/trading jobs; skill proposals are the safe path for a `prototyper` to grow its own toolbox.

## BAD PARTS / anti-patterns

1. **Default is host execution, no sandbox, `security="full"`, `ask="off"`, plus a chat-driven escape hatch.** Evidence: `docs/gateway/security/trust-model.md` ("Trusted single-operator default: host exec on gateway/node is allowed without approval prompts"), `src/infra/exec-approvals-core.ts:131`, `docs/gateway/sandboxing.md` ("Sandboxing is off by default"), `docs/tools/elevated.md` (`/elevated full` from an allowlisted chat sender skips approvals), `docs/gateway/permission-modes.md` ("Without those settings or sandboxing, the default is full access"). Why we leave it out: it inverts invariant 3 (default deny) and invariant 9; safety is an opt-in config the operator must discover (`openclaw security audit`), and a tainted channel message can flip a session to elevated. Our gate must be the only path and must not have a `/elevated`.
2. **The model is an access-control decider.** Evidence: `docs/tools/exec.md` L139-152 (`mode: auto`: "eligible misses receive an allow, deny, or ask verdict from the native reviewer"; reviewer sees a redacted transcript excerpt), `docs/gateway/permission-modes.md` (`workspace` mode: "LLM review: allow, deny, or ask a human"), `docs/cli/openclaw.md` L287-290 ("Ambiguous consent goes to a separate configured completion call"), `docs/tools/skill-workshop.md` (autonomy settings). Why we leave it out: invariant 3 says the model never makes an access-control decision. The three-denials-escalate rule shows they know the reviewer can be gamed. We keep deterministic gate + human only.
3. **Credentials are agent-reachable by design; the vault is optional and unencrypted.** Evidence: `docs/gateway/secrets.md` warning ("Plaintext credentials remain agent-readable ..."), `docs/gateway/secrets/runtime-model.md` "Agent-access boundary" ("SecretRefs ... are not a process-isolation boundary"), `docs/gateway/secrets/secret-store-and-egress.md` ("Store values are not encrypted at rest"; `env` entries added as plaintext to exec), egress proxy "default-off", `docs/concepts/multi-agent.md` warning that a secondary agent reads through to the main agent's OAuth token. Why we leave it out: invariant 2 (agents never hold a key; injection only at the egress edge). We take the proxy design (Best 2) but make it mandatory for any worker with egress, keep secrets only in pmmcp's vault, and never put a `kind: env` plaintext path in.
4. **Everything shares one trust boundary: gateway-wide session read, agent-to-agent messaging, cross-provider sends all default on.** Evidence: `docs/gateway/security/trust-model.md` (`tools.sessions.visibility: all`, `tools.agentToAgent.enabled: true`, "Everyone who can message a tool-enabled agent shares that agent's delegated tool authority"), `docs/gateway/security/tool-permissions.md` (`allowAcrossProviders` default `true`; "an unsandboxed agent can still read a sandboxed agent's sessions"), `SECURITY.md` ("Session ownership, visibility, and presence are usability features, not security boundaries"). Why we leave it out: a tainted `comms` agent must not be able to read the CEO's transcripts or message the `publisher`; our default is per-agent pmmcp namespaces, hub-mediated tool views, and taint propagation, not a flat Gateway.
5. **Plugins, skills, and MCP bundles are in-process trusted code with allow-by-default tool exposure.** Evidence: `docs/gateway/security/tool-permissions.md#plugins` ("Plugins run in-process with the Gateway - treat them as trusted code"; "OpenClaw does not run built-in local dangerous-code blocking during install/update"), `docs/plugins/architecture.md` (hooks can claim turns, `before_prompt_build` widens/narrows tools), `src/agents/sandbox/tool-policy.ts` ("`allow: []` => allow all"), `src/agents/sandbox/constants.ts` (`DEFAULT_TOOL_ALLOW` includes `exec`, `write`), `extensions/` (~150 bundled). Why we leave it out: invariant 7 (unknown tools default `kernel-only`, classified in `tool-views.yaml`) and the no-new-dependency rule; our MCP hub classifies every tool before an agent sees it, and packs are data (manifests + schema-hash pins), not code loaded into the kernel.
6. **Agent-writable persona/instruction files and a workspace that is "default cwd, not a sandbox".** Evidence: `docs/concepts/agent-workspace.md` warning ("absolute paths can still reach elsewhere on the host unless sandboxing is enabled"; `workspaceAccess: "rw"` mounts the workspace with `AGENTS.md`/`SOUL.md`/`MEMORY.md`), `docs/concepts/memory-architecture.md` ("any process that can edit them already controls the agent workspace"), `docs/gateway/sandbox-vs-tool-policy-vs-elevated.md` ("Binding `/var/run/docker.sock` effectively hands host control to the sandbox; only do this intentionally"), `docs/gateway/security/network-exposure.md` L197-222 (list of `dangerously*` keys). Why we leave it out: invariant 8 (souls and AGENTS.md read-only to agents) and invariant 9 (never `docker.sock`, never `$HOME`); our manifests are versioned under `agents/<id>/history/` and only the control plane writes them.

## Conflicts with CLAUDE.md invariants

1. Invariant 1 (loopback + bearer header only): OpenClaw binds loopback by default but accepts the token in `connect.params.auth.token|password` (WS frame body), supports `gateway.auth.mode: "none"` on "private ingress", Tailscale header identity, and trusted-proxy header auth (`docs/concepts/architecture.md`, `docs/gateway/security/network-exposure.md`). Container images default to an exposed bind (`docs/gateway/security/index.md`). We keep header-only bearer and loopback-only.
2. Invariant 2 (agents never hold credentials): plaintext creds in config/`.env`/models.json are agent-readable; `env`-kind store values injected into exec; sentinels live in the same process; proxy default-off (Bad 3). Conflict.
3. Invariant 3 (gate -> human -> quarantine -> execute -> log, default deny, model never decides): default `full/off` host exec (Bad 1); LLM exec reviewer and `workspace` mode (Bad 2); `/elevated full` via chat; Full Access runs auto-apply config operations. Conflict. Partial alignment: sub-agent hard-deny, `guarded` mode, exec identity binding.
4. Invariant 4 (two events per LLM call with prompt/content/tokens/cost): the audit ledger is deliberately metadata-only ("never stores prompts, message bodies, tool arguments, tool results"); transcripts are in per-agent SQLite, cost is estimated in `/usage cost` from session logs (`docs/gateway/audit.md`, `docs/concepts/usage-tracking.md`). Different contract; we keep full events in the chained log with redaction.
5. Invariant 5 (append-only hash chain, immutability triggers): no hash chain; ledger persistence is "best-effort" and "can lose evidence"; execution-identity contexts expire after 30 days; `memory forget` and transcript pruning delete. Conflict with "archive never deletes" (inv. 6) as well.
6. Invariant 6 (ephemeral bounded by template; promotion is human): sub-agents inherit parent policy and can be spawned with `sandbox: "inherit"` (default) so an unsandboxed parent yields unsandboxed children; `agents.defaults.subagents.model` can differ from parent. Aligned on the creation side: agent-requested agent creation needs operator approval and records provenance (Best 6).
7. Invariant 7 (unknown MCP tools default `kernel-only`; nested-LLM tools disabled): MCP tools are allowed by profile/policy once the server is configured; `llm-task`, `code_execution`, Code Mode/Swarm let scripts call agents; `bundle-mcp` exposes all server tools in sandbox with one allow entry (`docs/gateway/sandbox-vs-tool-policy-vs-elevated.md`). Conflict.
8. Invariant 8 (souls/AGENTS.md read-only to agents): `AGENTS.md`/`SOUL.md` live in the agent workspace; with `workspaceAccess: "rw"` or no sandbox the agent's `write`/`edit` tools reach them; Skill Workshop autonomy and "automatic background learning" write skills with file tools (Bad 6). Conflict.
9. Invariant 9 (container hardening; never privileged/docker.sock/$HOME): when enabled, defaults match ours (`--read-only`, `--cap-drop ALL`, `no-new-privileges`, `network none`); but sandbox is off by default, `user` is unset by default, pids/memory/cpu caps are unset by default, `docker.sock` binding is documented as an intentional option, and `dangerouslyAllow*` overrides exist (`src/agents/sandbox/config.ts` L110-117, `src/agents/sandbox/docker.ts`). ## Verdict

Take the mechanics that are pure kernel shape: the closed lane enum with capacity groups and steer/collect ingress, the depth-typed sub-agent policy with fan-out backstops and one-level announce chain, the Claw-style role manifest with lane contracts, the memory provenance and session-kind gating rules, the exec identity-binding approval model, and the secret egress proxy design (sentinel + exact-host binding + revocable per-process grant) as the blueprint for our Phase 2 sidecar. Leave the posture: host exec with `full/off` by default, opt-in sandboxing, an LLM reviewer that grants exec, chat-driven `/elevated`, in-process trusted plugins with allow-by-default tools, agent-readable plaintext credentials, Gateway-wide session and agent-to-agent reach, agent-writable SOUL/AGENTS files, and a best-effort metadata-only audit that can lose evidence. In our fleet these become: every roster entry ships a lane contract and a Claw-like manifest a human approves; `comms`/`publisher`/`sales` start at delegate Tier 1 and are promoted by a human; the coding fleet runs as depth-capped leaves under one orchestrator with exec approvals bound to bytes; and nothing an agent reads from the network can become curated memory or a write without passing the kernel gate.
