## What it is

An "agentic operating system" product stack: a single-agent runtime (`@elizaos/core` `AgentRuntime`) that hosts one `Character` per runtime, extended by plugins that contribute actions, providers, evaluators, services, model handlers, routes, and UI views. The product (Eliza app) bundles a personal assistant, messaging connectors (Discord/Telegram/X/Slack/WhatsApp/iMessage/Matrix/WeChat), a non-custodial EVM+Solana wallet with swaps/bridges/LP/governance/pump.fun, a coding-agent orchestrator that spawns Codex/Claude/Kimi/Grok/Pi via ACP, an MCP client plugin, and a fine-tuning pipeline (`packages/training`) that trains "eliza-1" models on the runtime's own trajectories. CONFIRMED (`README.md`, `plugins/*/README.md`).

It is not a multi-agent kernel: there is no control plane that owns a fleet. "Multi-agent" appears as (a) ACP-spawned coding sub-agents routed back into the single main agent's message loop, (b) a scenario-runner "arena" that boots several independent runtimes for evals, and (c) Eliza Cloud hosting. CONFIRMED (`plugins/plugin-agent-orchestrator/docs/sub-agent-routing.md`, `packages/scenario-runner/README.md`).

## Orchestration model

- Message pipeline per turn: HANDLE (`should_respond`, `compose_state`, provider context) -> PLAN (planner picks actions) -> ACTION (handlers run) -> EVALUATE (post-turn evaluators). CONFIRMED (`plugins/plugin-trajectory-logger/README.md`; `packages/core/src/runtime/planner-loop.ts` exists).
- Actions have `ActionMode` (PLANNER default, plus ALWAYS/CONTEXT/MESSAGE x BEFORE/DURING/AFTER hooks); providers are gated by `contexts`/`contextGate`. CONFIRMED (`packages/core/src/types/components.ts` lines 312-390, 787-817).
- Sub-agents: `plugins/plugin-agent-orchestrator` spawns external coding agents over ACP as subprocesses on the same host; terminal events (`task_complete`, `error`, `blocked`) are re-injected as synthetic `Memory` rows into a task room / worktree room so the main agent's planner decides what to do next ("main-agent-in-the-loop"). A per-session round-trip cap (default 32) force-stops ping-pong loops. Origin metadata (`messageId`, `roomId`, `userId`) is captured at spawn so results land back in the originating room. CONFIRMED (`plugins/plugin-agent-orchestrator/docs/sub-agent-routing.md`, `README.md`).
- Swarm event stream: `SwarmEvent` carries `seq`, `taskId`, `parentSessionId` so a flat wire stream can be rebuilt into a task -> sub-agent -> step tree; `toSwarmActivity` is the single boundary that validates raw ACP payloads into typed envelopes. CONFIRMED (`packages/core/src/types/swarm-coordinator.ts`).
- Workflows: `plugins/plugin-workflow` wraps Smithers (TS/TSX workflow modules) with approval-gated steps that resume only after a persisted decision. CONFIRMED (`plugins/plugin-workflow/README.md`).
- Autonomy: an autonomy service issues self-prompts stamped `content.metadata.isAutonomous`; "private" actions are only exposable on those turns. CONFIRMED (`packages/core/src/runtime/private-action-gate.ts`).

## Memory model

- Everything is a `Memory` row: `{entityId, agentId, roomId, worldId, content, embedding, metadata}` with `MemoryScope` in `shared | private | room | global | owner-private | user-private | agent-private`. Path: `packages/core/src/types/memory.ts`. CONFIRMED.
- Long-term memories via a `MemoryStorageProvider` registered by the SQL plugin; core degrades if absent. Path: `packages/core/src/types/memory-storage.ts`. CONFIRMED.
- Recall for connector messages goes through a provenance envelope: `source:account:room:platformRecordId` dedupe key, `trust: self | sender-stamped | unverified`, fail-closed scope ladder, destination containment; missing provenance withholds the item from recall (nothing defaults to `global`). Explicitly notes that stored metadata "is not an unforgeable attestation". Path: `packages/core/src/access-control/provenance-envelope.ts`. CONFIRMED.
- Disclosure at egress is min-over-members of the attested audience; non-owners are admitted only what an explicit grant or open scope allows. Path: `packages/core/src/access-control/audience-egress.ts`. CONFIRMED.
- Post-turn evaluators extract facts/relationships; `semanticSignal` lets memory-extracting evaluators skip low-signal turns. Path: `packages/core/src/types/evaluator.ts`. CONFIRMED.
- Trajectories: every turn's exact model request/response (with native tool calls) is captured by `TrajectoriesService` and exported as SFT rows for the eliza-1 training pipeline. Path: `packages/core/src/features/trajectories/TrajectoriesService.ts`, `packages/training/README.md`. CONFIRMED.

## Sandbox & security posture

Isolation
- No container/VM isolation for the agent or its tools in this repo. Coding agents and shell run as host subprocesses; `plugin-pty` spawns real Claude Code / Codex CLIs on the host with a minimal env. "Sandbox" in `packages/agent` means a cloud-provisioned character, and `SandboxService` in coding-tools is a path allowlist. CONFIRMED (`plugins/plugin-coding-tools/README.md`, `plugins/plugin-pty/README.md`, `packages/agent/src/runtime/sandbox-character.ts`).
- Network: SSRF guard with private-range blocklist, DNS pinning, redirect revalidation (`packages/core/src/network/ssrf.ts` per `packages/docs/security.md`). CONFIRMED via doc; code file not opened.

Credentials
- Character files carry `secrets` and `settings.secrets`; at boot the runtime merges DB secrets, runtime overrides, `character.secrets`, and `character.settings.secrets` and writes the merged map back onto `this.character.secrets` / `this.character.settings.secrets`; `getSetting()` reads `character.secrets` first. Path: `packages/core/src/runtime.ts` lines 1884-1930. CONFIRMED.
- Local Vault: AES-256-GCM in PGlite, master key from OS keychain or `ELIZA_VAULT_PASSPHRASE`; `vault://<key>` references resolve into an in-memory settings overlay and are "never copied into `process.env`"; list APIs return metadata only. Path: `docs/security/vault-and-credential-trust-domains.md`, `packages/vault/README.md`. CONFIRMED (design doc + package README; runtime resolver not read).
- Wallet keys: `EVM_PRIVATE_KEY` / `SOLANA_PRIVATE_KEY` in env or keychain for the `local` backend; `/api/wallet/export` exports private keys behind a second token `ELIZA_WALLET_EXPORT_TOKEN`. Path: `plugins/plugin-wallet/README.md`, `packages/docs/security.md`. CONFIRMED.
- API surface writes env: `PUT /api/env` with a `BLOCKED_ENV_KEYS` denylist (LD_PRELOAD, NODE_OPTIONS, proxies, tokens, wallet keys); `/api/terminal/run` executes shell behind `ELIZA_TERMINAL_RUN_TOKEN`. Path: `packages/docs/security.md`. CONFIRMED (doc).
- Sub-agent credentials: Pi spawns get a mode-0700 private home whose config references a child-only env var, "the credential itself is never written to disk"; Kimi/Grok adapters strip API keys from the child env so subscription logins cannot silently become PAYG. CONFIRMED (`plugins/plugin-agent-orchestrator/README.md`).

Gates
- Unified action gate: private-action gate -> disclosure gate -> operator `ACTION_ROLE_POLICY` override -> contextGate -> roleGate, in one function every exposure/execution path uses. Path: `packages/core/src/runtime/action-gate.ts`. CONFIRMED.
- Inbound hardening: `hardenIncomingUserMessage` strips forged `isAutonomous` / security stamps, regex-detects injection patterns and financial command language (`send 5 eth`, `transfer all`), stamps `promptInjectionSuspected`, and for public sources (discord, telegram, twitter, slack, whatsapp, imessage, sms, webhook, api) wraps the text in an external-content envelope with a warning while retaining the raw payload in `userPayloadText`. Path: `packages/core/src/security/incoming-message-security.ts`, `external-content.ts`. CONFIRMED.
- Should-respond risk gate: pure scorer (hidden chars, homoglyphs, letter-split / reversed keywords, authority/urgency/intimidation keywords) runs in parallel with should-respond; OWNER/ADMIN bypass; borderline USER/GUEST escalates to a single `TEXT_LARGE` model adjudication. Path: `packages/core/src/features/trust/should-respond-risk-gate.ts`. CONFIRMED.
- Confirmation: `requireConfirmation` stashes a pending record in runtime cache keyed `confirmation:<userId>:<action>:<pendingKey>` (5 min TTL) and, on the next turn from the same entity, tests the reply against a multilingual yes-regex; `llmConfirmedFlagIsAuthoritative()` always returns `false` ("LLM `confirmed: true` must not authorize destructive ops (GHSA-rqm7 class)"). Path: `packages/core/src/utils/confirmation.ts`. CONFIRMED.
- Wallet gates: `ON_CHAIN_WRITE_SUBACTIONS` is the single source for both the injection block (`assertWalletFinancialActionAllowed`, refuses on `promptInjectionSuspected`, cites GHSA-gh63-5vpj-39qp) and the mandatory confirmation (`gateWalletFinancialExecution`, pending key derived from actual params so a "yes" cannot authorize different params, cites GHSA-rqm7-f4jc-84x3); transfer recipients must appear in the user's own text/params, never from token metadata or prior context (GHSA-7qxr-x6cg-r9cc); `mode=prepare` default, `simulate` needs only the public key. Path: `plugins/plugin-wallet/src/security/*.ts`, `README.md`. CONFIRMED. The three GHSA ids are cited in source; public advisory pages returned 404, so they are INFERRED to be repo-scoped advisories.
- Spend policy: `PolicyModule.evaluate(scope, summary) -> ok | requires_approval | blocked` with size limits, allowlists, cooldowns. Path: `plugins/plugin-wallet/src/policy/policy.ts`. CONFIRMED (interface only).
- Wallet audit: hash-chained append-only `AuditLogRow` (SHA-256 over canonical fields + `prevHash`, genesis `0*64`) for validate/handler/sign/approval/automation events. Path: `plugins/plugin-wallet/src/audit/audit-log.ts`. CONFIRMED.
- Pending-user-action inbox: one `PendingUserAction` contract (`approval | task_approval | prompt | credential | clarifying_question | blocked_task | choice`) that every producer maps onto. Path: `packages/core/src/types/pending-user-action.ts`. CONFIRMED.
- Plugin install runs `--ignore-scripts`; Electrobun RPC validates `openExternal` schemes; DNS-rebinding Host check; `$include` / `__proto__` key blocking. Path: `packages/docs/security.md`. CONFIRMED (doc).

Security history (web, CONFIRMED as fetched search results; papers not fetched in full because arxiv is egress-blocked)
- Patlan et al., "Real AI Agents with Fake Memories: Fatal Context Manipulation Attacks on Web3 Agents" (arXiv 2503.16248, also IACR ePrint 2025/526 "AI Agents in Cryptoland: Practical Attacks and No Silver Bullet"), Mar 2025: defines context manipulation across input channels, memory, and external feeds; demonstrates memory-injection against ElizaOS where an attacker's instructions persisted in the shared conversation store cause later unintended transfers across sessions and platforms; finds models "significantly more vulnerable to memory injection compared to prompt injection" and prompt-based defenses insufficient; introduces CrAIBench. https://arxiv.org/abs/2503.16248 , https://eprint.iacr.org/2025/526.pdf
- AIXBT incident, 18 Mar 2025: attacker gained access to the agent's operator dashboard and queued two prompts that caused 55.5 ETH (~$106k) to leave a "simulacrum" wallet; remediation was server migration, key rotation, dashboard suspension. AIXBT is an Eliza-ecosystem agent; sources do not attribute the bug to the framework itself. https://incidentdatabase.ai/cite/1003/ , https://crypto.news/aixbt-agent-hacked-losing-55eth-aixbt-token-drops-2025/
- The codebase's own response is visible in code: `promptInjectionSuspected` + external-content envelope (GHSA-gh63-5vpj-39qp), recipient-authorization (GHSA-7qxr-x6cg-r9cc), model-flag-never-authoritative confirmation (GHSA-rqm7-f4jc-84x3), and the provenance envelope that refuses to treat stored metadata as verified. CONFIRMED in source.

## BEST PARTS

1. Idea: one composed action gate that every exposure and execution path must call, with a fixed precedence (private -> disclosure -> operator policy -> context -> role) and a startup warning for policy keys that loosen a declared gate or match nothing. Evidence: `packages/core/src/runtime/action-gate.ts`, `action-role-policy.ts`. Sector: kernel. Why: it is the structural cure for "the model chose an action the gate never saw"; our `src/policy` gate should likewise be the single function the planner, the tool-view filter, and the executor all call, and the tool-view loader should warn on classifications that widen a default.
2. Idea: model-supplied confirmation flags are never authoritative; a destructive op needs a fresh human turn, the pending key is derived from the actual parameters, and a "yes" cannot authorize different parameters than were previewed. Evidence: `packages/core/src/utils/confirmation.ts` (`llmConfirmedFlagIsAuthoritative` returns false), `plugins/plugin-wallet/src/security/wallet-financial-confirmation.ts`. Sector: trading, ops-security. Why: this is invariant 3 made concrete; our approval records should bind a hash of the canonical tool args and reject a resolution whose args differ.
3. Idea: one source-of-truth set of write sub-actions shared by the injection block and the confirmation gate so a newly added verb cannot be covered by one and missed by the other; a `simulate` mode that needs only the public key and skips the gate because it cannot broadcast. Evidence: `plugins/plugin-wallet/src/security/wallet-context-safety.ts`, `README.md`. Sector: trading. Why: our trading agent should get `quote/simulate` tools at `read` risk and `submit` tools at `irreversible`, defined once in `tool-views.yaml`, with daily and per-order caps (their x402 `X402_GLOBAL_DAILY_LIMIT` / `X402_PER_REQUEST_MAX` and `PolicyModule` `ok|requires_approval|blocked` are the shape).
4. Idea: transfer recipients must be stated by the human in their own words or structured params, never inferred from token metadata, prior context, or memory; untrusted labels are sanitized of embedded addresses before display. Evidence: `plugins/plugin-wallet/src/security/wallet-context-safety.ts` header (GHSA-7qxr-x6cg-r9cc). Sector: trading. Why: closes the exact memory-injection path the Princeton paper exploited; our trading approval card should show the recipient/venue as a human-entered field, not a model-proposed one.
5. Idea: inbound trust boundary hardening: strip forged runtime markers, wrap public-source content in an explicit untrusted envelope while retaining the raw payload for non-prompt consumers, stamp `promptInjectionSuspected` from a synchronous scorer, and let role decide bypass vs model adjudication. Evidence: `packages/core/src/security/incoming-message-security.ts`, `features/trust/should-respond-risk-gate.ts`, `security/external-content.ts`. Sector: ops-security, growth (comms/social ingress). Why: it is a working implementation of our taint model at the ingress edge; the "OWNER bypasses, GUEST escalates" split is a good default for the `comms` agent, and the envelope-plus-retained-payload trick avoids resolvers parsing armor back out of prompts.
6. Idea: provenance envelope on recall: `source:account:room:platformRecordId` identity, `trust: self|sender-stamped|unverified`, fail-closed when provenance is missing, and an explicit refusal to label stored metadata "verified". Evidence: `packages/core/src/access-control/provenance-envelope.ts`. Sector: kernel (memory), growth. Why: pmmcp memories written by tainted runs need a provenance stamp so the CEO's recall can down-rank or exclude `unverified` items; this is the direct defense against memory injection across agents that the paper called out.
7. Idea: sub-agent results re-enter the parent as boundary events only (`task_complete|error|blocked`), with origin room/user/message captured at spawn, an in-memory dedupe key, a per-session round-trip cap that force-stops loops, and a cache-stable provider for live status so streaming does not thrash the prompt cache. Evidence: `plugins/plugin-agent-orchestrator/docs/sub-agent-routing.md`. Sector: engineering (coding fleet), executive. Why: our CEO -> coder delegation should carry `goalId` + origin, emit only terminal events into the CEO's lane, and cap CEO<->worker round trips in code rather than trust the model to stop.
8. Idea: child-process credential hygiene for coding sub-agents: private 0700 home per spawn, credential passed by child-only env reference never written to disk, adapters strip PAYG API keys so a subscription login cannot silently bill, spawn fails closed if account selection fails instead of using ambient keys. Evidence: `plugins/plugin-agent-orchestrator/README.md`, `plugins/plugin-pty/README.md` ("minimal child env", "dedicated cloud credential", `--coding-only` prevents recursive spawns). Sector: engineering, ops-security. Why: matches invariant 2's spirit and gives concrete rules for the T2 coder's egress proxy: per-agent credential, no ambient keys, no nested orchestrators.

Also worth noting (smaller): the `PendingUserAction` single inbox contract (`packages/core/src/types/pending-user-action.ts`) for our Approvals view; the hash-chained wallet audit row (`plugins/plugin-wallet/src/audit/audit-log.ts`) which is the same idea as our event chain scoped to signing; DM policy defaulting to `pairing` and failing closed on unknown values (`plugins/plugin-x/src/dm-policy.ts`) for the Telegram/SMS ingress in Phase 4; the HITL credential probe catalog with `ok|unauthorized|unavailable` states and masked values (`docs/testing/hitl-probes.md`) as a template for `aos probe`.

## BAD PARTS / anti-patterns

1. Issue: secrets live in the character file (`Character.secrets`, `settings.secrets`) and the runtime merges every secret source back onto the in-memory character object; `getSetting()` reads `character.secrets` first; the MCP README shows a GitHub PAT inline in `settings.mcp.servers.env`; Telegram README shows `botToken` inline. Evidence: `packages/core/src/types/agent.ts`, `packages/core/src/runtime.ts` 1884-1930, `plugins/plugin-mcp/README.md`, `plugins/plugin-telegram/README.md`. Why leave out: violates invariant 2 and our "never write a secret into any file under the repo" rule; the vault-reference doc is the right direction but the code path still tolerates plaintext.
2. Issue: the agent process holds the wallet private key (`local` backend from env/keychain), the MCP connections, the provider keys, and a `/api/wallet/export` endpoint that returns private keys behind a second bearer token; plus `PUT /api/env` (env-var writes with a denylist) and `/api/terminal/run` (shell via HTTP). Evidence: `plugins/plugin-wallet/README.md`, `packages/docs/security.md`. Why leave out: the AIXBT incident was exactly "attacker reaches the operator surface, agent executes"; denylist-based env writes and key export over HTTP are surface we must not have. Our broker and egress proxy hold keys; the kernel exposes no key-returning or env-writing command.
3. Issue: no process/container isolation for tools; SHELL runs `/bin/bash -c` on the host, `SandboxService` confines only FILE arguments and "does not confine paths referenced by a shell command"; the exec approval has an `allow-always` allowlist persisted to a file. Evidence: `plugins/plugin-coding-tools/README.md`, `src/shell/approvals/service.ts`. Why leave out: conflicts with invariant 9; a standing allowlist is a gate bypass that grows over time. Our coder runs in T2 Docker with the proxy; approvals are per-run, never "always".
4. Issue: regex/keyword injection detection plus a model adjudication decides whether a message is trusted; OWNER/ADMIN bypass the gate entirely; confirmation is a yes-regex on the next message from the same `entityId` (no channel binding, no re-authentication). Evidence: `packages/core/src/security/incoming-message-security.ts`, `features/trust/should-respond-risk-gate.ts`, `utils/confirmation.ts`. Why leave out: the Princeton paper's finding is that prompt-level defenses fail against memory injection; a `TEXT_LARGE` adjudication is the model making an access-control decision (invariant 3), and a spoofed owner identity on a public channel gets bypass. Keep the scorer as a taint signal only; approvals come through the loopback control plane with the bearer token, never through the chat channel.
5. Issue: autonomous social loops (post, timeline likes/retweets/quotes, discovery engagement with follow-count thresholds, DM auto-reply) run on timers with no per-post human approval; `TWITTER_DRY_RUN` is the only brake. Evidence: `plugins/plugin-x/README.md`, `src/post.ts` (only `dryRun` grep hits). Why leave out: Phase 4 exit criterion requires a human approval between clip and post; a `publisher` agent gets `post` at `irreversible` risk, and discovery/engagement is a `read`-only scout unless a human turns a specific campaign on.
6. Issue: operator-configurable gate widening via env: `ACTION_ROLE_POLICY` replaces an action's declared gates ("used to whitelist actions whose upstream contextGate is narrower"), and `ELIZA_RUNTIME_MODE=local-yolo` unlocks coding tools on Android. Evidence: `packages/core/src/runtime/action-role-policy.ts`, `plugins/plugin-coding-tools/README.md`. Why leave out: "widening what an agent can reach" is change-controlled in CLAUDE.md, must go through `tool-views.yaml` review, never an env var at boot.
7. Issue: the framework's trajectories feed a fine-tuning pipeline (eliza-1) and the memory store persists whole conversation histories including public-channel content. Evidence: `packages/training/README.md`, `packages/core/src/features/trajectories/TrajectoriesService.ts`. Why leave out for now: our log is evidence, not training data; if we ever train on it, tainted-run content must be excluded by provenance, which their pipeline README does not mention.

## Conflicts with CLAUDE.md invariants

1. Invariant 1 (loopback-only control plane, bearer only): Eliza serves an HTTP API with token auth and a Host-header check but also exposes env-writing, shell, and key-export routes; not comparable to our protocol. Reject the route set; keep nothing.
2. Invariant 2 (agents never hold MCP connections, provider keys, vault handles): the `AgentRuntime` is the MCP client, the model caller, the vault reader, and the wallet signer in one process; `character.secrets` is in the agent's own object. Direct conflict.
3. Invariant 3 (gate -> approval -> quarantine -> execute -> log; model never decides access): the action gate is deterministic (good) but the risk gate escalates to a model adjudication and OWNER/ADMIN bypass; confirmation is chat-channel yes/no. Partial conflict; take the deterministic gate, drop model adjudication as a decision.
4. Invariant 4 (two events per LLM call with cost): trajectories capture request/response, but cost accounting is not part of the captured row as read; INFERRED. Not a conflict, just not a source.
5. Invariant 5 (redacted, hashed, chained event log with immutable triggers): only the wallet plugin has a hash chain; the general memory store is mutable (`updateLongTermMemory`, `deleteLongTermMemory`). Our chain is broader; take nothing but the audit-row shape.
6. Invariant 6 (ephemeral agents bounded by template; promotion is human): no template/tier concept exists; sub-agents are external CLIs with whatever the host has. No mapping.
7. Invariant 7 (unknown tools kernel-only; nested LLM tools disabled): MCP tools are exposed to the planner as one `MCP` action over all connected servers with no per-tool classification; coding sub-agents are nested LLM loops outside the parent's router/budget (they note `--coding-only` to prevent recursion, which is the same concern). Conflict; our tool-views classify per tool and nested agents run only as kernel-managed runs.
8. Invariant 8 (souls/AGENTS.md read-only to agents): characters are persisted and editable via API/UI (`packages/agent/src/services/character-persistence.ts`, character history). Conflict with our frozen manifests + `history/`; the history idea itself is fine.
9. Invariant 9 (container hardening): no containers; host subprocesses with path allowlists. Conflict.
10. Invariant 10 (tool naming): not applicable; they use umbrella actions with sub-operation params.

## Verdict

Take the deterministic composed action gate, the parameter-bound human confirmation with model flags never authoritative, the single write-verb set shared by injection block and confirmation gate, the human-stated-recipient rule, the ingress envelope plus taint stamp, the provenance-scored recall, the boundary-only sub-agent routing with round-trip cap, and the child-credential hygiene rules for coding agents. Leave the single-process design where the agent holds keys, MCP, vault, and wallet; plaintext secrets in character files; host-level shell with a persistent allowlist; env-driven gate widening; model-adjudicated trust; and autonomous social posting without approval. ElizaOS is the best available worked example of what memory- and context-injection attacks on a trading agent look like and of the specific code-level patches that followed, which makes it a strong source of gate test cases for our trading and social sectors and a weak source of architecture.
