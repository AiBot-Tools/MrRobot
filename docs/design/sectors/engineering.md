# Engineering sector: the coding fleet and the prototyper

Design for aos-kernel's ENGINEERING sector, 2026-09-20; adversarially reviewed and revised 2026-09-21 (findings and rejections in §13-14). Inputs: `CLAUDE.md` (the contract), `docs/plan/phase-0-bootstrap.md` (the Phase 0 shapes for `agent.yaml`, `tool-views.yaml`, `kernel.yaml`, protocol v1 and the event catalog; cited as `plan §3.4/§3.6`), and the 23 survey reports under `scratchpad/survey/`. The starter roster (ceo, researcher, writer, coder T2, auditor, producer, publisher, comms; templates scout/checker/worker; tiers T0 kernel-hosted / T1 process sandbox / T2 Docker `trusted` + egress proxy / T3 Docker `hostile` no egress) is the baseline this document extends.

**Evidence legend.** `CONFIRMED` = I opened the cited file in the reference clone this session and read the cited lines (paths relative to `scratchpad/refs/`). `SURVEY` = the cited survey report (`scratchpad/survey/<name>.md`) states it read the file; I did not re-open it. `INFERRED` = derived from confirmed or surveyed facts, or a web-snippet fact the survey itself marked INFERRED. `DESIGN` = a choice in this document. Nothing below is a feature claim about a project unless it carries one of the first three tags.

## 1. Mission

Ship reviewed, tested, reproducible changes to the operator's repositories at a rate one person cannot sustain alone, with every network call a logged proxy decision, every edit confined to a kernel-created worktree, every "tests passed" an execution-grounded `verify.result` event produced by a human-pinned command over a test suite whose weakening is itself a gate, and every irreversible step (PR open, merge to a protected branch, tag, publish, deploy, migration, rollback) a human decision made in the control plane with the evidence attached. The sector also owns a prototyper that turns a design brief into a running, visually verified demo branch that is explicitly not mergeable until the fleet hardens it.

The measured levers from the coding-fleets landscape decide the shape: execution-grounded verification, best-of-k selection by a verifier, a reasoning/editing model split, a bounded tool interface, and cheap context management move outcomes; more agents per se, peer swarms, LLM reviewers without execution, and unmatched-budget comparisons do not (SURVEY `landscape-coding-fleets.md` §15, "Reading across them"). The roster is therefore small: three persistent agents and four ephemeral templates carrying eleven named profiles and souls, each justified by a distinct tool surface, isolation or taint need, model binding, context boundary or gate posture (Frontier rule 1). Everything else is a soul layered on one of these or a tool view.

## 2. Org topology

```
operator (control plane, HumanActor)          all approvals, promotions, ESTOP, plan sign-off
   |
 ceo (T0, orchestrator, cross-sector)          delegates ONE engineering objective per run, sees terminal events only
   |
 eng-lead (T2 trusted, persistent, depth 1)    owns the objective: goal tree, integration lane, spawn budget
   |-- prototyper (T2 trusted, persistent)     demo branch + visual evidence; never merges
   |-- sre (T1, persistent, tainted-by-default) reads prod state, proposes irreversible ops; scheduled reconcile
   |
   `-- ephemeral leaves (depth 2, cannot spawn, cannot message):
         scout(eng)  architect  implementer{code|docs|refactor}  tester
         reviewer{code|security}  release
```

Three persistent agents, four ephemeral templates, eleven named profiles. `architect` and `docs-writer` were persistent/standalone in the first draft and are not any more (review findings F8, F9 in §13): persistence buys a pinned pmmcp namespace and a schedule, and `architect` needs only the first, which a template can be granted at spawn; `docs-writer` differed from `implementer` only in model chain and ownership set, which `profiles:` (K1) now expresses on one manifest.

* **Depth is two and fixed.** `ceo -> eng-lead` is a standard-agent delegation carrying `goalId`, a self-contained brief and a budget slice; `eng-lead -> leaf` is `spawnEphemeral` from a template. Leaves have `spawn: none`, no `pmmcp` write outside their own namespace, no messaging or scheduling tools, and cannot re-add any of those (OpenClaw depth table, CONFIRMED `openclaw/docs/tools/subagents/nesting.md:33-40`, and its tool policy by depth, "**Leaf (at `maxSpawnDepth`):** no recursive orchestration tools", CONFIRMED same file `:68-71`; Hermes children never gain a tool the parent lacks, SURVEY `hermes-agent.md` `tools/delegate_tool_toolsets.py`). The Hermes post-mortem's finding that depth-2 subagents were 65% of a $19.3k run (SURVEY `hermes-agent.md`, `evals/postmortem/README.md`) is why leaves carry hard wallclock, turn, tool-call and micro-USD caps and why `eng-lead.spawn.maxChildren` is a manifest number the kernel refuses to exceed.
* **Policy is pinned at spawn, and a mid-run policy change never widens a live run.** OpenClaw snapshots the requester's effective sender policy into the child at spawn so later config edits do not retroactively change it, while keeping depth policy authoritative (CONFIRMED `openclaw/docs/tools/subagents/nesting.md:68-70`). DESIGN: every run records `policyVersion` = the content hash of the `tool-views.yaml` + manifest + spawn-spec triple it was admitted under, in `run.started`. The gate evaluates the pinned version for the life of the run. If the operator edits `tool-views.yaml` mid-run, the kernel takes the **stricter of** pinned and current (an exposure that narrowed applies immediately; one that widened does not), and logs `policy.drift{runId, from, to, effect}`. A pack whose schema hash drifts mid-run fails closed: the tool is denied for the remainder of the run and the drift is an alert, which is the Managed Agents rationale for defaulting MCP toolsets to `always_ask` ("This ensures that new tools added to an MCP server do not execute in your application without approval", SURVEY `landscape-agent-os.md` §8).
* **Cancellation cascades; the objective is the unit.** Explicit cancellation of an orchestrator cascades through its descendant tree (OpenClaw cascade stop, CONFIRMED `openclaw/docs/tools/subagents/nesting.md:83-85`). `aos kill <objective>` fences every live leaf's dispatch capability, stops new spawns, tears down containers, keeps every branch and worktree, and emits `run.cancelled` per leaf; an incomplete cascade is reported as a failure and the objective stays in `cancelling` until a human clears it (OpenClaw reset semantics, "If child cancellation is incomplete, reset reports a failure before clearing the conversation", CONFIRMED same file `:81`). This is distinct from `eng.pause` (§ ESTOP), which never touches in-flight work. Without the cascade, killing `eng-lead` leaves up to `maxConcurrent` leaves burning budget against a dead parent.
* **The dispatcher is kernel code, not a model.** The `eng-lead` LLM handles exceptions (re-plan after failed verification, merge conflicts, blocked workers, budget reallocation). The per-task pipeline `implementer -> tester -> hooks -> reviewer -> integrate -> PR` is a kernel workflow of deterministic nodes with gated AI nodes (Archon's YAML-DAG-plus-worktree shape, SURVEY `landscape-agent-os.md` §16; Hermes's dispatcher loop, CONFIRMED `hermes-agent/website/docs/user-guide/features/kanban.md:126`). This keeps access control out of the model and keeps `eng-lead` runs cheap.
* **One writer per checkout, one integration owner.** Every writing run gets a kernel-created git worktree under the domain's `mountRoot` (`<mountRoot>/<repo>/<branch-slug>`, the herdr layout, CONFIRMED `herdr/docs/next/website/src/content/docs/cli-reference.mdx:181-183`); the kernel never lets two writers share a worktree and only `eng-lead`'s integration lane edits manifests and lockfiles (ruflo, CONFIRMED `ruflo/CLAUDE.md:68,75`; Claude Code's mechanical refusal of edits reaching the main checkout, SURVEY `landscape-coding-fleets.md` §1). Ownership is a path set in the spawn spec, enforced by a kernel hook that denies edits outside it; "a lease coordinates ownership; it never grants authority" (CONFIRMED `ruflo/CLAUDE.md:75`).
* **Delegation contract.** `eng-lead`'s spawn call carries only `{template, brief, ownership, acceptance, budgetSlice, capabilities ⊆ template}`; there is no model-facing `tools` or `model` parameter (Hermes `DELEGATE_TASK_SCHEMA`, SURVEY `hermes-agent.md` `tools/delegate_tool.py:56,631`). The brief follows the Task-spec contract Target / Change / Constraints / Ownership / Observable acceptance (SURVEY `orca.md`, `skill-guides/orchestration.md` "Task-spec contract") and the OpenHands rule that the child "cannot see the parent's history" so the brief "must be self-contained" (CONFIRMED `OpenHands/src/api/launch-child-conversation-client-tool.ts:48,98`). Results re-enter `eng-lead` only as terminal events (`run.finished`, `verify.result`), never as streamed chunks (eliza boundary-only routing, CONFIRMED `eliza/plugins/plugin-agent-orchestrator/docs/sub-agent-routing.md:9-10,47-48`), and a per-objective round-trip cap (default 32, eliza's `ACPX_SUB_AGENT_ROUND_TRIP_CAP`, CONFIRMED same file line 124) force-stops ping-pong in code.
* **Exactly one terminator per leaf run.** A leaf ends with one of `complete | request_review | block`; `crashed | gave_up | timed_out | budget_reached | cancelled` are kernel-emitted, and a run that exits without a terminator is treated as crashed (Hermes lane contract, CONFIRMED `hermes-agent/website/docs/user-guide/features/kanban-worker-lanes.md:74-83`). The outcome is a typed field, "never encode failure only in prose" (Orca, CONFIRMED `orca/skill-guides/orchestration.md:83-85`). Child summaries are self-reports: the kernel requires a verifiable handle (artifact hash, diff stat, test log id) in every `complete` (Hermes `_DESCRIPTION_HEAD`, SURVEY `hermes-agent.md`).
* **A leaf's summary is untrusted model text and is shaped like data.** The terminator payload is zod-typed: typed fields (`evidence[]`, `changedPaths[]`, `verifyResultId`, `blockedQuestion`) plus at most one free-text field capped at 2 KB. The kernel renders it into `eng-lead`'s context inside an explicitly untrusted delimiter, never as an instruction block, because a leaf's summary is derived from repository content the leaf read and is therefore an injection channel into the only agent that can spawn. The kernel additionally strips forged tool-result and event-envelope shapes from every `llm.response` before it is stored or re-rendered and logs `llm.sanitized{runId, pattern, count}` (MiroFish report-agent fabricated-result stripping and minimum-evidence gate, SURVEY `MiroFish.md` best part 5, `backend/app/services/report_agent.py`, `backend/tests/test_report_tool_result_sanitizer.py`). Without this, "the tester passed" is a sentence any leaf can write.
* **Taint is computed by the kernel from provenance, never declared by the spawner.** A run is tainted iff its brief, workspace or context transitively references an artifact whose provenance record is marked untrusted (web fetch, inbound message, third-party log payload, a quarantined artifact that has not been released). `eng-lead` is a model; letting it decide whether a child's brief is tainted would make the model an access-control decider (invariant 3). The spawn spec may only *raise* taint, never clear it; clearing is a human quarantine release recorded as `quarantine.released{artifactHash, approver}`. Every manifest's "taint posture" below therefore describes what the kernel will compute, not what the agent asserts.
* **Restart safety.** Each spawn mints a hashed, revocable dispatch capability; a re-pointed or re-spawned task fences the prior worker, which then receives `consumer_fenced` and must not report done (Orca, SURVEY `orca.md`, `dispatch-capability.ts`). Liveness is three-valued (`live | unverifiable | exited`) and "absence never authorizes stop, abandon, retry, or release" (SURVEY `orca.md`). After a kernel restart the projection rebuilds from the log; a run with a live worktree and no terminator becomes `run.orphaned` and waits for a human or an idempotent resume key (Mastra's warning that blanket boot recovery re-issues paid calls, SURVEY `mastra-ai.md` `mastra/index.ts:614-629`). Resume references are trusted only from the kernel's own source, length-capped and deduped (herdr `agent_resume.rs`, SURVEY `herdr.md`).
* **Fan-out is all-or-nothing.** Best-of-k spawns k worktrees in one transaction; if any creation fails the already-created ones are killed so nothing is orphaned (CubeSandbox clone semantics, CONFIRMED `CubeSandbox/docs/guide/snapshot-rollback-clone.md:100`).
* **ESTOP.** `eng.pause` writes a sentinel; the dispatcher skips new spawns and new PR opens, in-flight runs are never killed, and a corrupt sentinel still counts as engaged (Hermes, CONFIRMED `hermes-agent/agent/estop.py:1-8`). `eng.resume` is a human control-plane action.

### 2.1 Tiers: isolation and capability are two axes

The starter ladder is an isolation ladder (T0 kernel-hosted, T1 process sandbox, T2 Docker `trusted` + proxy, T3 Docker `hostile` no egress). Phase 0's `agent.yaml` `tier: 0..3` is a capability ladder (D15: 0 no tools, 1 read-only MCP, 2 write + sandbox exec, 3 may request irreversible) (`plan §3.4`). The engineering fleet needs them separate: `tester` needs T3 hostile isolation (it executes freshly written code) while holding no tool that outlives its own disposable overlay; `sre` is T1 isolation yet must be able to *request* irreversible tools. DESIGN: keep `tier` as isolation and add `riskCeiling: read | write | irreversible` (the highest risk class the agent may request; the gate still sends `irreversible` and tainted writes to a human). This is kernel change K1 (§10) and open decision O1 (§11). Manifests below state both.

**A risk class is a property of (tool, domain, target), not of a tool name.** The first draft asserted `tester: riskCeiling read` while giving it `ws.exec` and `ws.test`, which K2 classifies `write` — a ceiling contradicted in the same paragraph is prose, not a gate (review finding F1). The gate resolves risk from a policy block in `tool-views.yaml`, evaluated by the kernel:

| Condition | Class | Rationale |
|---|---|---|
| `ws.exec` / `ws.test` in a `hostile` domain, no egress, overlay discarded at run end, worktree mounted read-only | `sandboxed-exec` (a `read`-ceiling class) | No effect survives the run; the only output is an exit code and an artifact hash |
| `ws.exec` / `ws.test` / `ws.edit` / `ws.commit` against a persisted worktree | `write` | The worktree survives and feeds integration |
| `ws.push` to `^aos/` | `write` | Kernel-namespaced branches, never protected |
| `ws.push` to any other ref, `git.tag` | `irreversible` | Reaches a shared remote |
| `pmmcp.remember` / goal writes inside the run's own `project_id` | `write-scoped` (a `write`-ceiling class bounded by `memory.projectId`) | Cannot reach another agent's memory or `aos/shared` |
| Anything unclassified | `kernel-only` | Invariant 7 |

`architect` is therefore `riskCeiling: write` with `writeScope: [pmmcp:aos/agent/architect, pmmcp:goals]` and no code-write tool in its view, rather than the first draft's `read` with a parenthetical exception. `tester` is `riskCeiling: read` and is *entitled to* `sandboxed-exec` only, which the kernel refuses to grant in any domain but `hostile`. The classes are data in `tool-views.yaml`, so a run cannot argue its way into one.

### 2.2 Tool interface first, org chart second

The largest measured per-feature gains come from the agent-computer interface, not from agent count: a dedicated editor +7.7 points, lint-on-edit +3.0, a 100-line viewer, filename-only search, an explicit empty-output message (SWE-agent ACI, SURVEY `landscape-coding-fleets.md` §5, §15), and a graph-ranked 1k-token repo map (Aider, SURVEY same §6). DESIGN: a kernel-hosted `repo` MCP server exposes exactly these over the run's worktree (`repo.map`, `repo.view` with a window, `repo.search` returning filenames, `repo.diff`, `repo.deps_diff`, `repo.log`), all `read` risk; and the in-sandbox `ws` server exposes `ws.edit` with lint-on-edit rejection and read-before-write (Mastra `requireReadBeforeWrite`, CONFIRMED `mastra-ai/packages/core/src/workspace/workspace-safety.test.ts:27-33`), `ws.exec` (all shell goes through the sandbox driver, never a "run locally" alternative, the CubeSandbox hook principle, CONFIRMED `CubeSandbox/docs/guide/integrations/claude-code.md:82,104`), `ws.test` (runs the repo's declared check commands), `ws.commit`. Each is one classified entry in `tool-views.yaml` (invariant 7). For local models the hub retrieves the top-K relevant tools over the *allowed* view per turn while the gate still enforces the full policy on execution (odysseus, CONFIRMED `odysseus/src/tool_index.py:5,31-35,296`). Keep the surface small on purpose: coordination cost grows disproportionately with tool count ("a coding agent with access to 16+ tools", SURVEY `landscape-coding-fleets.md` §15, arXiv 2512.08296), so a template's view is capped at 16 exposed tools and the cap is an eval-checked number, not a guideline.

**A run has two phases, and only the first one has a network.** Codex Cloud "provisions an isolated container ... and clones your repository into it, along with the dependencies you configured. Once the task starts, that container has no internet access"; setup scripts run with internet, the agent phase does not by default (SURVEY `landscape-coding-fleets.md` §3, https://developers.openai.com/codex/cloud/internet-access). DESIGN, and a correction to the first draft (review finding F2): a writing run is `setup` then `agent`.

* **Setup phase.** No model, no agent. The kernel runs the repo's *pinned profile* install command (`npm ci --ignore-scripts` for this repo class) with the proxy open to the registry hosts in the profile. Lifecycle scripts are disabled: the alternative is that unreviewed third-party package code executes inside a T2 container that still has egress, before any human has seen the dependency. Output is a `setup.result{lockfileHash, packagesAdded[], durationMs}` event.
* **Agent phase.** `egress.allow: []` for `tester` and every `implementer` profile. The container keeps `github.com` fetch only where a manifest names it, and `registry.npmjs.org` is *not* reachable from the agent phase at all. An agent that needs a dependency it does not have ends `block{needsDependency}`; the human resolves `dependency-ack` and the kernel re-runs the setup phase with the new lockfile. This replaces the first draft's O12 default (allow the install, gate at PR open), which let unvetted code run with network for the length of a 45-minute run.
* **Repo profiles are kernel config, not repository content.** The declared check, build and install commands for each target repo live in `config/repo-profiles.yaml` under the kernel's change control, pinned once by a human per repo. Target-repo `AGENTS.md` / `CLAUDE.md` / `package.json` scripts are *read-only input that may propose* a profile change; the proposal becomes an approval card, never an executed command (this closes O11: "they carry the real commands" cannot mean "the repo supplies the command line", since the repo is attacker-writable in the general case and Codex ships a `## Code Review Rules` injection surface of exactly this shape, SURVEY `landscape-coding-fleets.md` §3).
* **A tool failure is typed, never a string.** crewAI returns a structured `ToolFailure` from `_run` instead of an error string so "the framework now knows the call failed", with a per-tool `ToolFailurePolicy` of `IGNORE | WARN | RAISE` (CONFIRMED `crewAI/lib/crewai/src/crewai/tools/tool_failure.py:57-77`, `base_tool.py:188-194`). DESIGN: every kernel tool result carries `failure?: {reasonCode, message, retryable}`; the default policy is `WARN` (logged, run continues) and **`RAISE` is mandatory for every verification tool** (`ws.test`, the `verify.*` hooks, `evidence.get`). A `ws.test` that could not execute must abort the run, because under `WARN` the model is free to narrate the missing result as a pass.

### 2.3 Model routing in the sector

* Per-agent chains as data, bound only after `aos probe` reports `toolCalling: true`; a chain is a property of the manifest and is never inherited from the spawner (Hermes per-child bundle, SURVEY `hermes-agent.md` `_resolve_child_runtime`).
* A second binding slot `editorModel` on writing templates: the primary model proposes the change, a cheap or local model applies the diff; both calls are separate `llm.request`/`llm.response` pairs (Aider architect/editor 79.7% -> 85%, SURVEY `landscape-coding-fleets.md` §6). Kernel change K4.
* Named auxiliary lanes (`summarize`, `classify`, `embed`) bound to local llama.cpp/Bonsai independent of the agent's primary (Hermes `auxiliary.<task>`, SURVEY `hermes-agent.md`). Kernel change K4.
* A $0 deterministic tier before any model for structural transforms (ruflo Tier 1 codemods via the TypeScript compiler, CONFIRMED `ruflo/CLAUDE.md:95-105`), used by `implementer#refactor`.
* Fallback only before any tokens were streamed and always visible as a `model.fallback` event (odysseus `stream_llm_with_fallback`, SURVEY `odysseus.md`).
* Per-role model split proven in production: strong adviser/planner, cheap workers (PentAGI `AgentConfig` per role, SURVEY `pentagi.md` `pconfig/config.go:141-296`).
* **No price, no binding.** Anthropic's Managed Agents "budgets are rejected for models with no public list price" (SURVEY `landscape-agent-os.md` §8, CONFIRMED against its budgets page). DESIGN: the router refuses to bind any model ref that lacks a pricing entry in `providers.yaml`, including local ones, which must carry an explicit `pricing: {input: 0, output: 0, metered: false}` so a $0 binding is a deliberate statement rather than a missing field. A budget is not enforceable over an un-priced model, so an un-priced binding would silently void invariant 4's cost field and the objective ceiling at once.

All refs below other than `anthropic/claude-opus-5` are placeholders per CLAUDE.md ("Model ids in `config/providers.yaml` are placeholders except the Claude entry").

### 2.4 Budgets and caps (kernel-enforced, never prompt text)

Every leaf carries `budgetMicroUsd`, `wallclockMs`, `maxTurns`, `maxToolCalls`, `maxLlmCalls`; templates cannot raise them (invariant 6, ruflo `capability-envelope-cannot-grow`, CONFIRMED `ruflo/v3/@claude-flow/security/src/policy/envelope.ts:61-100`). Per-tool usage caps per run (`github.create_pull_request: 1`, `ws.push: 3`) follow crewAI `max_usage_count` (CONFIRMED `crewAI/lib/crewai/src/crewai/tools/base_tool.py:184,267-271`). Two consecutive spawn failures on one task auto-block it (Hermes `failure_limit` 2, CONFIRMED `kanban.md:126`). Two-tier tool-call caps by role (PentAGI: general 100, limited 20, CONFIRMED `pentagi/README.md:497`) are the defaults for writing versus read-only templates.

**A per-template cap is a ceiling, not an allocation, and the objective ceiling is enforced by reservation.** The first draft's numbers do not add up: an objective ceiling of $40 "including all children" against eight concurrent `implementer` runs at $6 each is $48 before the architect, testers and reviewers (review finding F3). Paperclip makes "task checkout and budget enforcement atomic" (SURVEY `landscape-agent-os.md` pattern 5) and Managed Agents enforce the cap "between model requests, not mid-request" with overshoot "bounded by one model request per thread" (same, §8). DESIGN:

* A spawn **reserves** the child's full `budgetMicroUsd` from the objective's remaining balance, in the same transaction that claims the lane. If the reservation does not fit, the spawn is refused with `spawn.refused{reasonCode: budget}` — the dispatcher queues the task rather than starting a run it cannot pay for.
* Unspent reservation returns to the objective on `run.finished`. Ceilings may therefore sum above the objective total; only reservations may not.
* Within a run, the kernel pre-reserves the next request's worst-case cost between model requests so the ceiling is never crossed (SURVEY `landscape-agent-os.md` anti-pattern 7), and the 50/75/90/100 ladder with a hard stop still applies to the objective (ruflo cost tracker, SURVEY `ruflo.md`).

**Concurrency is admitted against memory, not counted.** `maxChildren: 8` concurrent T2 containers is not runnable on the target machine (review finding F4): 64 GB total, with CLAUDE.md's local-model budget of ~40 GB for weights plus KV, two Colima VMs, Qdrant and Ollama all drawing on the same pool. A Node build container with a dev server is 1.5-3 GB and Chromium adds roughly 1-1.5 GB, so eight of them plus a `hostile` tester is 15-25 GB in the VMs alone and the local `editorModel` starves. DESIGN: `maxChildren: 8` becomes a *per-objective lifetime* cap; concurrency is a separate `maxConcurrent: 3` (default) and admission is by a declared `sandbox.memoryMb` per template summed against `kernel.yaml sandbox.domains.<d>.memoryBudgetMb` — an admission controller in the spawn path, refusing with `spawn.refused{reasonCode: capacity}` and queueing. Per-resource queues with their own concurrency and time slice also apply per provider and per MCP server (AIOS `RRScheduler`, SURVEY `landscape-agent-os.md` pattern 17), so three concurrent Opus-bound implementers do not collide on one provider lane. The operator can raise `maxConcurrent` only by raising a memory budget, which is the honest knob.

### 2.5 The approval budget: one operator, a countable number of decisions

A gate the operator rubber-stamps is worse than no gate, because the log then records consent that was never given. The first draft never counted its own demand (review finding F5). Worst case per objective under §5.1: `plan.approve` (1, conditional) + out-of-allowlist `ws.exec` (0-n) + `dependency-ack` (0-1) + PR open (1, always) + merge (1, irreversible) + `block`-as-question (0-n) = **3-4 typical, more on a bad day**. At four objectives a day that is 12-16 engineering decisions, before `release` (3 per cut), `sre` (one per deploy and per migration) and the other four sectors. DESIGN, four kernel-enforced dampers, none of which removes a human from an `irreversible` action:

1. **Backpressure, not a queue.** `eng-lead` may hold at most `maxOpenApprovals: 3`. Beyond that the dispatcher stops spawning work that would need a fourth. The fleet slows to the operator's review rate instead of building a backlog the operator clears by clicking.
2. **Expiry is fail-closed.** Every approval card carries a TTL (default 24 h, 2 h for `question`). Expiry resolves to **deny** and interrupts the waiting run, the secure-openclaw envelope shape with the correct default (120 s timeout resolves to deny with `interrupt: true`, SURVEY `secure-openclaw.md` best part 1 / `gateway.js:125-150`) — scaled to human hours, not chat seconds. A stale card never becomes a silent allow.
3. **One card per decision point, with everything attached.** The PR-open card carries the full evidence bundle (§5.1 step 9) so the decision costs one read, not five. The approval record itself is durable and self-describing — who, what, when, from where, and an explicit agreement field — the shape agency-os uses for proposal acceptance (`os_proposal_approvals{signature_text, esignature_agreement, ip_address, metadata}`, SURVEY `agency-os.md` best part 3), so the approvals projection replays from the log without re-deriving intent.
4. **Remove recurring sources rather than auto-allowing them.** Exec approvals recur because commands are not pinned; pinning them once per repo in `config/repo-profiles.yaml` (§2.2) is a human, change-controlled act that removes a class of cards without growing an agent-side allowlist — which is precisely the eliza `allow-always` anti-pattern we reject (SURVEY `eliza.md` bad part 3).

What we deliberately do **not** do in Phase 1-2: a standing mandate that lets the fleet open PRs without a card. Open decision O13 records the argument and the conditions under which it could be revisited; the default stays `approval: always`.

## 3. Agent manifests (prose)

Field order is fixed: id · kind · role and responsibilities · tier / riskCeiling · tool-view exposure · egress allowlist · model priority chain · taint posture · budget caps · approval preconditions (named irreversible actions) · KPIs / evals · soul summary · phase introduced. Money is integer micro-USD (`plan §3.4` D4); dollar figures are shown for readability and are open decision O7.

### 3.1 `eng-lead` (persistent)

* **kind** standard, `role: orchestrator` within the sector; the only engineering agent with `spawn`.
* **role and responsibilities** Owns one engineering objective per run: converts the CEO's brief into a pmmcp goal tree (objective -> milestones -> tasks, `auto_resume` off), decides whether a task is "single-file fix" (no architect) or needs an `architect` plan (ruflo complexity rule: swarm only for 3+ files, features, cross-module, API/schema/security/perf changes, CONFIRMED `ruflo/CLAUDE.md:341`), spawns leaves, owns the integration lane (rebase task branches onto `aos/int/<objective>`, re-run `tester` on merged state, kernel-side push), files the PR-open approval with evidence attached, handles `request_changes` routing back to the original implementer (Hermes same-card review, CONFIRMED `kanban-worker-lanes.md:89`), and updates task goal status on every run start/finish (Phase 1 exit criterion). It never edits code outside the integration worktree and never resolves a blocked worker's question itself: a `block` becomes `approval.requested{kind:question}` for the human (herdr "refuse to type into a blocked agent", SURVEY `herdr.md`). It may only *file* promotion or budget-raise requests.
* **tier / riskCeiling** T2 `trusted` (needs `ws.exec` for `git rebase`, `npm test` on the integration worktree) / `write`. Merge and protected-branch push are `irreversible` and therefore human even though its ceiling is `write`.
* **tool-view exposure** `pmmcp`: `recall`, `remember` (own namespace `aos/agent/eng-lead`, write), goal tools (typed wrappers from Phase 1; create/update task status = write), no secret/admin tools (kernel-only by invariant 7). `repo.*` read. `ws.exec` (write, in-sandbox), `ws.test` (write, in-sandbox), `ws.commit` (write), `ws.push` (write when target matches `^aos/`; `irreversible` otherwise; executed kernel-side with the broker's token, the container has no push credential). `github`: `pull_request_read`, `list_pull_requests`, `get_check_run`, `list_commits`, `search_issues`, `issue_read` (read); `create_pull_request` (write, `approval: always`, preconditions P1-P6 in §6); `update_pull_request`, `add_issue_comment` (write); `merge_pull_request`, `enable_pr_auto_merge` (`irreversible`); `push_files`, `create_or_update_file`, `delete_file` (`kernel-only`: they bypass worktree discipline); `request_copilot_review` (`disabled`: an external LLM call outside the router and log, invariant 7 rationale). Spawn: templates `scout, architect, implementer{code|docs|refactor}, tester, reviewer{code|security}, release`, `maxChildren: 8` per objective lifetime, `maxConcurrent: 3`, `maxDepth: 1`, `maxOpenApprovals: 3`. Tool names above are the GitHub MCP server's as visible in this session (INFERRED for exact spelling; Phase 2 pins them by schema hash, and a mid-run hash drift fails closed per §2).
* **egress allowlist** Setup phase only: `registry.npmjs.org` for the pinned `npm ci --ignore-scripts`. Agent phase: `github.com` git fetch of the target repo only, with a read-scoped token injected at the proxy edge; `git-receive-pack` blocked at the proxy so a push cannot originate inside the container. Everything else denied; every decision a `proxy.decision` event. Credential substitution is **outbound only**, so any endpoint that returns a bearer token in its response body is banned from every allowlist in this sector: Managed Agents documents exactly this hole ("Substitution is outbound only" so exchange flows leak the returned token, SURVEY `landscape-agent-os.md` §8 and pattern 6). Concretely: no OAuth token or device-code endpoint, no `/login/oauth/access_token`, no STS or client-credential exchange, on any host, for any agent in this sector. A proxy rule denies them by path as well as by host.
* **model priority chain** primary `anthropic/claude-opus-5` for planning/exception turns; fallback `anthropic/<sonnet-class>` (placeholder); `aux.summarize` -> `local/bonsai` (llama.cpp `localhost:8080/v1`). Bound only after `aos probe`.
* **taint posture** Clean by default; kernel-computed, not self-declared (§2). Any delegated result from a tainted leaf (a scout that fetched the web, a repro built from an untrusted bug report) taints the objective's writes until a human releases the quarantine hold; `eng-lead` can still read and plan while tainted (invariant 3: tainted runs cannot use `write` tools without a human).
* **budget caps** Objective ceiling 40 000 000 micro-USD ($40) including all children, enforced by reservation at spawn (§2.4) rather than by summing per-template ceilings; 8 h objective wallclock; `eng-lead` own turns `maxTurns: 80`, `maxToolCalls: 200`; round-trip cap 32 per objective; `maxChildren: 8` per objective lifetime with `maxConcurrent: 3`; spawn refused above any cap, above the domain memory budget, or above `maxOpenApprovals`.
* **approval preconditions** `github.create_pull_request` (always, with evidence); `github.merge_pull_request` (irreversible); `ws.push` to a protected branch (irreversible); `plan.approve` when objective budget > threshold or the plan touches protected paths, deps, migrations, CI config (§6); `dependency-ack` when `verify.deps` reports an added dependency (CLAUDE.md change control); `lease.exclusive` for an `implementer#refactor` spawn; `test-removal-ack` when `verify.testdiff` fires; budget-raise requests. All resolve only by a `HumanActor` via the control plane.

* **soul summary** A calm integration owner who writes complete briefs, trusts evidence over reports, and never answers a question that was meant for the human. Treats a perfect self-report as a red flag. Keeps the plan small: one PR per task, one owner per file set, stop before the budget does.
* **phase introduced** Phase 1 (kernel delegation, goal tree, restart-safe projections); PR opening in Phase 2.

### 3.2 `architect` (ephemeral template, pinned namespace)

* **kind** ephemeral-template, `role: worker` (no spawn). Demoted from persistent in this revision (review finding F8): persistence in this kernel buys a versioned manifest with `history/`, a `schedule:` entry, and a pinned pmmcp namespace. `architect` is spawned per objective by `eng-lead`, never scheduled, and only needs the namespace, which a spawn spec can pin (`memory.projectId: aos/agent/architect`, read-write, narrowable only). Shipping it as a persistent agent bought a manifest-versioning ceremony for a run that lasts thirty minutes.
* **role and responsibilities** Plan-only. Reads the repo map, scout findings and the acceptance criteria; writes a plan artifact: milestone/task decomposition with per-task ownership path sets, dependency levels (L0 architecture, L1 implement + test, L2 review, L3 optimize, ruflo, CONFIRMED `ruflo/CLAUDE.md:230`), acceptance tests named per task, `codemodFirst` analysis (what is deterministic), a "when NOT to fan out" verdict, and a risk register naming every irreversible touch (migration, CI, deps). It asks before answering when the brief is ambiguous (ChatDev communicative dehallucination, SURVEY `landscape-coding-fleets.md` §11) by ending with `block{question}`. **Spec-quality triage runs before it, not inside it**: a kernel-scored rubric on the incoming brief (acceptance test named? files or symbols identified? reproduction available? out-of-scope stated?) decides the route, so "well-specified issues proceed directly to parallel repair and validation, while ambiguous issues first invoke repository exploration" (icat-agent, SURVEY `landscape-coding-fleets.md` §15, arXiv 2606.25514). A brief that scores well skips both `scout` and `architect` and goes straight to one `implementer`; a brief that scores badly buys `scout` first and `architect` second. This is the cheapest lever in the sector because it is the one that does not spend tokens.

**Shared implicit decisions are the architect's output, not an emergent property.** Cognition's Flappy Bird case is two subagents producing a mismatched background and sprite because neither saw the other's implicit style decision, and its prescription is that "writes stay single-threaded" (SURVEY `landscape-coding-fleets.md` §4). We run parallel implementers anyway, so the mitigation has to be structural: every parallel task set carries a `decisions` block in the plan artifact — interfaces, types, naming, style tokens, error shapes — pinned as text that the kernel injects verbatim into every sibling's brief. A task set whose members would have to invent a shared decision is not parallelizable and the architect must serialize it or hoist the decision into an L0 task. The eval that catches a regression here is the integration-lane `tester` re-run on the merged state (§5.1 step 8), which is why it is not optional. It keeps ADRs and module maps in `aos/agent/architect` so the next objective starts from memory, not a re-brief.
* **tier / riskCeiling** T1 / `write` with `writeScope: [pmmcp:aos/agent/architect, pmmcp:goals]` (§2.1). It holds no tool that can touch a file, a remote or a container; the ceiling says `write` because its pmmcp and goal writes really are writes, rather than the first draft's `read` with a parenthetical exception (review finding F1).
* **tool-view exposure** `repo.*` read; `pmmcp.recall`/`remember` own namespace; goal create/update (`write-scoped`). No `ws.*`, no `github` writes, no spawn. Plan mode is the gate's read-only allowlist, not a prompt (odysseus `PLAN_MODE_READONLY_TOOLS`, SURVEY `odysseus.md`).
* **egress allowlist** none (T1, hub-mediated only).
* **model priority chain** `anthropic/claude-opus-5` -> `openrouter/<frontier-reasoner>` (placeholder). Reasoning effort high; no editor model (it edits nothing).
* **taint posture** Clean; reads tainted scout output only through quarantine release.
* **budget caps** 8 000 000 micro-USD ($8), 30 min wallclock, `maxTurns: 40`, `maxToolCalls: 60` (limited-agent cap class).
* **approval preconditions** Its plan is subject to `plan.approve` (human) when: objective budget > `kernel.yaml eng.planApprovalAboveMicroUsd` (default $10), or the plan touches protected paths, dependencies, schema migrations, CI, release or deploy; else the kernel proceeds and logs `plan.accepted{auto:true}`. Never irreversible itself.
* **KPIs / evals** Plan acceptance rate by the human without edits; rework ratio (tasks re-planned after `verify.result` fail); fan-out discipline (tasks per plan ≤ 6-8, ruflo `Keep maxAgents at 6-8 for tight coordination`, CONFIRMED `ruflo/CLAUDE.md:113`); replayed trajectory conformance on recorded plans (ADK-style, SURVEY `landscape-agent-os.md` §6).
* **soul summary** A senior architect who names the smallest change that satisfies the acceptance test, owns one file set per worker, and writes down why. Refuses to plan against a vague brief: asks one precise question instead.
* **phase introduced** Phase 1.

### 3.7 `tester` (ephemeral template)

* **kind** ephemeral-template.
* **role and responsibilities** The only path to "tests passed" in the log. Mounts a finished worktree read-only plus a writable tmp overlay, runs the **pinned profile's** check commands (for this repo: `npm run typecheck && npm test`), runs the acceptance/reproduction test named in the brief, optionally replays a browser acceptance script against a built prototype, and emits a typed `verify.result{pass|fail, checks[], reproductions[], artifactHash, degradedPaths[], testDelta}`.
* **A green exit code from code the implementer just wrote is not proof.** The first draft claimed the tester's verdict "cannot be tainted into a false pass because the verdict is computed from exit codes, not model text". That is false as stated and it sits under the load-bearing claim of the whole sector (review finding F6). Three ways a pass is forged and the three structural answers:
  1. *The command is changed.* Answer: check commands come from `config/repo-profiles.yaml` (kernel config, §2.2), pinned by a human, never from the head commit's `package.json` scripts or `AGENTS.md`. A diff that changes a script the profile names is a hard gate, not an input.
  2. *The tests are weakened.* Answer: `verify.testdiff` is a deterministic kernel hook computing `testDelta{filesChanged[], testsRemoved, testsSkipped, assertionsRemoved, coverageDelta}` over the base-to-head range against the pinned test globs. Any removal, `.skip`, `.only`, or negative assertion delta is a **hard block** on PR-open requiring an explicit human `test-removal-ack`, and it is rendered on the approval card as its own line. "Tests pass" and "the same tests pass" are different claims and only the second one is evidence.
  3. *The test process is subverted at runtime* (a `postinstall`, a test-time network call, a monkey-patched assertion library). Answer: the tester runs in `hostile` with no egress and an overlay discarded at exit, dependencies come from the setup phase with `--ignore-scripts`, and the run's own `proxy.decision` list (empty by construction) is attached to the verdict. A non-empty list in a `hostile` run is an incident, not a warning.
 Residual risk is real and named: a sufficiently clever in-repo change can still make a pinned command exit 0 with weaker semantics. That is what the security reviewer soul and the human's diff read are for, and it is why `verify.result` is a *precondition* for the PR-open card rather than a substitute for it. In best-of-k it runs every candidate and ranks by outcome (Agentless regression + reproduction rerank, SURVEY `landscape-coding-fleets.md` §12). It has no LLM turn in the default profile; an optional `analyze` capability lets a cheap model summarize failures for the reviewer. Every degraded path (a skipped check, a missing fixture) is an event, never silent (claude-video's silent-degradation lesson, SURVEY `claude-video.md` bad part 5).
* **tier / riskCeiling** T3 `hostile` (executes freshly written, possibly injected code; no egress) / `read`, entitled to the `sandboxed-exec` class only (§2.1) — which the kernel grants in no domain but `hostile`, with the worktree mounted read-only and the overlay discarded at exit.
* **tool-view exposure** `ws.test` and `ws.exec`, both `sandboxed-exec`, restricted to the check commands in the repo's pinned profile plus the brief's reproduction command; anything else denied. `repo.diff` read; `browser.*` read/act only when the `browser` capability is in the spawn spec and only against `localhost` inside the container. No `pmmcp` writes; results go to the log.
* **egress allowlist** none, enforced by the `hostile` domain's internal network; dependencies must already be present in the worktree (installed by the implementer in T2) or the image.
* **model priority chain** none by default; `analyze` capability: `local/<qwen-coder-class>` -> `anthropic/<haiku-class>`.
* **taint posture** Inherits the worktree's taint. Its verdict is derived from exit codes rather than model text, which removes one forgery path (the model narrating a pass) but not the three above; treat the verdict as strong evidence about the pinned command, not as proof about the change.
* **budget caps** 1 000 000 micro-USD ($1, mostly zero), 20 min wallclock (30 min for browser replays), `maxToolCalls: 20`, idle timeout additive to the wallclock, kill always wins over pause (CubeSandbox lifecycle, CONFIRMED `CubeSandbox/docs/guide/lifecycle.md:17,22`).
* **approval preconditions** none; it can neither write nor reach the network.
* **KPIs / evals** Agreement between `verify.result` and the human's eventual merge decision; flake rate (a flaky check is deleted or fixed, never retried into green, prime-agent test policy, SURVEY `prime-agent.md`); reproduction-test discriminative power on the fixed task set.
* **soul summary** (for the `analyze` capability only) A terse test engineer who quotes the failing assertion and the exit code and offers no opinion about the code's intent.
* **phase introduced** Phase 1 with the fake sandbox and a `trusted` domain; `hostile` domain in Phase 2.

### 3.8 `reviewer` (ephemeral template; souls `reviewer-code`, `reviewer-security`)

* **kind** ephemeral-template. The starter roster's `checker` is folded here for engineering: `tester` is the execution verifier, `reviewer` is the execution-free verifier; both feed the human gate with independent evidence because each alone saturates (R2E-Gym hybrid verifier, INFERRED via SURVEY `landscape-coding-fleets.md` §15).
* **role and responsibilities** A fresh-context reviewer that sees only the diff, the acceptance criteria, the `verify.result` and the hook results, never the reasoning that produced the change (Claude Code adversarial reviewer, SURVEY `landscape-coding-fleets.md` §1). Returns a typed verdict `approve | request_changes | block` with findings `{file, line, severity, evidence, fix}`; a review-only terminator authorizes synthesis of findings, never edits (Orca review ownership, SURVEY `orca.md`). The `reviewer-security` soul additionally reads `repo.deps_diff`, the `verify.secrets` and `verify.witness` results, and the proxy-decision summary for the run (which hosts new code contacts). Evidence-over-claims doctrine: default verdict NEEDS WORK, perfect prior scores are a red flag, inconclusive evidence is FAIL (agency-agents reality-checker, CONFIRMED `agency-agents/testing/testing-reality-checker.md:25,43,48`), tempered by the documented reviewer bias ("a reviewer prompted to find gaps will usually report some", SURVEY `landscape-coding-fleets.md` §1): findings must cite a line and a consequence or they are dropped by the kernel's schema.
* **tier / riskCeiling** T1 / `read`.
* **tool-view exposure** `repo.diff`, `repo.view`, `repo.search`, `repo.deps_diff`, `repo.log` (read); read access to `verify.*`, `tool.hook` and `proxy.decision` events via a kernel-hosted `evidence.get` read tool — **scoped by the kernel to the objective under review and to those three event kinds**, redacted like any other log read, never a general `events.query` primitive (an agent that can read the log can read another objective's approval arguments and another agent's tool inputs); `pmmcp.recall` over `aos/shared` (coding standards, prior findings). No `ws.*`, no `github`, no writes.
* **egress allowlist** none.
* **model priority chain** `anthropic/claude-opus-5` for `reviewer-security`; `anthropic/<sonnet-class>` -> `openrouter/<frontier-coder>` for `reviewer-code`; a second, different model family as fallback is preferred to diversify bias (open decision O8).
* **taint posture** Inherits the diff's taint; a tainted verdict is still advisory-only and cannot be laundered into an approval.
* **budget caps** 1 500 000 micro-USD ($1.50), 10 min, `maxTurns: 15`, `maxToolCalls: 20` (limited class), `minEvidenceCalls: 2` (must read the diff and the verify result before a verdict; MiroFish minimum-evidence gate, SURVEY `MiroFish.md`).
* **approval preconditions** none; its verdict is an input to the human's PR-open decision and never the decision.
* **KPIs / evals** Precision of findings (human accept rate), false-positive rate, catch rate on seeded defects and seeded secrets/invariant-guard deletions in a fixture repo; disagreement rate between the two souls.
* **soul summary** `reviewer-code`: a skeptical peer who reads the diff cold, wants a failing test for every fix, and writes findings someone can act on. `reviewer-security`: assumes the diff may be adversarial, hunts for widened reach (new hosts, new deps, deleted guards, secrets) and refuses to certify what it cannot see.
* **phase introduced** Phase 1.

### 3.9 `implementer#docs` (profile of §3.6, was a separate `docs-writer` template)

* **kind** profile on the `implementer` template. Its distinguishing fields — a local-first model chain and an ownership set of `docs/**`, `README.md`, `CHANGELOG.md`, ADRs — are exactly what `profiles:` expresses, so it no longer needs a manifest, a soul file and an eval suite of its own (review finding F9). The tool surface is `implementer`'s, narrowed.
* **role and responsibilities** Writes and updates documentation from a merged or pending diff plus the plan artifact; runs the docs build or link check via `ws.test`; produces changelog entries from conventional commits (deterministic extraction first, prose second). Never edits code paths; `verify.ownership` denies it.
* **tier / riskCeiling** T2 `trusted` / `write`.
* **tool-view exposure** `repo.*` read; `ws.edit`, `ws.test`, `ws.commit` write within `docs/**` and named files; `pmmcp.recall` over `aos/shared`; no `ws.exec` beyond the declared docs scripts; no `github`.
* **egress allowlist** none (`egress.allow: []`; docs builds must not fetch).

* **KPIs / evals** Link-check and build pass rate; human edit distance on accepted docs; local-model share of successful runs.
* **soul summary** A precise technical writer who documents what the code does, not what the plan hoped, and links every claim to a file.
* **phase introduced** Phase 1.

### 3.10 `implementer#refactor` (profile of §3.6, was a separate `refactorer` template)

* **kind** profile on the `implementer` template, carrying its own `gate` block (mandatory `plan.approve`, `lease.exclusive`) and the extra `ws.codemod` verb. The gate posture is the reason it is a named profile rather than a free-form spawn; it is not a reason for a second manifest.
* **role and responsibilities** Cross-cutting refactors and mechanical migrations that legitimately touch many ownership sets: codemod first (deterministic transform scripts using the target repo's own TypeScript toolchain, output logged as an artifact, $0 tier), then model-proposed edits applied by the editor model, then the full suite via `tester`. It runs only under an exclusive repo lease: the kernel refuses to spawn it while any other writer run is live on the repo and refuses other writers while it runs. Its worktree starts from the integration tip. Database schema migrations are written here or by an implementer but never applied; `supabase.apply_migration` belongs to `sre` and a human.
* **tier / riskCeiling** T2 `trusted` / `write`.
* **tool-view exposure** as `implementer` plus `ws.codemod` (write; runs a named transform script from the repo, never free-form) and ownership `**` under the lease; still no `github`, no push, no lockfile edits (the integration owner reconciles lockfiles).
* **egress allowlist** Agent phase: none. Codemod transforms and edits need no network; the setup phase already installed from the pinned lockfile.
* **model priority chain** `anthropic/claude-opus-5` (proposer) with `editorModel: local/bonsai` -> `anthropic/<haiku-class>`; codemod tier before either.
* **taint posture** Clean; refactors never consume external text.
* **budget caps** 15 000 000 micro-USD ($15), 90 min, `maxTurns: 100`, `maxToolCalls: 200`, `maxLlmCalls: 120`.
* **approval preconditions** `plan.approve` is mandatory (no auto-accept path for refactors); `lease.exclusive` approval names the repo and the expected duration; witness markers (`verify.witness`) must all be intact before the PR-open approval is even filed.
* **KPIs / evals** Behaviour-preserving pass rate (full suite green, witness markers intact, no API surface change unless planned); codemod share of the diff (higher is cheaper and safer); rework ratio.
* **soul summary** A methodical migrator who prefers a transform script to a hundred hand edits, proves preservation with the full suite, and stops the moment a guard line disappears.
* **phase introduced** Phase 2 (needs witness manifests and the exclusive-lease kernel change).

### 4.1 The kernel's own repository is a special target, and it is the first one

The first draft never named the case it will meet on day one: this fleet's first customer is `aos-kernel` itself (review finding F7, a blocker). When `implementer#code` works on this repo, its worktree contains `src/policy/gate.ts`, `src/events/chain.ts`, `src/secrets/broker.ts`, `config/tool-views.yaml`, `souls/`, `agents/*/AGENTS.md` and the witness manifest — that is, the code and data that define the gate the run is passing through. `verify.protected_paths` and `verify.witness` cover part of this by accident; the case deserves to be explicit policy.

DESIGN: `config/repo-profiles.yaml` carries `class: self | external` per repo. For `class: self`:

* **The running kernel never reads configuration, policy or souls from a worktree under its own management.** Config is loaded from the installed tree at boot and pinned by `policyVersion` (§2); a worktree copy is source under edit, never live policy. Without this rule an `implementer` editing `config/tool-views.yaml` could widen the view of a run that is still in flight.
* **A change under `src/policy/**`, `src/events/**` (chain, redaction, immutability triggers), `src/secrets/**`, `src/sandbox/**`, `config/tool-views.yaml`, `souls/**`, `agents/**/AGENTS.md`, or the witness manifest is `irreversible`-class** for approval purposes even though the mechanical act is a file edit: it requires `plan.approve` before the work starts *and* a human line-by-line diff read at PR open, and it is never eligible for any batching, mandate or auto-accept path that exists now or later. This is CLAUDE.md's change-control list ("touching redaction, chain hashing, or the immutability triggers"; "anything that widens what an agent can reach") expressed as a gate the fleet cannot route around.
* **Deleting or weakening a test that guards an invariant is a separate hard block** from ordinary `verify.testdiff`: the witness manifest names the invariant tests by path, and their removal is denied at edit time, not flagged at review time.
* **The fleet never restarts, reinstalls or deploys the kernel it just edited.** `aos` process lifecycle is not a tool in any manifest in this sector. The operator restarts the daemon; the log then shows an operator action between the merge and the new binary, which is what makes a self-modification auditable at all.
* **The eval harness runs against the installed kernel, not the candidate**, so a candidate that breaks the gate cannot also grade itself.

## 5. Workflows

### 5.1 Issue -> merged PR

1. Operator: `run.start{agentId: ceo, input: "fix #123 ...", goalId}`. CEO delegates the objective to `eng-lead` with a self-contained brief; events `run.queued/started{eng-lead}`, goal `objective -> in_progress`.
1b. **Spec-quality triage (kernel, no model).** The rubric in §3.2 scores the brief. A well-specified brief skips steps 2 and 3 entirely and goes to one `implementer`; an ambiguous one buys exploration first (icat-agent, SURVEY `landscape-coding-fleets.md` §15). The score and the route are a `plan.routed{score, route, reasons[]}` event, so the eval harness can measure how often the cheap route was right.
2. `eng-lead` spawns `scout` x N for localization (files -> symbols -> edit points); `run.finished{complete, evidence: file:line list}`. Complexity rule: single-file fix skips step 3.
3. `eng-lead` spawns `architect`; it writes the plan into the pmmcp goal tree (tasks with ownership sets, acceptance tests, levels) and ends `complete{planId}`; event `plan.proposed`. Kernel policy: `plan.approve` required if budget > threshold or the plan touches deps/migrations/CI/protected paths; the human approves in the control plane (`approval.resolved{kind: plan}`), else `plan.accepted{auto: true}`.
4. Kernel workflow creates one worktree per L1 task (`worktree.created{path, branch: aos/task/<id>}`), runs the **setup phase** per worktree (pinned `npm ci --ignore-scripts` with registry egress, `setup.result`), then spawns `implementer` per task with `egress.allow: []`, up to `maxConcurrent: 3` and only as far as the objective's budget reservations and the domain memory budget allow (best-of-k for tasks flagged hard: k worktrees in one all-or-nothing batch). Each implementer: read -> edit (lint-on-edit) -> `ws.test` -> commit -> `request_review{evidence}`. `verify.ownership` denies out-of-set edits as `tool.hook{blocked, reason}`. The kernel commits a **checkpoint** after each accepted `ws.edit` — a commit on a shadow ref (`refs/aos/ckpt/<runId>`), not on the task branch — so a run that goes wrong can be rewound to a known state by the operator or retried from a mid-point instead of from zero (Cline shadow-git checkpoints: "a shadow Git repository separate from your project's actual Git history ... After each tool use, Cline commits the current state", with its own documented caveat that on large codebases this "may use significant storage and slow down" the agent, SURVEY `landscape-coding-fleets.md` §8). The caveat is why checkpoints are per-run shadow refs with a retention of `objective + 7 days`, off by default for repos over a size threshold in the profile.
5. Kernel spawns `tester` (T3) on each candidate worktree: declared checks + reproduction test -> `verify.result`. Best-of-k: the passing candidate with the smallest diff wins; losing branches are kept, their checkouts removed (`worktree.removed{branchKept: true}`).
6. Deterministic hooks on the winner: `verify.secrets` (secret patterns and known token shapes), `verify.deps` (lockfile/manifest diff -> `dependency-ack` needed), `verify.testdiff` (tests removed/skipped/weakened -> hard block + `test-removal-ack`), `verify.witness` (invariant marker manifest intact: loopback bind, `--cap-drop=ALL`, immutability triggers, kernel-only defaults; ruflo witness, CONFIRMED `ruflo/verification/README.md:16-18`), `verify.protected_paths`. Each is a `tool.hook` event with `decision, matchedRule, reasonCode`.
7. Kernel spawns `reviewer` twice (souls code and security), fresh context, diff + criteria + `verify.result` only -> typed verdicts. `request_changes` routes once back to the original implementer (same worktree, same dispatch capability generation +1); two consecutive failures auto-block the task and file a `question` approval for the human.
8. `eng-lead` integration lane: rebase task branch onto `aos/int/<objective>`, re-run `tester` on the merged state, kernel-side `ws.push` (write, `aos/*` only).
9. `github.create_pull_request` (approval: always). The approval card carries: diff stat, `verify.result`, both reviewer verdicts, hook results, `dependency-ack` status, proxy-decision summary, cost to date, `argsHash`. Human approves -> PR opened -> `pr.bound{url}` (first URL binds permanently; retries cannot substitute a sibling PR, CONFIRMED `kanban.md:56`). CI status is read through `get_check_run` until required checks are green against branch protection.
10. `github.merge_pull_request` (irreversible) -> human -> `run.finished{eng-lead, complete}`; goal task -> `done`; worktree removed, branch kept; CEO receives the terminal event and a summary with evidence pointers. Chain verified after the run in tests.

Failure branches: `block` -> `approval.requested{kind: question}` (a sibling may never answer it); crash -> dispatcher reclaims by PID + spawn fingerprint and dispatch generation, respawns at most `failure_limit` times; kernel restart -> projections rebuilt from the log, live-worktree runs without terminators -> `run.orphaned`; `eng.pause` -> no new spawns or PR opens, in-flight untouched.

### 5.2 Design brief -> prototype demo PR

1. Operator or CEO brief (design intent, acceptance screenshots, operator-provided assets in the workspace) -> `eng-lead` -> spawn `prototyper` (persistent agent run, T2). Web references, if any, come from a tainted `scout` whose output the human releases from quarantine first.
2. `prototyper` scaffolds/edits in its worktree, starts the dev server inside the container (`ws.exec`), loops `browser.snapshot -> act -> re-snapshot` DOM-first with vision fallback, bounded at 40 actions; each act result event carries a verification class; Design Mode picks feed defect fixes; screenshots are artifacts (`environment_input` events by hash, perceptual dedup).
3. Terminator `request_review{screenshots[], verifiedRatio}`.
4. `tester` (T3, `browser` capability) builds and replays the acceptance script; unverified actions cannot count as pass; `verify.result` includes screenshot diffs.
5. `reviewer` (code soul, plus an a11y/UX rubric variant if the operator adds one) -> advisory verdict.
6. `github.create_pull_request` (approval: always; gate precondition `draft: true` and label `prototype`), human approves; the PR is never merged by this flow. Hardening becomes a new objective through 5.1 with `implementer` runs that own the same paths.

### 5.3 Cross-cutting refactor or migration

1. Brief -> `architect` plan with `codemodFirst` analysis; `plan.approve` is mandatory.
2. Kernel acquires `lease.acquired{repo, exclusive, ttl}` after a human approves `lease.exclusive`; new writer spawns on the repo are refused until release; in-flight writers finish or the human kills them.
3. `implementer#refactor` (T2) in a fresh worktree from the integration tip: codemod artifacts logged, then proposer/editor edits (two LLM pairs per change), `ws.test`, commit, `request_review`.
4. `tester` full suite (T3); `verify.witness` must be fully intact; `verify.deps`.
5. `reviewer` x2; integration; PR open (always) -> merge (irreversible, human) -> `lease.released`.
6. If the change includes a DB migration file: the PR merges the file only; `sre` later requests `supabase.apply_migration` (irreversible) with the plan approval and rollback SQL attached (5.4).

### 5.4 Release cut -> deploy -> reconcile

1. Operator: "cut v0.2.0". `eng-lead` spawns `release`: version computed, notes drafted, tag candidate built and passed through `tester`.
2. Three irreversible approvals in order, each with an idempotency key minted before the prompt: `git.tag` push, `github.create_release`, `npm.publish` (kernel-side through the proxy, token at the edge). Any denial stops the sequence; a partial sequence is a logged, resumable state, not a retry.
3. `sre` proposes `vercel.deploy` with the rollback plan; human approves; `ops.deployed`.
4. Scheduled `sre` `reconcile` runs (read-only, tainted) compare declared versus live state and health; `ops.drift` events; on a bad signal `sre` proposes `rollback` (irreversible). `ops.halted` (human-set sentinel) blocks further deploys; nothing auto-flattens.

## 7. Context management

* **Condense the view, never the log.** A `context.condensed{forgottenEventIds[], summaryRef, summaryOffset}` event records each compaction; the run's LLM view is the event list minus forgotten ids plus the summary; the condenser's calls are billed under their own usage id (OpenHands, CONFIRMED `OpenHands/src/types/agent-server/core/events/condensation-event.ts:16,26`).
* **Masking before summarization.** Default strategy is observation masking (old tool outputs replaced by a stub in the prompt), which halves cost and matches LLM summarization on SWE-bench Verified (The Complexity Trap, INFERRED via SURVEY `landscape-coding-fleets.md` §15); LLM summarization is opt-in per manifest. Prompt-side filtering is transient and stored history keeps the full tool parts (Mastra `ToolCallFilter`, CONFIRMED `mastra-ai/packages/core/src/processors/processors/tool-call-filter.ts:18-32`).
* **Bounded observations.** `repo.view` returns a window; `repo.search` returns filenames; empty output is an explicit message; tool results over `MAX_LOGGED_OUTPUT` become artifacts with hashes.
* **Summary-only delegation.** Leaves return typed results; their transcripts never enter `eng-lead`'s context; the CEO receives only terminal events.
* **Repo map.** A kernel-generated, graph-ranked map capped at ~1k tokens by default, expanded when no files are in focus (Aider, SURVEY `landscape-coding-fleets.md` §6).
* **Tool-set retrieval for small models.** Top-K tools per turn over the allowed view, with a tiny always-available core and a per-turn `ToolPolicy{hidden, disabled, reasons}` surfaced to the Run Inspector (odysseus, CONFIRMED `odysseus/src/tool_index.py:5,31-35`).
* **Memory tiers.** `aos/agent/<id>` for each persistent agent's own notes and ADRs; `aos/agent/<template>/<runId>` scratch for leaves; `aos/shared` receives only human-promoted items (staged drafts with provenance `origin: agent`, session kind, taint), never direct writes from a leaf or a tainted run (OpenClaw memory provenance and session-kind gating, SURVEY `openclaw.md` best part 3); memory kinds tagged `guide | answer | code` for retrieval (PentAGI kind-split store, SURVEY `pentagi.md` `registry.go:36-43`). Recalled content is marked and never re-extracted (recall-loop prevention).
* **Prompt-cache discipline.** System prompts are byte-stable within a run; tool sets never swap mid-run (Hermes "prompt-cache is sacred", SURVEY `hermes-agent.md`); children use the 5-minute cache tier because their lifetimes are short.

## 12. Phase placement

* **Phase 1** (first real loop): `eng-lead`, `scout`, `architect` (template, pinned namespace), `implementer` profiles `code` and `docs` (agent phase with no egress, which Phase 1 gets for free since there is no proxy yet), `tester` (trusted domain + fake driver, pinned commands, `verify.testdiff`), `reviewer` (both souls); delegation with `goalId`, restart-safe projections, terminators, dispatch capabilities, `verify.result`, masking condenser, cascade cancel, budget reservation, memory admission control, `policyVersion` pinning, `config/repo-profiles.yaml` with the kernel's own `class: self` entry, typed tool failures, `llm.sanitized`. Phase 1 already exercises §4.1, because the first repo the fleet works on is this one.
* **Phase 2a** (sandboxes and the wire): egress proxy with per-template allowlists, the setup/agent phase split, `git-receive-pack` and token-returning paths blocked, `hostile` domain and the Chromium worker image, `prototyper`, `implementer#refactor` with the exclusive lease, `release` (tag + GitHub release; `npm.publish` deferred per O16), packs with schema-hash pinning and fail-closed drift, exec approval binding, witness manifest, `sre` **read-only** (reconcile, drift, proposals). ## 13. Review findings applied

An adversarial review of the first draft against the three lenses (invariants and security; frontier versus theater; feasibility for one operator on one M1 Max). Blockers first.

* **F1 (blocker, invariants).** `riskCeiling` was contradicted in the same paragraphs that declared it: `tester` was `read` while holding `ws.exec`/`ws.test`, which K2 classifies `write`; `architect` was `read` "plus pmmcp writes ... which are `write`". A ceiling with parenthetical exceptions is prose. **Applied:** §2.1 now derives the class from (tool, domain, target) as a table the kernel evaluates, adds the `sandboxed-exec` and `write-scoped` classes, and §3.2 / §3.7 state ceilings that match their tool views.
* **F2 (blocker, security).** `implementer`, `refactorer` and `prototyper` held `registry.npmjs.org` egress for the whole run, and O12's default allowed installs in the worktree with the ack deferred to PR open. That runs unvetted third-party code, including `postinstall` scripts, inside a networked T2 container before any human sees the dependency. **Applied:** the Codex two-phase model (§2.2) — kernel-run setup phase with registry egress and `--ignore-scripts`, agent phase with `egress.allow: []`; `dependency-ack` moves *before* the install; O12 resolved against its own first default.
* **F3 (blocker, feasibility/correctness).** The budget arithmetic did not close: a $40 objective ceiling "including all children" against eight concurrent $6 implementers is $48 before architect, testers and reviewers. **Applied:** §2.4 makes per-template caps ceilings and enforces the objective by *reservation* atomic with the lane claim (Paperclip), with `spawn.refused{reasonCode: budget}` and queueing.
* **F4 (blocker, feasibility).** `maxChildren: 8` concurrent T2 containers is not runnable on 64 GB alongside a ~40 GB local-model budget, two Colima VMs, Qdrant and Ollama. **Applied:** `maxChildren` becomes a per-objective lifetime cap, `maxConcurrent: 3` is separate, and admission is by declared `sandbox.memoryMb` against a per-domain memory budget, plus per-provider lanes (AIOS).
* **F5 (blocker, feasibility).** The design never counted the human decisions it generates: 12-16 engineering approvals a day before four other sectors. A rubber-stamped gate records consent that was not given. **Applied:** §2.5 adds four kernel-enforced dampers (backpressure at `maxOpenApprovals: 3`, fail-closed TTL, one card per decision with the full bundle, pinned repo profiles to remove recurring exec cards) and records the mandate argument as O13 with a default of *not adopted*.
* **F6 (blocker, security).** "The verdict cannot be tainted into a false pass because it is computed from exit codes" was false, and it sat under the sector's load-bearing claim. **Applied:** §3.7 names the three forgery paths and the three structural answers — commands pinned in kernel config not the head commit, the new `verify.testdiff` hard gate on removed/skipped/weakened tests with `test-removal-ack`, and hostile-domain execution with `--ignore-scripts` and an attached (empty) proxy-decision list — and states the residual risk instead of denying it.
* **F7 (blocker, invariants).** The document never named its own first customer: this fleet editing `aos-kernel`, whose worktree contains the gate, the chain, the secrets broker, `tool-views.yaml` and the souls. **Applied:** new §4.1 — `class: self | external` in the repo profile; the running kernel never loads policy from a managed worktree; protected-area edits are `irreversible`-class for approval with no batching path; invariant-test removal denied at edit time; no process-lifecycle tool in this sector; the eval harness runs the installed kernel, not the candidate. New K12.
* **F8 (major, frontier).** `architect` was persistent without needing anything persistence provides but a pinned namespace. **Applied:** demoted to an ephemeral template with `memory.projectId: aos/agent/architect` pinned at spawn.
* **F9 (major, frontier).** `docs-writer` and `refactorer` differed from `implementer` only in model chain, ownership set and (for the refactorer) gate block. Three manifests, three souls, three eval suites for two field sets. **Applied:** one `implementer` manifest with `profiles: {code, docs, refactor}` (K1); the refactor profile keeps its own `gate` block. Roster drops from 11 manifests to 7.
* **F10 (major, phase ordering).** `sre` shipped its production deploy, rollback and migration surface in Phase 2 alongside the packs, ahead of that phase's own critical-fixes audit pass and beyond its stated exit criterion. **Applied:** split into Phase 2a read-only and Phase 2b ops-after-audit, each irreversible op bound individually with a staging drill as promotion evidence.
* **F11 (major, security).** Taint was declared by the spawner in three manifests ("the spawn spec marks the run tainted", "clean when the brief is operator-authored"). `eng-lead` is a model; that makes the model an access-control decider. **Applied:** §2 makes taint kernel-computed from artifact provenance, raisable but not clearable by a spawn spec, cleared only by a logged human quarantine release; §3.3 and §3.6 restated.
* **F12 (major, security).** Nothing said what happens to a live run when `tool-views.yaml` or a pack's schema changes under it. **Applied:** `policyVersion` pinned in `run.started`, stricter-of evaluation on drift, `policy.drift` event, pack schema drift fails closed for the rest of the run (openclaw spawn-time snapshot; Managed Agents' ask-by-default rationale).
* **F13 (major, correctness).** Killing `eng-lead` left up to `maxConcurrent` leaves burning budget against a dead parent; only `eng.pause` was specified. **Applied:** cascade cancellation with a `cancelling` state, per-leaf fencing and `run.cancelled`, and an incomplete cascade reported as a failure (openclaw).
* **F14 (major, security).** Leaf summaries — model text derived from repository content — flowed into the one agent that can spawn, as free prose. **Applied:** zod-typed terminator payloads with a 2 KB free-text cap rendered as explicitly untrusted content, plus kernel stripping of forged tool-result and event-envelope shapes from every `llm.response` with an `llm.sanitized` event (MiroFish).

* **F16 (minor, correctness).** The router could bind a model with no pricing entry, silently voiding invariant 4's cost field and every budget above it. **Applied:** no price, no binding; local models must declare `pricing: {input: 0, output: 0, metered: false}` explicitly.
* **F17 (minor, security).** `evidence.get` was unscoped, which is a general log-read primitive in an agent's hands. **Applied:** scoped to the objective under review and to three event kinds, redacted.
* **F18 (minor, correctness).** `ws.test` failing to execute would surface as a string the model could narrate past. **Applied:** typed `failure` on every tool result with `WARN|RAISE` per tool and `RAISE` forced for verification tools (crewAI `ToolFailurePolicy`).
* **F19 (minor, frontier — missed pattern).** No spec-quality triage: every objective paid for a scout and an architect. **Applied:** §5.1 step 1b, a kernel-scored rubric routing well-specified briefs straight to one implementer (icat-agent).
* **F20 (minor, frontier — missed pattern).** No in-run rollback point; a 45-minute run that went wrong restarted from zero. **Applied:** shadow-ref checkpoints per accepted edit, retention-bounded and profile-disableable, with Cline's storage caveat carried over rather than hidden.
* **F21 (minor, frontier — missed risk).** Parallel implementers reproduce Cognition's Flappy Bird failure unless shared implicit decisions are made once. **Applied:** a `decisions` block in the plan artifact injected verbatim into every sibling brief; unparallelizable task sets must be serialized by the architect; the integration-lane re-run is the check.

* **F23 (minor, correctness).** Approval cards had no expiry semantics outside a mention in K3. **Applied:** fail-closed TTL (24 h; 2 h for `question`) resolving to deny and interrupting the waiting run, and the durable consent-record field set from agency-os.

## 14. Rejected review findings

Things the review raised and this revision deliberately did not change.

* **"Parallel implementers contradict Cognition's 'writes stay single-threaded', so go single-threaded."** Rejected. Cognition's own 2026 follow-up describes the shape we run — one orchestrator, ephemeral isolated subagents returning compressed summaries, no peer channel, no shared mutable state — and its warning is about *conflicting implicit decisions*, not about parallelism as such (SURVEY `landscape-coding-fleets.md` §4). Writes here are already single-threaded *per file set*: one writer per worktree, one integration owner. F21 adds the missing mitigation. Going fully serial would cost the main throughput lever for no measured safety gain, and the eval harness (K8) compares the shapes at equal spend before either becomes default.
* **"Merge `reviewer#security` into `reviewer#code`; two model reviewers is theater."** Rejected. They have different evidence surfaces, not different adjectives: the security soul reads `repo.deps_diff`, `verify.secrets`, `verify.witness` and the proxy-decision summary, which the code soul does not see at all. The hybrid-verifier result is that execution-based and execution-free verifiers each saturate alone (R2E-Gym, SURVEY `landscape-coding-fleets.md` §15). What the review *did* extract is the discipline: both are advisory, both are schema-dropped without a line and a consequence, and their disagreement rate is a tracked KPI.
* **"Drop `prototyper` until Phase 3, since its first customer is the Tauri shell."** Rejected, per O9's existing reasoning: a prototyper without visual verification is an implementer with a nicer soul, and the Chromium worker image it needs is the same image `tester` needs for browser replays. It is idle for part of a phase; that is cheaper than shipping it twice.
* **"Make PR-open a standing mandate now to fix approval fatigue."** Rejected for Phase 1-2, recorded as O13 with the argument written out. Changing `approval: always` on a tool is a CLAUDE.md ask-before item, the four dampers in §2.5 are strictly safer, and the honest way to ask the operator for a mandate is with a month of measured card counts rather than an estimate.
* **"Give `tester` an LLM by default so failures come back explained."** Rejected. The default profile stays model-free: it is the cheapest run in the fleet and its value is that the verdict is not model text. The optional `analyze` capability already exists for the reviewer's benefit and stays opt-in per spawn.
* **"Let the fleet restart the kernel after a self-repo merge so the loop closes."** Rejected outright (§4.1). The operator restarting the daemon is the human action that makes a self-modification auditable; automating it would let a merged change take effect with no human between the diff and the running binary.
* **"Adopt CubeSandbox `on_timeout: pause` (snapshot) instead of kill for expensive runs."** Noted, not adopted. CubeSandbox supports both (CONFIRMED `CubeSandbox/docs/guide/lifecycle.md:17,22`), and a paused snapshot of a 45-minute implementer is attractive, but it keeps a stopped VM's state on disk holding potentially tainted content past the run's lifetime and complicates the fencing story. Checkpoints (F20) give most of the recovery value at git cost. Revisit if checkpoint retries prove insufficient.
* **"Fold `release` into `eng-lead`."** Rejected. Its surface is three distinct irreversible tools with idempotency keys and a clean-worktree precondition, which is exactly the "distinct gate posture" criterion. What the review did change is scope: `npm.publish` is deferred (O16) until a repo actually publishes.
