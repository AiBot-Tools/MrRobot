### 3.5 Event log schema (frozen with the chain, D11/D4)

```sql
CREATE TABLE events (seq INTEGER PRIMARY KEY AUTOINCREMENT, id TEXT NOT NULL UNIQUE, ts TEXT NOT NULL, type TEXT NOT NULL,
  run_id TEXT, agent_id TEXT, payload TEXT NOT NULL, prev_hash TEXT NOT NULL, hash TEXT NOT NULL UNIQUE) STRICT;
CREATE TRIGGER events_no_update BEFORE UPDATE ON events BEGIN SELECT RAISE(ABORT, 'events is append-only: UPDATE refused'); END;
CREATE TRIGGER events_no_delete BEFORE DELETE ON events BEGIN SELECT RAISE(ABORT, 'events is append-only: DELETE refused'); END;
CREATE TRIGGER events_append_only BEFORE INSERT ON events
  WHEN NEW.seq IS NULL OR NEW.seq != (SELECT coalesce(max(seq), 0) + 1 FROM events)
    OR EXISTS (SELECT 1 FROM events WHERE id = NEW.id OR hash = NEW.hash)
BEGIN SELECT RAISE(ABORT, 'events is append-only: seq must be tail+1 and id/hash unique'); END;
```

**The seq contradiction in security §1.3 ("never supply seq") vs §2.2 ("seq is in the hash") is resolved thus:** the store reads the tail inside `BEGIN IMMEDIATE`, computes `seq = tail + 1`, hashes `{seq, id, ts, type, runId, agentId, payload, prevHash}` over the **redacted** payload, and supplies `seq` in the single prepared INSERT; the trigger refuses anything else (NULL seq, gaps, duplicates, `INSERT OR REPLACE`, `REPLACE INTO` — CONFIRMED §8 V3, `errcode 1811`). **`AUTOINCREMENT` is kept** even though the store supplies `seq`: it is compatible with explicit values on a `STRICT` table (CONFIRMED §8 V7) and keeps `sqlite_sequence.seq` monotonic, which is security §1.4 defence #3. Precisely: an explicit re-insert of `tail+1` after a tail delete fills the hole and leaves **no** gap (§8 V7: rows `1,2,3,4`, `sqlite_sequence = 4`), so the defence is not a visible gap but a visible **counter**: the store reads `sqlite_sequence.seq` inside the same `BEGIN IMMEDIATE` and refuses to append (`ChainBroken`, `'truncation: sqlite_sequence (N) is ahead of the tail (M)'`) when it exceeds `max(seq)`, and `verifyChain` reports the same reason even without an anchor (an attacker must also edit `sqlite_sequence`, which the anchor then catches). Per-open pragmas: `journal_mode=WAL` (file DBs), `synchronous=FULL`, `recursive_triggers=ON`; every reader opens `readOnly: true`. Boot compares each expected trigger's `sqlite_master.sql` against the canonical DDL (name **and body**, CONFIRMED §8 V6). `GENESIS = sha256('aos-kernel:events:v1')` (**D11**). Anchor: `<dataDir>/events.head` (0600) every `anchorEvery` appends and at shutdown (**D12**). **Anchor semantics (this overrides security §2.3's tail-equality check, which would refuse every boot after a crash, SIGKILL or power loss between anchor writes):** `verifyChain(db, anchor)` passes iff the chain verifies **and** `tail.seq >= anchor.seq` **and** `hash(row at anchor.seq) === anchor.hash`. It fails with `'truncation: tail (seq N) is behind the anchored head (seq M)'` only when `tail.seq < anchor.seq`, and with `'rewrite: row at anchored seq M has a different hash'` when that row exists with another hash. Rows after the anchor are legitimate (the log is expected to be ahead of `events.head` between writes); boot re-anchors to the verified tail immediately after a successful verify, so an unclean exit costs nothing but the re-anchor.
