## What it is

A prompt library, not an agent system. Each file is one persona (YAML frontmatter + Markdown body) meant to be dropped into a host that already has an agent loop: Claude Code subagents, Cursor, Codex TOML, Gemini CLI, OpenCode, Qwen, OpenClaw workspaces (SOUL.md/AGENTS.md/IDENTITY.md), Hermes (a lazy-router plugin), and others (CONFIRMED: `tools.json`, `scripts/convert.sh`). The repo's own `SECURITY.md` states the scope: "Non-executable prompt definitions ... Never add executable code inside agent Markdown files." There is no orchestration code, no memory store, no tool runtime, no sandbox, no credential handling. Everything under "orchestration", "memory", "gates" is text the host LLM is asked to follow.

## Orchestration model

CONFIRMED, all prose:

- `specialized/agents-orchestrator.md` — an "autonomous pipeline manager" persona: `PM → ArchitectUX → [Dev ↔ QA loop] → Integration`, max 3 retries per task then "escalate", "Handle errors and bottlenecks without manual intervention". Phases are literally shell comments plus quoted spawn prompts ("Please spawn a project-manager-senior agent to ..."). Decision logic is `IF QA = PASS ... IF QA = FAIL ...` in a Markdown block. State is tracked in `project-tasks/*-tasklist.md` checkboxes.
- `strategy/nexus-strategy.md` — "NEXUS" doctrine: 7 phases (Discover → Strategize → Scaffold → Build → Harden → Launch → Operate), a quality gate between each with a named "Gate Keeper" agent (section 12.1: Production Gate = "Reality Checker (sole authority)"), three activation modes (Full / Sprint 15-25 agents / Micro 5-10), a producer→consumer division matrix (10.1), critical handoff pairs (10.2), escalation "To Agents Orchestrator / To Studio Producer" (11.3), risk owners matrix (13.1).
- `strategy/coordination/handoff-templates.md` — Standard Handoff, QA PASS, QA FAIL, Escalation Report templates.
- `strategy/coordination/agent-activation-prompts.md` — copy-paste activation prompts per agent with `[PLACEHOLDERS]`.
- `strategy/runbooks.json` + `strategy/runbooks/scenario-*.md` — machine-readable rosters per scenario with activation groups (`"activation": "always" | "week 3+" | "as needed"`); slugs are file stems and CI (`scripts/check-runbooks.sh`) verifies each resolves to a real agent.
- `integrations/hermes/README.md` + `scripts/build-hermes-plugin.py` — the one piece of real code: a Hermes plugin exposing four tools (`agency_agents_search`, `_inspect`, `_load`, `_delegate`) over an on-disk `agents.json`, explicitly to avoid preloading 279 skills into the host's catalog.

Who decides: the orchestrator persona and the QA personas. PASS/FAIL, advance/retry, and escalation are all LLM judgments. Escalation targets are other agents ("Studio Producer decides: fix, descope, or accept with risk", 12.2), not a human.

### Real vs theater

Method (CONFIRMED): frontmatter census; code-fence density; presence of `tools:`/`services:`; whether the body names distinct tooling or context that a different persona would not have.

- Only **17/279** declare `tools:` (all Claude-Code-style lists: `WebFetch, WebSearch, Read, Write, Edit[, Bash]`; 9 marketing/paid-media/product/PM files, 7 of them with `Bash`). Only **4** declare `services:` (`ui-finish-gate-reviewer`, `carousel-growth-engine`, `multi-platform-publisher`, `x-twitter-intelligence-analyst`). **0** declare `model:`. The `tools:` field is only emitted by the qwen/zcode converters (`scripts/convert.sh:428,463`) and the identity (claude-code) format.

## Memory model

CONFIRMED: none built in. The "Memory" bullet in Identity and the "Learning & Memory" section (169 files) are aspirational text ("You remember pipeline bottlenecks ..."). Real memory is an optional add-on in `integrations/mcp-memory/README.md`: any MCP server with `remember` / `recall` / `rollback` / `search`, plus a "Memory Integration" prompt block telling the agent to recall at session start, remember on decisions/deliverables, tag with agent name + project + topic, and on handoff "remember your deliverables tagged for the receiving agent". `examples/workflow-with-memory.md` shows the pattern replacing copy-paste handoffs. Guidance is explicit that "the LLM will figure out when to remember" and that rollback is "the killer feature".

## Tool / plugin / MCP model

CONFIRMED: no tool definitions. `tools.json` is an *install-target* catalog (which host dirs to write to, which converter format), not agent tools. Tool access, where declared, is a per-persona allowlist string in frontmatter. MCP appears only as (a) the memory add-on above, (b) `specialized-mcp-builder` (a persona that writes MCP servers), (c) services named inside `multi-platform-publisher` (`xhs-mcp`). ## Sandbox & security posture

CONFIRMED: no runtime, therefore no isolation, no credential handling, no gates. `SECURITY.md` rules: no secrets in agent files, no executable code in Markdown, review shell scripts, report prompt-injection-shaped agent definitions. Security *doctrine* exists as persona text and is good: `secrets-credential-engineer` ("a leaked secret is already burned — rotation at the provider is the remediation", "never print, log, or echo a raw secret", "a credential fetched outside the vault is an incident"); `agentic-identity-trust` ("never trust self-reported identity/authorization", "never trust mutable logs", "if evidence cannot be written, the action should not proceed"); `multi-agent-systems-architect` (scope tokens never passed between agents, allowlisted network, per-call audit log with trace_id, sanitizer agent for untrusted content, HITL gate placement table). But every one of these is advice to the model, and the same file lists "default approve" as an acceptable blocking-gate timeout behavior and an "Advisory Flag Gate" that acts first and lets a human roll back later.

## BEST PARTS

1. **Persona/operations split with header-keyword classification.** Evidence: `scripts/convert.sh` `convert_openclaw()` (SOUL.md = identity / communication / style / critical rules / learning & memory; AGENTS.md = mission / deliverables / workflow / metrics; IDENTITY.md = emoji + name + vibe), mirrored by `scripts/lint-agents.sh` `classify_header_target` and `CONTRIBUTING.md` "Agent Structure". Sector: kernel (all). Why: it is exactly our `souls/*.md` vs `agents/<id>/AGENTS.md` boundary; adopting the keyword set gives a lintable rule for what may live in a read-only soul (voice, rules) versus the versioned manifest (mission, tools, deliverables).

2. **Evidence-over-claims QA doctrine.** Evidence: `testing/testing-reality-checker.md` ("Default status is NEEDS WORK until overwhelming proof", "treat perfect scores from prior agents as a red flag", "if evidence is inconclusive: default to FAIL"), `testing/testing-evidence-collector.md` ("first implementations ALWAYS have 3-5+ issues", quote the spec, document what you see), `nexus-strategy.md` §1.2 "Evidence Over Claims". Sector: engineering (the `checker` ephemeral template), executive (CEO summaries). Why: the cheapest known defense against a coder agent's self-certification; our checker soul should carry these rules verbatim and the kernel should require an evidence artifact reference in `run.finished` for coder runs.

3. **Handoff, QA-FAIL and escalation templates as structured payloads.** Evidence: `strategy/coordination/handoff-templates.md` (From/To/Phase/Task ref/Priority; Current State; Relevant Files; Dependencies; Constraints; Deliverable + acceptance criteria checklist; Must pass; Evidence required; Handoff to next), QA FAIL (per issue: Expected / Actual / Evidence / Fix instruction / Files to modify; "Fix ONLY the issues listed"), Escalation Report (failure history per attempt, root cause, options checklist). Sector: executive. Why: this is the delegation payload our CEO should put into a pmmcp task goal and the `delegate_task` body — zod-typeable, and it makes "trustworthy summary" (Phase 1 exit) a schema rather than prose.

4. **HITL gate placement table, gate types, and the agent role definition template.** Evidence: `engineering/engineering-multi-agent-systems-architect.md` lines 328-358 (Irreversibility / High blast radius / Low confidence / Novel situation / Regulatory exposure / Explicit policy → Blocking approval vs Advisory vs Sampling; "Over-escalation → rubber-stamping → HITL becomes theater"), lines 359-366 (every review surface shows reasoning, alternatives, consequence, confidence, one-click approve/reject/escalate), lines 392-424 (`RECEIVES FROM` / `NOT RESPONSIBLE FOR` / `PRODUCES` / `FAILURE BEHAVIOR` / `TOOLS PERMITTED` / `CONTEXT WINDOW BUDGET`), lines 283-320 (least-privilege tool matrix, scope tokens not passed, sanitizer agent for untrusted content). Sector: kernel, ops-security. Why: the table is a ready classification rubric for `tool-views.yaml` risk levels and the approvals UI (Phase 3 Approvals view); the role template is a checklist for `agent.yaml` fields we do not yet have (negative scope, context budget, failure behavior).

5. **Roster as data with CI-enforced integrity and originality.** Evidence: `divisions.json` (single source of truth, `scripts/check-divisions.sh`), `strategy/runbooks.json` (scenario rosters with `activation: always | week 3+ | as needed`, slugs verified by `scripts/check-runbooks.sh`), `scripts/check-agent-originality.sh` (entity-neutralized shingle overlap, WARN 20 / FAIL 40), `scripts/lint-agents.sh` (required `name`/`description`/`color`, recommended sections, LF only). Sector: kernel, executive. Why: runbooks with activation groups are the shape of a CEO plan (core team always, growth team later, support as needed) and a natural fixture for the Phase 1 eval harness; the originality check is how we stop the fleet from growing 15 souls that differ by a platform name.

6. **Lazy roster routing with a fixed tool surface.** Evidence: `integrations/hermes/README.md` (four tools: search / inspect / load / delegate; "do not preload the full Agency roster"), `scripts/build-hermes-plugin.py` (roster in `agents.json`, duplicate-slug guard). Sector: executive, kernel. Why: the CEO should never see 279 personas in context; it should search a catalog and delegate by slug, which is also how ephemeral templates (`scout`/`checker`/`worker`) get a soul selected at spawn time without widening what the run can reach.

7. **Memory tagging convention on handoff.** Evidence: `integrations/mcp-memory/README.md` "The Pattern" (recall at start by role + project; remember decisions/deliverables tagged agent + project + topic; on handoff, remember tagged for the receiver; search last known-good on failure), `examples/workflow-with-memory.md`. Sector: all. Why: maps directly onto pmmcp `project_id` namespacing (`aos/agent/<id>` for own, `aos/shared` for handoffs) and tells us what the kernel should write on `run.finished` so the next delegated run can `recall` instead of being re-briefed.

8. **Draft-first, never-publish, rate-and-risk rules for the growth sector; "burned secret" rules for ops.** Evidence: `marketing/marketing-multi-platform-publisher.md` ("NEVER trigger publish-to-production ... return draft URLs and explicitly hand control back", daily caps, inter-post jitter, platform-fit matrix), `security/security-secrets-credential-engineer.md` (rotate at provider, never echo, one credential per workload). Sector: growth, ops-security. Why: these are the soul texts for `publisher` and `comms`; in our kernel the rule is enforced by the gate (`irreversible` → human), and the persona text keeps the model from even proposing a bypass.

## BAD PARTS / anti-patterns

1. **The orchestrator and every gate are LLM judgments.** Evidence: `specialized/agents-orchestrator.md` "Autonomous Operation: Run entire pipeline with single initial command ... Handle errors and bottlenecks without manual intervention"; `nexus-strategy.md` §12.1 "Production Gate: Reality Checker (sole authority)", §12.2 escalation ends at "Studio Producer decides: fix, descope, or accept with risk"; `handoff-templates.md` §4 "Escalation To: Agents Orchestrator / Studio Producer". Why we leave it out: our invariant 3 says the model never makes an access-control decision; gates, retry caps and escalation must be kernel state (approvals projection, run retry cap), with the human as the terminal escalation target, not another persona.

2. **Tool access is authored in the persona.** Evidence: `tools:` frontmatter in 17 files, e.g. `marketing/marketing-growth-hacker.md`, `paid-media/paid-media-ppc-strategist.md`, `product/product-manager.md` grant `Bash` (grep: `^tools:` values); emitted verbatim by `convert_qwen` / `convert_zcode`. Why: capability follows from the manifest tier and `tool-views.yaml`, never from a prompt file; a soul that names tools invites the model to assume it has them.

3. **Roster bloat and re-skins.** Evidence: 279 personas, 36 marketing of which 15 are China-platform variants, 21 game-dev, 13 GIS, 6 spatial ~200 words each; median 1,809 words, 66 files >50% code fences; the maintainers shipped `scripts/check-agent-originality.sh` because re-skins kept arriving. Why: every extra soul is prompt tokens on every run and a manifest to keep honest; our fleet should have ~10 real agents and a small catalog of souls, and platform specifics belong in tool-view config, not in ten near-identical personas.

4. **Fictional memory and self-modification language.** Evidence: 169 files with `## 🔄 Learning & Memory` ("Remember and build expertise in ...") and 217 with a "Memory:" bullet, with no store; `integrations/mcp-memory/README.md` "Let the LLM decide what's important" and `rollback` as a first-class tool. Why: our memory is pmmcp with the kernel as caller and an append-only event chain; a persona that believes it "learns" will try to write to its own soul (invariant 8) or treat rollback as undoing logged state (invariant 5).

5. **Stale executable content inside prose.** Evidence: `testing/testing-evidence-collector.md` "ALWAYS RUN FIRST: `./qa-playwright-capture.sh http://localhost:8000 public/qa-screenshots`" (script not in repo), `engineering/engineering-rapid-prototyper.md` 1,840-word persona of which most is a Next.js/Prisma/Clerk sample with `url = env("DATABASE_URL")`; 66 personas are majority code. Why: a coder agent will try to run or copy these; our AGENTS.md should reference the repo's real commands, and samples belong in skills/evals, not souls.

6. **Gate semantics that our invariants forbid.** Evidence: `engineering-multi-agent-systems-architect.md` "Timeout behavior must be defined: default approve, default reject, or escalate further"; "Advisory Flag Gate: pipeline continues ... human can trigger rollback"; "Sampling Gate: human reviews X% of outputs". Why: approvals never time out to approve, `irreversible` is never advisory or sampled; we take the placement table and drop these three options.

## Conflicts with CLAUDE.md invariants

1. Invariant 3 (gate → human → quarantine → execute → log; model never decides access): NEXUS gates are judged by personas (`nexus-strategy.md` §12), escalation terminates at an agent, default-approve timeouts and advisory-after-the-fact gates are offered as valid (`multi-agent-systems-architect.md` lines 341-358).
2. Invariants 2 and 7 (agents hold no connections/keys; unknown tools kernel-only): per-persona `tools:` allowlists including `Bash`; `services:` frontmatter implies the persona reaches the vendor directly (`multi-platform-publisher.md` names cookies/tokens it manages).
3. Invariant 6 (ephemerals bounded by template): `agents-orchestrator.md` spawns "appropriate developer agent" ad hoc with whatever context it composes; no template ceiling.
4. Invariant 8 (souls read-only): "Learning & Memory" sections instruct the persona to accumulate and refine its own rules.
5. Invariants 4 and 5 (every LLM call logged with cost; append-only chain): no notion of cost or a log; the mcp-memory `rollback` tool mutates shared state outside any chain.
6. Invariant 9 (container hardening): not a conflict, an absence — nothing here runs.

## Verdict

Take the schema, not the system: the soul/AGENTS header split and lint rules, the evidence-first QA rules for the `checker` soul, the handoff / QA-FAIL / escalation templates as zod-typed delegation payloads, the HITL placement table and role-definition fields for `agent.yaml` and `tool-views.yaml`, runbooks-as-data with activation groups for the CEO planner and eval harness, lazy catalog routing, and the memory tagging convention for pmmcp. Leave the prose orchestrator, persona-authored tool allowlists, fictional learning sections, the 250-odd voice-only re-skins, embedded stale code samples, and every gate variant that lets the model or a timeout approve. There is no trading persona to borrow; the finance-investment-researcher's bull/bear, thesis-breaker and quantify-the-downside rules are the only text worth carrying into a trading `analyst` soul, and execution stays a human-approved `irreversible` tool by construction.
